# Accord · согласование заявок

<!-- status:versions -->
Текущие зависимости: **common2 2.21.1 / react2 3.5.1**.
<!-- /status:versions -->

Самостоятельный пример: сотрудник описывает запрос, отправляет неизменяемую версию на рассмотрение, проверяющий согласовывает, возвращает на уточнение или отказывает. История показывает, как команда пришла к решению.

Собран из чистой копии [forms](../forms/README.md) как контрольная проверка каталога: насколько быстро из готовых блоков получается новый SaaS. Измерение — [отчёт K08](../../doc/reports/K08-approvals.md).

## Запуск

```text
npm ci
npm run build
npm start
```

Сервер: `http://127.0.0.1:3818`. Порт меняется переменной `SERVICE_PORT`, каталог данных — `SERVICE_DATA_DIR` (по умолчанию `approvals-data`). Описание клиента — `/api/client`, библиотечные login и команды — `/api/approvals`, состояние процесса — `/health`.

Для разработки интерфейса: `npm run dev` рядом с запущенным `npm start`.

Второй обслуживающий узел:

```text
SERVICE_UPSTREAM=http://127.0.0.1:3818 SERVICE_NODE_ID=approvals-a npm run start:node
```

## Роли и аккаунты

Пароль каждого демо-аккаунта — имя аккаунта плюс `-pass`.

| Аккаунт | Роль | Что может |
| --- | --- | --- |
| `requester` | Сотрудник | Создаёт и правит свою заявку, отправляет версию, отзывает её с рассмотрения |
| `requester2` | Сотрудник | То же, отдельный автор для проверки изоляции |
| `reviewer` | Проверяющий | Видит отправленные версии команды, согласовывает, возвращает или отказывает |
| `owner` | Владелец | Всё то же плюс состав команды и роли |
| `outsider` | Владелец Harbor Labs | Другая организация: заявок Northstar не видит |

Сотрудник видит только свои заявки. Проверяющий и владелец видят отправленные версии всей организации, но не чужие черновики. Свою заявку не согласовывает никто, включая владельца.

## Команды домена

| Команда | Кто | Правило |
| --- | --- | --- |
| `requestSave` | автор | Создаёт или правит черновик. Разрешено до отправки и после возврата или отзыва |
| `requestSubmit` | автор | Фиксирует неизменяемую версию со снимком анкеты. Не более 20 версий |
| `requestDecide` | проверяющий, владелец | Решение по конкретной версии. Возврат и отказ требуют объяснения до 2000 символов |
| `requestWithdraw` | автор | Отзывает свою ожидающую заявку |
| `memberRole` | владелец | Меняет или отзывает роль. Последнего владельца снять нельзя |

Представление `workspace` отдаёт каждому клиенту только разрешённое: свои организации, видимые заявки, анкету и — владельцу — состав команды.

## Идемпотентность и версии

У каждой команды два разных идентификатора.

- `requestId` библиотеки защищает от повтора одного сетевого вызова: common2 вернёт прежний receipt.
- `key` приложения — ключ намерения. Одно действие пользователя может прийти разными командами после переподключения или обновления страницы; ключ гарантирует, что вторая заявка не появится. Повтор того же ключа с другими данными отклоняется как конфликт.

`revision` заявки — оптимистичная блокировка: команда с устаревшей ревизией отклоняется до применения.

Отправленная версия хранит копию анкеты на момент отправки. Изменение вопросов организации не меняет то, по чему принималось решение.

## Пределы

До 1000 заявок на стенд, 20 версий на заявку, 5000 ключей намерения, 160 символов в названии, 32 KiB на ответы. Пределы защищают небольшой стенд от бесконечного роста и не заменяют эксплуатационную политику.

## Проверки

```text
npm run typecheck
npm test
npm run build
```

`backend/domain-check.ts` работает на настоящем service leader: роли и организации, идемпотентность ключа и конфликт того же ключа, устаревшая ревизия, условные вопросы и отказ скрытому полю, неизменяемость отправленной версии, запрет решения по своей заявке, обязательное объяснение возврата, повторное решение той же версии, история, отзыв, состав команды и предел 20 версий настоящим циклом «возврат — правка — отправка».

`backend/check.ts` поднимает authority и два обслуживающих узла: полный цикл через разные узлы, изоляция чужой организации, повтор ключа намерения, отказ узла, отзыв роли на уже открытой сессии, восстановление заявок и истории после рестарта. Печатаемый замер — небольшая приёмочная выборка на одной машине, а не производительный benchmark.

## Ограничения

Внешних интеграций нет: ни почты, ни платежей, ни модели. Вход демонстрационный, по паролю из состояния. Файлы к заявке не прикладываются. Организации и анкета заданы в начальном состоянии и через интерфейс не создаются — владелец управляет только составом команды. Приложение не запускает и не требует соседних примеров.
