# Общие правила кода и примеров

Эти правила действуют по умолчанию для приложений в этом репозитории. Они описывают желаемую архитектуру, а не требуют дополнительного согласования обычных действий в рамках поставленной задачи.

## Назначение репозитория

- Создавайте небольшие, но законченные приложения с реальным поведением, которые можно использовать как основу боевого проекта.
- Показывайте `wenay-common2` и `wenay-react2` как основной набор механизмов приложения: фасады, RPC, роли, реактивное состояние, replay, reconnect и репликация должны по возможности обеспечиваться библиотеками.
- Не добавляйте Zod, параллельную систему типизации, транспорт, reconnect, replay или другую инфраструктуру, если нужный механизм уже есть в библиотеках.
- Используйте только публичные экспорты опубликованных npm-версий. Не подменяйте зависимость соседним репозиторием, `npm link`, локальной сборкой или архивом.
- Сохраняйте точные версии пакетов и воспроизводимую установку. После публикации нужного исправления обновляйте зависимость и повторно проверяйте сценарий.
- У масштабируемого примера должен быть реальный эффект: узлы действительно обслуживают нагрузку, разделяют или реплицируют состояние и имеют описанное поведение при отключении.

## Перед реализацией

- Сначала проверьте, нет ли нужной логики в приложении или публичном API установленных библиотек. Используйте готовый механизм; если его почти достаточно, предпочитайте небольшой адаптер повторной реализации.
- Определите несколько мест, в которых будет жить существенное поведение, и минимальные связи между ними.
- Соберите самый маленький рабочий скелет с правильными границами. Создавайте ресурс раньше его потребителя, но не стройте целый слой заранее.
- Держите горизонтальных слоёв немного и делайте их явными. Если временное переплетение остаётся постоянным, разделите ответственности.

## Слои и фасады

- Слой считается оформленным, когда у него есть намеренно спроектированный фасад.
- Фасад служит системой адресации ответственности, а не случайным набором методов. По нему должно быть понятно, где менять конкретное поведение.
- Для крупной поверхности используйте многоуровневые фасады по реальным границам и аудиториям. Небольшую поверхность можно оставить плоской.
- Называйте части фасада по назначению: `control` для входящих команд, `resource` для сырого IO, `events` или `on` для исходящих событий, `view` для синхронного чтения, `health` и `source` для соответствующих поверхностей. Избегайте общего имени `api`.
- Одна часть фасада представляет одну границу или аудиторию. Если потребитель постоянно выбирает из неё несвязанные поля, разделите поверхность.
- Входы и поведение передавайте вниз через `deps`; факты поднимайте событиями. Потоки подписки (`UseListen` и аналоги) оставляйте на внешней поверхности.
- Целые части фасада ретранслируйте через spread, а не копированием каждого поля. Один элемент может обоснованно присутствовать в нескольких фасадах.
- Преобразование сырых данных в типизированные — отдельная ответственность. Обычный слой преимущественно передаёт уже правильно сформированные фасады.
- Ролевой фасад должен выдавать конкретному типу клиента только разрешённые команды и представления. Доступ проверяется при построении фасада и повторно на сервере во время выполнения команды; предметные ограничения остаются внутри операции.

## Фабрики и внутреннее устройство

- Для сервисов, слоёв и оркестрации с состоянием используйте фабрики с замыканием: `function createX(deps) { ... return { ... } }`.
- Экспортируемая или повторно используемая фабрика принимает один явный объект `deps`. Вложенные фабрики и локальные помощники могут захватывать окружающее состояние.
- Храните скрытое состояние в замыкании и явно собирайте внешний фасад. Не используйте класс только как контейнер методов сервиса.
- Оставляйте классы там, где их семантика относится к модели или контракту: value objects, коллекции, итераторы, наследники `Error`, требования фреймворка или значимое поведение прототипа и конструктора.
- Разделяйте ресурсы (соединения, сокеты, хранилища и адаптеры), повторно используемые чистые утилиты и предметную логику.
- Выносите утилиту только при реальном повторном использовании. Одноразовый приватный помощник держите рядом с местом применения.

## Типизация

- Реализация служит источником типа. Тип экспортируемой фабрики выводите как `export type X = ReturnType<typeof createX>` вместо параллельного интерфейса.
- Общий контракт вводите только для настоящего семейства похожих слоёв и оставляйте в нём минимальную общую поверхность. Реализацию проверяйте через `satisfies`; потребители зависят от контракта.
- Выводите типы из исходных таблиц и объединений с помощью `Extract` и других стандартных средств вместо повторного объявления полей.
- При ретрансляции сохраняйте исходные типы и следите, чтобы вывод не сужался случайно до значений вроде `0 | 1` или `undefined`.
- Оставляйте generic только там, где его специализирует вызывающая сторона или он нужен для проверки через `satisfies`.
- Префиксуйте алиасы объединений и примитивов буквой `t`, например `tOrderId`. Параметры generic пишите в верхнем регистре: `T`, `K`, `Cb`. Реестры и таблицы объявляйте `as const` и выводите из них литеральные типы.
- Отдельную проверку типов можно усиливать позже, но новый код уже должен использовать типизационную систему библиотек и TypeScript без дублирующих схем.

## Синтаксис и комментарии

- Используйте `==` и `!=`, кроме случаев, где строгая проверка действительно нужна.
- Используйте одинарные кавычки, отступ в четыре пробела и не ставьте точки с запятой.
- Не указывайте возвращаемый тип функции, если аннотация не улучшает чтение и не задаёт необходимое сужение.
- Именуйте функции с нетривиальной логикой, функции, способные выбросить исключение, асинхронные обработчики и обработчики событий. Стрелочные функции подходят для простых getters, mappers и predicates.
- Разделяйте крупные части файла короткими заголовками вида `// ===...===`. Комментарии объясняют причину решения, а не пересказывают код.

### Плотность

- Строка до 160 символов. Исключение — одна строковая константа, URL или строка импорта, которую нельзя разбить.
- Одно действие в строке. Точка с запятой не соединяет операторы: `if (x) {a(); b()}` записывается блоком в несколько строк.
- Цепочка из трёх и более вызовов `map`/`filter`/`flatMap`/`some`/`every`/`reduce`/`find` в одной строке разбивается на именованные шаги или отдельную функцию.
- Условие с тремя и более `&&`/`||` выносится в именованный предикат или переменную с говорящим именем.
- Пробелы после запятой, вокруг `=` и операторов, после `if`, `for` и `while`. Сжатый код без пробелов не принимается.
- Тернарный оператор без вложенности: вложенный заменяется `if`, `switch` или таблицей.

Эти правила проверяет `scripts/style-check.mjs` и они входят в `npm run check:all`. Они не отменяют краткость: короткая функция в одну строку остаётся допустимой, пока укладывается в перечисленное.

## Проверка результата

- Проверяйте каждый существенный примитив и ресурс до слоя, который на него опирается.
- Проверяйте обёртку через её фасад и контракт, а не через внутренние детали.
- Проверяйте приложение как композицию слоёв и проходите законченный пользовательский сценарий для каждого типа клиента.
- Для масштабирования проверяйте реальную топологию, согласованность состояния, переподключение и отключение узла, а не только сборку или изменение числа в интерфейсе.

## Прогресс работы

- Для задачи шире небольшой локальной правки создайте перед изменениями краткий файл `doc/progress/<task>.md`.
- Фиксируйте в нём цель, контрольные точки, заметные решения, блокеры и выполненные или оставшиеся проверки.
- Обновляйте файл после важных этапов и перед переключением контекста.
- После завершения удалите временный файл прогресса. Если работа приостановлена, оставьте в нём точное следующее действие; долговечные выводы перенесите в документацию приложения или `doc/changes/`.

## Обнаруженные ограничения библиотек

- Не исправляйте библиотеку внутри примера и не подключайте неопубликованный код вместо npm-пакета.
- Оформляйте проблему как воспроизводимое задание: пользовательский сценарий, точные версии, фактическое и ожидаемое поведение, минимальные шаги воспроизведения, проверенные публичные API и критерии готовности.
- Предлагайте минимальное общее улучшение библиотеки; предметные правила сохраняйте в приложении.
- После публикации версии обновите точную npm-зависимость, адаптируйте пример через публичный API и повторите рабочий сценарий.

## Делегирование

- Изолированные и хорошо ограниченные подзадачи можно отдавать менее затратному агенту, включая Sol с низким уровнем рассуждения, только когда результат легко проверить и делегирование экономит время.
- Не делегируйте связанную архитектурную работу, если постановка, проверка и исправление результата займут дольше самостоятельного выполнения.
- Делегирование не является обязательным этапом и не запускается автоматически.

## Коммиты

- Изменение приложения и его документации — один коммит. Одна задача плана — один коммит, кроме явно оговорённых в самой задаче.
- Обновление версии библиотеки — отдельный коммит на приложение: `Обновить <app> до common2 X / react2 Y`, со ссылкой на `doc/changes/`.
- Сообщение на русском в повелительном наклонении; первая строка до 72 символов; далее пустая строка и суть изменения.
- Генерируемые файлы (`doc/STATUS.md`, содержимое между маркерами `status:*`) не правятся вручную: запустите `npm run status` и закоммитьте результат.
- Ветка `main` принимает только состояние с прошедшим `npm run check:all`. Проверка, пропущенная из-за отсутствия Docker или Python, отмечается как пропущенная, а не как пройденная.
