# Booking · запись и расписание

<!-- status:versions -->
Текущие зависимости: **common2 2.21.1 / react2 3.5.1**.
<!-- /status:versions -->

Самостоятельный пример бронирования на `wenay-common2 2.21.1` и `wenay-react2 3.5.1`. Authority принимает все изменения вместимости, временные удержания, подтверждения и переносы. Serving nodes обслуживают ролевые проекции и библиотечные подключения. Отдельной системы транспорта, Zod или самописного планировщика таймеров нет.

## Запуск

Из `apps/booking`:

```text
npm ci
npm run typecheck
npm test
npm run build
npm start
```

Backend по умолчанию `http://127.0.0.1:3814`, архив `booking-data`. Окружение: `SERVICE_PORT`, `SERVICE_HOST`, `SERVICE_DATA_DIR`, независимые стабильные `SERVICE_TOKEN_SECRET` и `SERVICE_NODE_TOKEN`. `BOOKING_HOLD_MS` задаёт TTL удержания (по умолчанию 300000, максимум 900000); малые значения предназначены для автоматической проверки. `.env` автоматически не загружается. После build сервер открывает календарь, брони, настройки и помощника; Vite dev проксирует API к порту 3814.

| Аккаунт | Пароль | Роль |
| --- | --- | --- |
| owner | owner-pass | Все настройки и брони Northstar Studio |
| staff | staff-pass | Исполнитель: свои ресурсы и услуги; календарь и брони организации |
| customer | customer-pass | Только свои брони, ожидание и напоминания |
| customer2 | customer2-pass | Второй независимый клиент для проверки последнего места |
| outsider | outsider-pass | Владелец Harbor Labs, без доступа к Northstar |

Демонстрационные аккаунты — явная часть стенда, не готовая внешняя регистрация. Northstar: `studio`, Europe/Berlin, capacity 2, понедельник–пятница 09:00–18:00. Услуга `consultation`: 45 минут встречи + 15 минут после, максимум один участник на бронь. Один ресурс может обслуживать несколько услуг, но их брони используют общую вместимость.

## Время и вместимость

Расписание задаётся локальными окнами ресурса, рабочие интервалы и брони хранятся в UTC milliseconds. Окна не пересекаются и не переходят через полночь; ночную работу разделяют на два окна разных дат. Исключение на конкретную дату заменяет всё недельное расписание этой даты; пустой список означает выходной. Частота стартов — 15 локальных минут от начала окна. Длительность встречи и буферы — фактически прошедшие минуты.

Для IANA-зон используется `@js-temporal/polyfill 0.5.1`: публичный [Temporal ZonedDateTime](https://tc39.es/proposal-temporal/docs/zoneddatetime.html) и явные варианты разрешения [DST ambiguity](https://tc39.es/proposal-temporal/docs/timezone.html). Несуществующий местный старт пропускается. Повторившийся осенний старт возвращает два разных UTC instant с отдельным `offset`; UI должен отображать смещение. Если сама граница рабочего окна попала в разрыв, окно сужается к существующим моментам: начало после разрыва, конец до него. При повторении границы охватываются обе её ветки. Никакое несуществующее время не превращается незаметно в предложенный клиенту слот.

Занятый интервал — `[start − before, end + after)`. Совпадающие конец и начало не пересекаются. При проверке вместимости sweep суммирует участников одновременно пересекающихся броней, а не всех броней, которые хоть частично касаются запрошенного интервала. Учитываются подтверждённые брони и удержания, чей TTL ещё не истёк. Истёкшее удержание перестаёт занимать место сразу при новой проверке, даже до фоновой записи статуса `expired`.

Доступность ограничена 1–14 днями, горизонтом 180 дней и 1000 слотами за ответ. `truncated:true` предлагает сузить диапазон. Доступность является снимком, а не разрешением записаться: создание удержания повторяет все проверки внутри authority-команды. Изменение расписания не сдвигает ранее обещанные UTC-интервалы; новые записи и переносы используют текущую конфигурацию. Снижение вместимости ниже существующей одновременной загрузки запрещено.

## Контракт UI и интеграций

`BookingDefinition` выводится из `createBookingRuntime` в `backend/runtime.ts`, `BookingWorkspace` — из `bookingWorkspace` в `domain.ts`. Полные типы сущностей находятся в `model.ts`; типы не дублируются отдельными схемами.

`workspace`: `{account, organizations, people, resources, services, bookings, waitlist, notices, audit}`. Клиент видит только собственные брони/заявки/напоминания, участников команды и себя, без других клиентов или аудита. Команда видит календарь своей организации. Клиентам не выдаются аккаунтные секреты или сохранённые ключи намерений.

Ресурс `calendar` расположен на authority:

```ts
calendar.control.read({orgId, serviceId, from: '2026-10-25', days: 1, partySize: 1})
// {serviceId, resourceId, zone, generatedAt, slots, truncated}
// slot: {start, end, occupiedFrom, occupiedTo, local, offset, available}
```

Каждое чтение заново проверяет организацию. Здесь нет приватных данных соседних броней. `generatedAt` нужен, чтобы UI не выдавал старый снимок за текущую доступность.

| Команда | Вход |
| --- | --- |
| resourceSave | `{orgId,id,revision,name,staff,zone,capacity,weekly:[{day,start,end}],exceptions:[{date,windows:[{start,end}]}]}` |
| serviceSave | `{orgId,id,revision,resourceId,name,description,duration,before,after,capacity,depositUnits,active}` |
| bookingHold | `{orgId,key,serviceId,start,partySize,customer,note,reminder}`; customer пустой означает текущего клиента, другой аккаунт выбирает только команда |
| bookingConfirm / bookingCancel | `{orgId,id,revision,key}` |
| bookingMove | `{orgId,id,revision,key,start}` |
| reminderSet | `{orgId,id,revision,key,enabled}` |
| waitJoin | `{orgId,key,serviceId,start,partySize}` |
| waitCancel | `{orgId,id,key}` |
| depositSimulate | `{orgId,id,eventId,outcome:'paid'\|'failed'}` — только локальный тест |

Для нового ресурса/услуги `id:''`, `revision:0`. Все часы — `HH:mm`, дата — `YYYY-MM-DD`, день недели ISO 1–7. Настройку чужого исполнителя меняет только владелец. Обычный результат команды — `{id,revision,status,fresh}`.

`key` — долговечный ключ прикладного намерения, отдельный от command requestId библиотеки. После потерянного ответа повторяют то же намерение; при новом действии создают новый key. Другое содержание с прежним key отклоняется. При семантическом повторе с новым command requestId `fresh:false`; возвращается первоначальная квитанция, а текущее состояние нужно брать из workspace. Повтор того же transport requestId воспроизводит исходную квитанцию библиотеки целиком. Истёкшее удержание повтором старого key не оживляется.

## Удержание, перенос, ожидание

Hold резервирует вместимость на пять минут или до начала слота, если оно наступает раньше. Confirm проверяет TTL, актуальную revision, владельца и тестовый депозит; ни внешний вызов, ни async-работа не находятся между проверкой и изменением состояния. Cancel освобождает место. Move работает только для будущей подтверждённой брони: сначала полностью проверяет новый слот с исключением своей старой записи, затем обновляет исходную бронь. При конфликте исходная бронь остаётся без изменений.

Лист ожидания относится к точному времени, услуге и числу участников. `createReconciler` просматривает сохранённые заявки в порядке `createdAt,id`, предлагает доступное время первой подходящей заявке и создаёт для неё обычный hold. Слишком большая заявка не блокирует меньшую подходящую. Предложение не дублируется после рестарта: offerId детерминированно связан с заявкой, статус сохраняется. Клиент подтверждает предложенную бронь обычной командой. Истёкшее или отклонённое предложение завершает эту заявку; следующий участник получает свою возможность. Прямые новые записи и фоновое предложение конкурируют на той же authority-проверке вместимости; отдельной гарантии приоритета очереди над прямой записью нет.

## Локальные напоминания и тестовый депозит

`createReconciler` с `ctx.retry` обслуживает TTL и сохранённые сроки напоминаний. Подтверждение создаёт локальное напоминание за час до начала (либо сразу, если осталось меньше). Оно появляется в `notices` со статусом `delivered`; email, SMS, push и сторонние аккаунты не вызываются. Настройка клиента отключает новые напоминания, перенос/отмена отменяют старую pending-запись. Перед доставкой повторно проверяются revision и подтверждённый статус. У каждого напоминания стабильный ID, поэтому восстановление не создаёт вторую доставку той же версии.

Услуга может требовать `depositUnits` тестовых единиц. `depositSimulate` явно моделирует событие, не является webhook настоящего платёжного провайдера и не имеет денежных полномочий. Успешный тестовый депозит сам по себе не подтверждает бронь. Событие с тем же `eventId` дедуплицируется; изменение outcome с тем же ID запрещено. Оплата после TTL/отмены помечается `refundDue` и не возвращает вместимость. Отмена уже оплаченной брони также требует условного возврата. Исполнение реального возврата/эквайринг отсутствуют.

## Проверки и границы

`npm test` состоит из доменного теста через настоящий service leader, локальных проверок помощника и сетевого теста с authority + двумя serving nodes. Домен: весенний gap, осенний fold, 30-минутный DST Lord Howe, исключения, буферы, ограничение диапазона, роли, утечка чужих броней, гонка последнего места, TTL, перенос с конфликтом, предложение ожидания, напоминания, поздний тестовый депозит. Сеть: реальные два клиента, отключение обслуживающего узла, стабильный store, автоматическое истечение hold, перезапуск authority и восстановление брони/ключа намерения. Docker для этих проверок не нужен.

Границы стенда: до 50 ресурсов, 100 услуг, 2000 броней, 500 заявок ожидания, 4000 намерений и последних 2000 записей аудита. Нет очистки семантических ключей, календарной синхронизации iCal/Google, внешней регистрации клиентов, массовых рассылок или подключённой языковой модели. Single authority остаётся транзакционным владельцем. Несколько serving nodes — проверяемое масштабирование чтений и соединений, а не несколько независимых авторов одной вместимости.

## Разбор пожеланий без автоматической записи

Ресурс `assistant` использует публичный `createAiRunHost`: состояние задания, отмену, replay и checkpoint. По умолчанию `PreferenceProvider` — явно подписанный тестовый разборщик текста, без LLM и платных запросов. Он понимает имя услуги, ISO-дату/сегодня/завтра/послезавтра, время HH:mm и число участников. Относительная дата вычисляется в зоне выбранного ресурса. Неоднозначный выбор услуги требует уточнения.

`assistant.control.context(orgId)` возвращает текущий `catalogKey` и доступные услуги с ревизиями/зоной. `assistant.ai.createRun({requestId,kind:'preferences',resourceIds:[orgId],input:{orgId,prompt,catalogKey}})` предлагает услугу, дату и partySize. Исполнитель получает только актуальный каталог разрешённых услуг, без чужих броней и заметок. Результат читается отдельно через `assistant.control.result(runId)`: повторная проверка членства и версий, свежая availability, до восьми вариантов, источники и `requiresConfirmation:true`. Уже занятый другим клиентом вариант исчезает даже из ранее завершённого предложения.

Интерфейс применяет предложение к выбору времени. Создание hold требует отдельного действия пользователя и повторно проходит обычную атомарную проверку. Помощник не имеет команд изменения бронирования. Текст пожеланий и возвращаемые исполнителем значения рассматриваются как данные: неизвестная услуга, некорректная дата или вместимость отклоняются.

Одновременно выполняются до двух заданий, по одному на аккаунт; сохранено до 100 запусков, тайм-аут по умолчанию десять секунд. Отмена, изменение каталога и отзыв членства прерывают исполнителя; поздний ответ не меняет итог. Ошибки провайдера очищаются. Частный результат хранится отдельно от replay статусов и переживает рестарт; незавершённое задание после рестарта не повторяет провайдера автоматически. Прочитанные ранее клиентом сведения нельзя стереть из его памяти серверной командой.

`npm run test:assistant` проверяет отсутствие автоматической записи, недоступность чужой организации, версии/зону, изменение доступности после предложения, отмену/тайм-аут/поздний ответ, отзыв роли, очистку ошибок и восстановление частного результата. Качество настоящей модели этим тестом не оценивается.

## Контейнер и обновление

Dockerfile использует закреплённый digest Node 24 Alpine, пользователя node и каталог `/data`. Перед сборкой образа нужно выполнить `npm run build`; наружу открыт порт 8080. `.dockerignore` разрешает только package/lock, backend/shared и готовый public: данные, секреты и тестовые файлы не входят в образ. Передайте отдельный volume для `/data`, стабильные секреты service и `APP_RELEASE` для проверки версии через `/health`.

```text
npm run build
docker build --memory 768m --build-arg APP_RELEASE=first -t wenay-examples.local/booking:first .
docker build --memory 768m --build-arg APP_RELEASE=second -t wenay-examples.local/booking:second .
```

Из исходного репозитория, в `apps/hosting`: `node --import tsx backend/booking-live-check.ts`. Приёмка использует настоящий hosting authority/agent, неизменный адрес gateway и один writer с лимитом 256 МиБ. Удержание, созданное в first, остаётся после second; повтор прикладного key не создаёт вторую бронь, конфликт вместимости отклоняется. Во second удержание подтверждается, rollback first сохраняет подтверждение и напоминание; затем бронь отменяется. Те же клиент и ресурс calendar переподключаются после смены контейнера. Это совместимый откат данных одной схемы, не доказательство произвольной миграции схем.

Проверено 10 сентября 2026: first/second/rollback — PASS, память контейнера в контрольных точках 59.45/60.17/59.12 МиБ из 256 МиБ. Образы собирались последовательно, ограничение сборки 768 МиБ. Тест удалил собственные контейнеры, volume и временный архив; пользовательские данные не используются. Сам hosting-тест зависит от соседнего приложения и намеренно не входит в самостоятельную scaffold-копию booking.
