# OCI-исполнитель: Node.js и другие языки

Один контракт для любого HTTP-приложения: образ с digest, порт, путь проверки готовности, CPU и RAM. В `examples/node` и `examples/python` находятся два приложения с одинаковыми `/` и `/healthz`, разными языками и непривилегированными пользователями контейнера. Node.js используется и для управляющего сервиса/агента; он не требуется внутри Python или другого пользовательского образа.

## Среда

Нужен работающий Linux Docker Engine. На Windows агент обращается к локальному named pipe Docker Desktop, на Linux — к `/var/run/docker.sock`. `DOCKER_SOCKET` задаёт конкретный путь. Никакой открытый незащищённый Docker TCP endpoint не требуется.

9 сентября 2026 пользователь восстановил запуск Docker Desktop 4.90.0. Проверен настоящий Linux Engine 29.7.2 на WSL 2.7.13. Ошибка `sailor-ingest.sock` больше не блокирует контейнерный сценарий.

## Воспроизводимый контейнерный тест

После успешного `docker info`:

```sh
npm run prepare:examples
npm run test:docker
```

Подготовка последовательно собирает Node/Python, получает локальные repo digests и сохраняет их в игнорируемом `data/example-images.json`. Registry и дополнительные контейнеры не запускаются. Нужен image store, возвращающий manifest digest после локальной сборки; проверено с containerd в Docker Desktop. Если digest отсутствует, скрипт явно завершается ошибкой: можно отдельно подготовить/загрузить образы из своего registry и передать `HOSTING_NODE_IMAGE`/`HOSTING_PYTHON_IMAGE` непосредственно в `test:docker`. Image config ID не подставляется вместо manifest digest.

Базовые Dockerfile используют каналы Node 24 и Python 3.13, поэтому новая сборка может дать новый digest. Конкретный релиз всегда закреплён digest. Имена `wenay-examples.local/*` используются только для установленных локально образов, публикация в интернет не выполняется. `DOCKER_BIN` позволяет указать CLI явно; каталог CLI добавляется только в PATH дочернего процесса для поиска credential helper в старых Windows-сессиях.

Тест использует настоящий Docker и настоящий common2: deploy Node → заведомо неготовая версия → deploy Python → rollback Node. Проверяет HTTP-ответы и сохранение прежнего рабочего адреса после failed readiness. Перезапускает агент между версиями; удаляет только контейнеры своего уникального владельца и своих operation IDs. Можно передать уже подготовленные образы через `HOSTING_NODE_IMAGE` и `HOSTING_PYTHON_IMAGE`. При отсутствии движка/образов тест завершается ошибкой, а не пропускается как успешный.

Живой сценарий успешно пройден 9 сентября 2026. После завершения Docker не содержал контейнеров теста. `npm test` отдельно проверяет REST/RPC и agent/provider с HTTP fixture, включая потерянный ответ create и восстановление существующего кандидата.

## Бюджет памяти тестов

На текущем компьютере пользователь ограничил работу максимум 3 ГиБ, желательный расход 1–2 ГиБ. Сборки и проверки запускать последовательно; не поднимать VM/Kubernetes в рамках этого прогона. Каждый тестовый кандидат ограничен 64 МиБ и 0.25 CPU. В сценарии 0.4.0 перед следующим деплоем проверяется очистка предыдущего кандидата: одновременно нужны активный и новый контейнер (128 МиБ суммарного лимита). Это лимиты кандидатов, а не всего Docker: WSL, движок, сборщик и процесс теста расходуют дополнительную память. Непрерывный замер пика не проводился. Глобальные настройки WSL/Docker не менялись.

Живой тест использует readiness deadline 3 секунды; обычный агент сохраняет 30 секунд по умолчанию. Образы и build cache остаются на диске для следующих лёгких прогонов, тестовые контейнеры удаляются.

## Запуск исполнителя

Сначала запустите API по README и создайте проект, окружение вида `docker` и релиз. Образ с этим digest должен быть установлен на Docker-хосте: подготовьте его описанным выше способом либо через доверенный registry. Автоматический pull приватного registry и передача секретов ещё не реализованы.

Задайте `HOSTING_URL`, `HOSTING_AGENT_ACCOUNT`, `HOSTING_AGENT_PASSWORD` и при необходимости `HOSTING_AGENT_DATA`, `DOCKER_SOCKET`; запустите `npm run start:agent`. В браузере доступны создание окружения/версии, deploy, история, отмена queued-заявки и rollback к ранее успешной версии.

Агент принимает только назначенные ему `docker`-окружения и не исполняет VM/Kubernetes как Docker. Существующие экземпляры LXD типа `container` остаются отдельным видом ресурсов. Имя контейнера детерминировано ID операции, образ и метки владельца проверяются перед повтором и удалением. Порт публикуется на loopback; выставлены CPU/RAM/PID limits, drop capabilities и no-new-privileges.

При отсутствии образа или неудачной readiness кандидат удаляется после проверки принадлежности, операция завершается ошибкой. При неопределённом результате IO агент оставляет операцию running и сверяет ресурс повторно. Ошибка одного окружения не должна блокировать обработку других. API и агент этого среза предназначены для одного компьютера.

## Постоянный адрес и удаление старых контейнеров

Агент открывает отдельный loopback listener и сохраняет его адрес в `environment.route` через `registerRoute`. Адрес неизменяем, в том числе после рестарта сервиса/агента. Поле `endpoint` остаётся внутренним адресом кандидата; панель открывает `route`. До появления подтверждённого активного контейнера шлюз отвечает 503. При занятом сохранённом порте агент ждёт устранения конфликта, не меняя ссылку и не начиная новый деплой.

`finishOperation` фиксирует `activeOperation`; агент сверяет Docker image, метки владельца/окружения/операции и фактический опубликованный порт, затем переключает шлюз. После переключения новые запросы идут в новый контейнер, уже принятые остаются у старого до завершения (максимум 30 секунд). Затем агент удаляет устаревшие контейнеры и подтверждает `cleaned` через common2. Ни активная, ни pending-операция не очищается. Ошибка удаления оставляет запись для повторной попытки; история релизов сохраняется. Возврат к версии создаёт новый контейнер, образ должен оставаться установленным локально.

Эта политика предназначена для stateless HTTP-приложений: writable layer удаляемого контейнера не сохраняется. Данные приложения должны жить во внешнем хранилище; подключение постоянных томов, резервное копирование и откат данных в этом срезе не реализованы. Образы и тома автоматически не удаляются.

Панель показывает постоянную ссылку и отметку удаления контейнера в истории. Успешное подтверждение деплоя и обновление listener выполняются последовательно, а не общей транзакцией: сразу после success проекция маршрута может ещё коротко обслуживать предыдущую версию. После рестарта восстанавливается ранее подтверждённый активный контейнер, без его повторного создания. Для старого окружения без `activeOperation` нужен первый новый успешный деплой, чтобы включить маршрут и очистку.

Нативный HTTP-шлюз работает в процессе агента, без дополнительного контейнера. Он передаёт path/query и тело потоками, удаляет hop-by-hop headers, не переписывает абсолютные redirect URL и cookies. WebSocket upgrade поддержан: `test:gateway-ws` проверяет двусторонние сообщения, bounded drain и reconnect на новый upstream при постоянном URL с настоящим локальным Socket.IO fixture. Это не принудительная WebSocket-проверка каждого product Docker deployment; её границы описаны в [live-gate](LIVE-GATE.md). CONNECT, TLS и HTTP-запросы дольше 30 секунд не поддерживаются. Лимит listener — 64 соединения. При остановке агента приложение по постоянной ссылке временно недоступно.

## Что ещё не готово для боевой эксплуатации

- Пока это локальный HTTP-маршрут: отдельные порты дают отдельные web origins, но cookies всё ещё привязаны к одному имени хоста. Маршрут не требует авторизации панели. Для недоверенных арендаторов/публичного доступа нужны отдельные домены, TLS и полноценная изоляция; панель не должна разделять домен приложений.
- Локальный lock запрещает второй агент в том же каталоге, но не является распределённым fencing. Запускать только один исполнитель данного account на Docker-хосте; при аварии lock удалять вручную после проверки завершения прежнего процесса.
- Не реализованы автоматические pull/registry credentials, периодический мониторинг после деплоя, квоты проекта, масштабирование реплик, межмашинный адрес приложения и удалённый Docker endpoint.
- Docker не заменяет VM/LXD и не даёт Kubernetes-кластер. Эти этапы остаются в [плане](../../doc/HOSTING-PLAN.md).
