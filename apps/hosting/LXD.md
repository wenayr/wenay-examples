# Машины LXD: первый исполняемый срез

Управляющий сервис, браузерная панель и LXD-агент связаны публичным `wenay-common2`. Панель использует `wenay-react2`. Создание машины и изменение питания — отдельная очередь, независимая от версий OCI-приложений. Команды сервиса только фиксируют намерение; HTTP-запросы к LXD выполняет агент.

## Подготовка Linux-хоста

Нужен уже установленный и настроенный LXD с локальным Unix-сокетом, отдельным проектом, пулом хранения и управляемой bridge-сетью. Агент проверяет доверенный доступ, объявленную поддержку типа машины, наличие пула и тип сети. Это ещё не полный аудит свободных ресурсов, KVM и квот. Для VM требуется хост с аппаратной виртуализацией и рабочим KVM; Docker Desktop для этого провайдера не нужен.

Образ заранее импортируется в LXD. Выберите cloud-init-совместимый образ нужного типа и передайте полный 64-символьный fingerprint. Ссылки на меняющиеся aliases не принимаются. Агент сверяет локальный fingerprint и тип образа; автоматического скачивания нет.

Запуск из `apps/hosting` на Linux:

```sh
export HOSTING_URL='https://your-control-host.example'
export HOSTING_AGENT_ACCOUNT='lxd-agent'
# HOSTING_AGENT_PASSWORD передайте через защищённое окружение процесса.
export HOSTING_AGENT_DATA='/var/lib/hosting/lxd-agent'
export LXD_SOCKET='/var/snap/lxd/common/lxd/unix.socket'
export LXD_PROJECT='hosting'
export LXD_POOL='hosting-pool'
export LXD_NETWORK='hosting-bridge'
npm run start:lxd-agent
```

`HOSTING_URL` — адрес управляющего сервиса, опубликованного через ваш HTTPS ingress/reverse proxy. Учётная запись `lxd-agent` с ролью `agent` и доступом к нужным проектам должна быть включена в начальную конфигурацию сервиса. Для другого способа установки LXD укажите фактический путь сокета.

Один аккаунт агента закрепляется за одним хостом и постоянным каталогом данных. Локальный `agent.lock` предотвращает запуск второй копии в том же каталоге, но не является распределённой блокировкой. Не запускайте одинаковый аккаунт из разных каталогов или на разных хостах. Агент имеет полномочия своего Unix-сокета; прикладные проекты пока не создают отдельных LXD tenants и сетевой изоляции.

## Работа пользователя

В панели выберите проект → «Машины» → «Создать машину». Укажите имя, аккаунт LXD-исполнителя, тип (Linux-контейнер или VM), fingerprint, CPU, RAM, диск и публичный ключ Ed25519. Создание ставит в очередь включение. Публичный ключ передаётся cloud-init для пользователя `hosting` с sudo; приватный ключ остаётся у владельца. Произвольные команды cloud-init, секреты, привилегированные контейнеры и подключение директорий хоста из панели не поддерживаются.

После завершения появляется подтверждённое состояние питания. «Включена» означает только состояние гипервизора. `preparation: unverified` сохраняется до появления отдельной проверки cloud-init, runtime и приложения. SSH-доступ также зависит от образа и маршрутизации сети; UI пока не выдаёт подтверждённый адрес подключения.

Включение/выключение учитывают текущую ревизию и запрещены при незавершённой операции. Выключение штатное, без принудительного отключения питания. Ошибка операции хранится в истории. При неоднозначном сетевом результате агент оставляет операцию выполняющейся и повторно сверяет ту же машину. Отсутствующий образ/пул/сеть требует исправления конфигурации хоста; заявка может оставаться выполняющейся до устранения причины.

## Фасады и гарантии

| Команда / представление | Доступ |
| --- | --- |
| `createMachine` | admin, owner своего проекта |
| `setMachinePower` | admin, owner, operator своего проекта |
| `claimMachineOperation`, `finishMachineOperation` | только назначенный agent своего проекта |
| `machineDashboard` | admin, owner, operator, observer в пределах проектов |
| `machineAssignments` | только машины и незавершённые операции назначенного agent |

Имя LXD детерминировано аккаунтом агента, проектом и ID машины. При повторе проверяются метки владельца, fingerprint образа, спецификация, явные устройства и отсутствие наследуемых profiles. После потери ответа повторное создание не получает нового имени. Подтверждённо существовавшая, но впоследствии исчезнувшая машина автоматически не пересоздаётся: требуется отдельное восстановление, чтобы не подменить её пустой системой. Запрос остановки отсутствующей машины также ничего не создаёт.

После HTTP 202 агент ждёт результат `/operations/{id}/wait`, проверяет внутренний status_code и заново читает состояние машины. Provider operation ID пока живёт только в текущем вызове: восстановление после потери процесса опирается на имя, спецификацию и наблюдаемое состояние. Постоянный журнал provider operations и fencing нужны до распределённого исполнения.

Формат архива сервиса обновлён с 1 до 2 через публичный `migrate`. Переносятся прежние данные, добавляются пустые коллекции машин и их операций. API/агентов нужно обновить совместно; откат к версии сервиса 1 после записи нового формата не поддерживается.

## Проверки и следующие этапы

`npm test` включает LXD HTTP fixture поверх настоящего сокета/Windows named pipe и настоящий common2 RPC. Проверены потеря ответа создания, отсутствие повторного запуска, отказ async-операции при HTTP 200, чужая машина, неподдерживаемая VM, роли/чужие проекты, повтор command receipt, ревизии, перезапуск агента, перенос настоящего архива v1.

**Реальный LXD-контейнер и VM пока не запускались.** Docker восстановлен и его отдельный Node/Python-сценарий прошёл, но Linux-хост LXD пока не подготовлен. Этот набор тестов не подтверждает работу KVM, дисковых квот, cloud-init или SSH. Текущий бюджет пользователя — максимум 3 ГиБ RAM; тяжёлые VM и кластеры не запускать. После подготовки подходящей среды: две реальные изолированные машины, проверка ОС, установка runtime, снимки/восстановление; затем связь машин с деплоем приложений и k3s. Отмена очереди машин, удаление машин, каталог образов/сетей/хранилищ, квоты и распределённое исполнение ещё не реализованы.

Контракт адаптера сверялся с [официальной схемой REST API LXD](https://raw.githubusercontent.com/canonical/lxd/main/doc/rest-api.yaml). Модель подготовки учитывает [стадии cloud-init](https://docs.cloud-init.io/en/latest/explanation/boot.html): включение VM не подтверждает завершение стадии Final.
