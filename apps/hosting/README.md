Новый результат: [размещение своих приложений и общий отчёт S3–S8](../../doc/changes/complete-strategy.md). Добавлены WebSocket gateway и постоянные тома с одним writer. В форме версии задаётся формат данных (`organizer-2`/`pizzeria-5`); пустое значение оставляет приложение без постоянного тома. Обновление сохраняемого приложения имеет простой, при плохой readiness восстанавливает прежнюю совместимую версию. Изменение формата требует отдельной миграции и блокируется обычным deploy.

Для воспроизведения сначала в `apps/pizzeria` выполнить `npm ci`, `npm run build`, `npm run build:organizer`. В этом каталоге: `npm ci`, `npm run prepare:products`, затем `npm run test:stateful`. Для пиццерии в PowerShell: `$env:HOSTING_APP_KIND='pizzeria'`, затем тот же тест. Уберите переменную перед повторным тестом органайзера. Стенд последовательно проверяет deploy/update/rollback, restart, плохую readiness и quiesced backup/restore в отдельное окружение; приложение 256 МиБ, helper 64 МиБ. Очищаются только собственные объекты теста. Backup пока воспроизводимый сценарий, не GUI-сервис расписаний.

`npm run test:gateway-ws` проверяет Socket.IO, а `npm run test:public-address` (старый alias `repro:public-address`) теперь положительно проверяет оба приложения через RPC/Store/SC1. H3 закрыт, размещённый UI проверен. `test:stateful` сохраняет отдельные REST backup/readiness-проверки. [Принятие 2.20.0 и A1/M1](../../doc/changes/common2-2.20.0.md). Никакие библиотеки локально не подменяются.

Самостоятельный пример на опубликованных `wenay-common2` и `wenay-react2`. [Полный план](../../doc/HOSTING-PLAN.md): LXD-контейнеры и VM, подготовка окружений, версионные деплои и Kubernetes. Добавлены браузерная панель и [OCI-исполнитель для разных языков](DOCKER.md). На настоящем Docker через common2 ранее проверены Node → Python → откат Node, перезапуск агента и сохранение работающего приложения после неудачной readiness. При [принятии 2.19.0](../../doc/changes/common2-2.19.0.md) повторены typecheck, fixture/RPC-тесты и сборка; настоящий Docker повторно не запускался. Каждый тестовый контейнер ограничен 64 МиБ; общий бюджет текущей машины — максимум 3 ГиБ.

## Уже работает

- Постоянный адрес Docker-окружения, восстановление маршрута после перезапуска и автоматическое удаление старых кандидатов после завершения запросов. История релизов сохраняется для rollback. [Результат 0.4.0](../../doc/changes/hosting-0.4.0.md).

- [Машины LXD](LXD.md): отдельные ролевые команды, очередь создания и питания, агент, панель и миграция архива v1 → v2. LXD проверен через HTTP fixture; реальные VM пока не запускались.

- Пять ролей, изоляция проектов, окружения с конкретным назначенным агентом.
- Неизменяемые релизы с OCI reference, закреплённым SHA-256 digest; уникальная версия внутри проекта.
- Deploy и rollback, ревизия окружения и одна незавершённая операция. Rollback принимает только ранее успешно подтверждённый релиз этого окружения.
- Очередь, получение операции назначенным агентом, отчёт о результате с проверкой ревизии и digest. Отмена разрешена только до начала выполнения.
- Раздельные проекции человека и агента, живые обновления, REST/OpenAPI/RPC, сохранение состояния и receipts через библиотеку.

Заявка без агента остаётся `queued`. Только агент может подтвердить результат. Проверка digest — проверка согласованности отчёта доверенного агента, а не независимое доказательство работающего приложения. Docker-агент проверяет HTTP readiness и сверяет контейнер при повторе. Распределённые lease/fencing и provider operation ID для LXD/Kubernetes входят в следующие этапы.

## Q11-P-Origin: объявляемый HTTPS origin

Native owner/admin resource `session.resources.open('publicOrigin')` предоставляет
`current().remote.control.set({requestId, environment, revision, publicOrigin})`
настраивает Docker-окружение только до первой deployment operation.
Значение — canonical HTTPS origin вроде `https://app.example.test`, без credentials,
path/trailing slash, query, fragment или wildcard; пустая строка снимает настройку.
Origin уникален среди окружений. Revision и повтор обслуживают существующие native commands/receipts.
Resource проверяет текущую role/project до команды и после receipt, включая environment самого receipt.
Закрытый/отменённый resource и старая runtime generation не возвращают результат.
Внутренняя `publicOriginSet` доступна только system account; прямой owner/admin HTTP alias отсутствует.
Operator/observer/agent и owner чужого проекта настройку не выполняют.

В панели owner/admin раздел «Публичный адрес приложения» предлагает только Docker окружения
без предыдущих deployment operations. Значение и revision берутся из dashboard view.
Кнопки сохраняют адрес или снимают настройку; при ошибке повтор использует исходные requestId,
revision и origin. «Отменить повтор и редактировать» начинает новое изменение с текущей revision.
Переход между проектами/окружениями, потеря роли и выход закрывают принадлежащий форме resource.
UI не вызывает внутреннюю system command. Подсказка явно отмечает, что DNS/TLS/proxy не настроены.

Resource input: `{requestId: string, environment: string, revision: number, publicOrigin: string}`.
RequestId непустой, до 120 символов; schema использует native input validation, revision должна
совпасть с текущей revision окружения. Origin — canonical HTTPS без credentials/path/query/fragment,
wildcard или запятой; пустое значение снимает настройку. Output:
`{environment: string, revision: number, publicOrigin: string}`. Новый вызов увеличивает revision,
повтор native receipt возвращает исходный результат после проверки текущего доступа.
Смена адреса после первой deployment operation отклоняется явно; automatic deployment/TLS здесь нет.

Optional `environment.publicOrigin` сохраняется отдельно от internal loopback route.
Agent/Docker передают ровно его в `SERVICE_PUBLIC_URL` и `SERVICE_CORS_ORIGINS`,
включая stateless workload; внутренний gateway/port bind остаётся loopback.
Старые данные без поля сохраняют прежнее поведение. Уже deployed окружение отклоняет
изменение домена понятной API ошибкой: reconfiguration/redeploy/migration этого среза не реализованы.
Нельзя считать настройку origin установкой proxy/TLS/DNS или готовым внешним deployment.
Owner/admin UI использует публичный native resource; descriptor публикует его доступность.
Internal system command не является owner/admin HTTP API. Targeted Hosting tests/build и перечисленные
browser сценарии прошли; reconnect UX и внешняя DNS/TLS/deployment приёмка остаются отдельными.
[Текущий scope, evidence и ограничения](../../doc/changes/hosting-public-origin-20260926.md).

## Установка и проверки

Node.js 22.12+:

```sh
cd apps/hosting
npm ci
npm run typecheck
npm test
npm run build
```

Живые проверки размещения продуктов запускаются отдельно и требуют собранных образов `wenay-examples.local/<продукт>:first` и `:second`: `npm run test:booking`, `test:crm`, `test:forms`, `test:monitoring`, `test:approvals`, `test:content`, а также `test:support`, `test:documents`, `test:metering` и `test:stateful` для пиццерии и органайзера. Каждая проходит установку, обновление и откат при постоянном адресе шлюза с лимитом контейнера 256 МиБ.

Тест запускает настоящий common2 HTTP/RPC host, семь независимых сетевых клиентов и повторно открывает долговечный архив. Проверяет авторизацию на сервере, чужие проекты, реактивные проекции, конкуренцию, неизменяемость релиза, отчёты успеха/ошибки, rollback и receipt после перезапуска. Наблюдения инфраструктурного агента в нём **имитируются**; VM и кластер не создаются. Временный архив удаляется после проверки.

## Запуск API

1. Скопируйте `accounts.example.json` в защищённый файл вне Git и замените все пароли уникальными секретами. Значения-заглушки сервер отвергает. `projects` ограничивает доступ аккаунта; agent должен быть назначен тому же проекту, что и окружение.
2. Задайте `HOSTING_ACCOUNTS_FILE` — путь к этому файлу, `SERVICE_TOKEN_SECRET` и `SERVICE_NODE_TOKEN` — разные случайные секреты длиной не меньше 32 символов. Сохраняйте ключи между запусками.
3. При необходимости задайте `SERVICE_PORT` (по умолчанию 3700), `SERVICE_DATA_DIR` (по умолчанию `data`), затем выполните `npm start`.
4. Откройте `/` — панель на react2, `/docs` или `/openapi.json` — описание API. `/api/client` — безопасный descriptor для `createServiceClient`. Пароли и хеши не входят в descriptor, проекции и архив приложения.

Состав аккаунтов, роли и доступные проекты инициализируются при первом создании архива. Изменение файла не мигрирует сохранённые роли/проекты: административное управление доступами — следующий срез. Пароли проверяются по текущему файлу. Это начальная серверная конфигурация, а не готовая регистрация клиентов хостинга.

## Порядок работы через фасады

Администратор вызывает `createProject`. Владелец создаёт окружение (`createEnvironment`) с типом `docker`, `container`, `virtual-machine` либо `kubernetes` и ID агента. Создание записи само по себе не создаёт машину. Владелец или оператор публикует релиз (`publishRelease`), затем отправляет `deploy`, передавая текущую `revision` окружения. В 0.2.0 исполняется только вид `docker`; остальные виды зарезервированы для следующих провайдеров.

Агент читает `views.assignments`, вызывает `claimOperation` с ревизией операции и, после реального действия провайдера в следующем этапе, `finishOperation`. Человек наблюдает `views.dashboard`; закрытая проекция не содержит аккаунтов или секретов. Все мутации вызываются с requestId: для повтора того же запроса сохраняют прежний ID, для нового действия создают новый. Конфликт ревизии требует перечитать окружение, а не бесконечно повторять старую команду.

При неудаче `active` остаётся прежним, `desired` сохраняет желаемую версию, операция получает `failed`. После начала выполнения пользовательская отмена запрещена: отмена ожидания не доказывает отмену инфраструктурного эффекта. Операции `running` после перезапуска остаются `running` до сверки и отчёта агента; автоматического reclaim пока нет.

## Границы и дальнейшая работа

Один управляющий writer, без горизонтального исполнения, квот, реального LXD/Kubernetes IO и размещения на физических хостах. Docker-провайдер и панель реализованы; эксплуатационные ограничения и статус настоящей проверки — в [DOCKER.md](DOCKER.md). Роли заданы начальной конфигурацией; аудит содержит инициатора и результат операции, но ещё не эксплуатационные временные отметки и политику хранения. На этом компьютере установлены Docker Desktop и WSL; рабочие серверы lanaFour не изменялись.

Следующий лёгкий срез: видимое состояние агента/маршрута, причины ожидания и лимиты числа одновременно обслуживаемых окружений. LXD provider реализован и проверен с HTTP fixture; полноценный Linux preflight, реестр хостов, проверка ОС и реальные VM ещё предстоят в подходящей среде. Для Kubernetes использовать официальный rollout и его наблюдаемое состояние, поверх них — фасады common2. [Результат настоящего Docker-сценария](../../doc/changes/hosting-docker-live.md).
Прежние абзацы о версиях и принятых пакетах: [история](../../doc/changes/hosting-history.md).
