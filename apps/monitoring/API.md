# Signal — устройство и контракт

Справочник к [README](README.md): операторские цели и правила HTTP-проверки, роли процессов с владением попыткой, путь от наблюдения к работе дежурного, сводка по фактам.

## Операторские цели и HTTP

`MONITOR_TARGETS_JSON` — массив до 100 целей, максимум 16 KiB:

```json
[{"id":"local","name":"Мой сервис","url":"http://127.0.0.1:4000/health","address":"127.0.0.1"}]
```

Пользователь выбирает `presetId`, не вводит произвольный URL. URL, адреса и тело проверяемого ответа не записываются в workspace/публичный статус. Для DNS-имени соединение направляется сразу на заданный IPv4/IPv6; имя сохраняется для Host/TLS. DNS повторно не разрешается. URL с credentials/fragment, несовпадающие literal IP и malformed targets отклоняются; редиректы не выполняются, TLS-проверка не отключается.

Ограниченный GET: timeout 100–10000 ms, заголовки до 8 KiB, тело до 16 KiB. Только 2xx считается успехом. Redirect, слишком большой ответ и timeout не дают ложного `up`. Секретные заголовки приложения не передаются.

При старте системная команда `configurePresets` согласует сохранённые названия с конфигурацией. Удалённая оператором цель приостанавливает связанные проверки, меняет revision и снимает старую аренду. Конфигурация должна совпадать у исполнителей; отсутствие цели у конкретного probe даёт `unknown`.

## Узлы, расписание и владение попыткой

Сервер включает один `probe-a`; `MONITOR_EMBEDDED_PROBE=0` отключает его. Второй процесс запускается через `npm run start:probe` с окружением `SERVICE_UPSTREAM=http://127.0.0.1:3816`, `PROBE_ACCOUNT=probe-b`, `PROBE_PASSWORD=probe-b-pass` и тем же `MONITOR_TARGETS_JSON`. `.env` автоматически не загружается.

Встроенный probe проходит обычный credential login и обращается к публичным assignment projection и corridor своей технической роли внутри authority. Отдельный probe использует сетевой `createServiceClient`; оба используют один цикл HTTP/аренды. Это позволяет встроенному процессу работать за внешним gateway, чей адрес недоступен из контейнера. Удалённым исполнителям по-прежнему нужны сетевой доступ к объявленным адресам roster и подходящая операторская маршрутизация; произвольные частные сети автоматически не соединяются.

Serving nodes запускаются через `npm run start:node`: `SERVICE_UPSTREAM`, уникальный `SERVICE_NODE_ID`, согласованные стабильные случайные `SERVICE_TOKEN_SECRET` и `SERVICE_NODE_TOKEN`. Секреты храните вне образа/исходников. Один authority владеет записью, serving nodes обслуживают представления, probe-процессы выполняют HTTP. Это разные роли масштабирования, не конкурирующие писатели одного архива.

`MONITOR_MIN_INTERVAL_MS` по умолчанию 15000; минимум 1000 предназначен для небольших локальных тестов. Интервал должен превышать timeout. Authority атомарно выдаёт попытку и аренду до `timeoutMs + 2000`. Предпочтительный probe начинает по расписанию; другой может забрать просроченную работу через 5 секунд после `nextAt`, когда активной аренды уже нет. Поздний отчёт старой попытки/revision/исполнителя или истёкшей аренды не принимается. Истёкшая попытка записывается как `unknown`, не как успех.

Один процесс выполняет максимум один HTTP-запрос одновременно. Цикл и повторы используют публичный `createReconciler`; команды, reconnect и смена обслуживающего узла — `createServiceClient`. Библиотечный durable host сохраняет расписание и номера попыток. После простоя обрабатывается актуальная работа, пропущенные интервалы не проигрываются лавиной.

## От наблюдения к работе дежурного

Владелец вызывает `monitorSave`: название, цель, preferred probe, публичность, пауза, интервал, timeout и пороги открытия/восстановления 1–10. Создание — `id: ''`, `revision: 0`; изменение требует текущую revision.

Порог ошибок открывает один инцидент, одну задачу с двумя пунктами и личные уведомления. Дежурный принимает инцидент через `incidentAcknowledge`, добавляет внутреннюю заметку. Порог успехов закрывает инцидент, но **не завершает человеческую задачу**: её пункты и завершение подтверждает сотрудник.

Задачи используют тот же прикладной `task-domain`, что пиццерия/CRM, через небольшой tenant-адаптер. Есть назначение, сроки, checklist и перенос карточек. `notificationSettings` задаёт личный тихий режим; `noticeRead` отмечает уведомление. Отправки email/Slack нет.

`views.workspace` проверяет организацию и роль. `views.taskBoards` доступен владельцу/дежурному, `views.assignments` — только probe. Публичный `views.status` содержит открытые сервисы и сокращённые инциденты без адресов, исполнителей и частных заметок. UI показывает время измерения, паузу и серые интервалы без данных: старое `up` не означает свежую доступность или 100% uptime.

## Сводка по фактам

SC1-ресурс `assistant` размещён на authority и использует `createAiRunHost`:

```ts
const run = await assistant.ai.createRun({
    kind: 'summary', requestId: crypto.randomUUID(), resourceIds: [id],
    input: {orgId, id, revision}
})
// После completed:
const result = await assistant.control.result(run.id)
```

Встроенный исполнитель — детерминированное демо без модели и платных запросов. Он собирает последние восемь наблюдений, сведения монитора и до трёх заметок текущего инцидента; без измерений прямо сообщает, что определить причину нельзя. `SummaryProvider` — заменяемый порт исполнителя, не утверждение о подключённом LLM.

AI replay содержит только статус/готовность. Текст и шаги лежат в частном журнале. Чтение требует того же владельца запуска, текущих прав и совпадения revision, последней попытки и версии текущего инцидента. Новое измерение, заметка, настройка или отзыв доступа закрывает старый текст. UI также убирает результат при смене контекста.

До двух активных запусков, один на монитор, 100 записей истории, timeout 10 секунд. Есть отмена; поздний результат не публикуется. Завершённый результат восстанавливается после рестарта, прерванный заканчивается ошибкой без автоматического повторного вызова. Прежние частные сводки остаются в дисковом журнале; автоматическая физическая очистка и отдельная политика резервных копий здесь не реализованы.
