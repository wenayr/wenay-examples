# Signal — мониторинг своих сервисов

<!-- status:versions -->
Текущие зависимости: **common2 3.1.1 / react2 5.0.0**.
<!-- /status:versions -->

Самостоятельный пример: HTTP-проверки разрешённых оператором адресов, инциденты, задачи дежурных, личные уведомления, публичная страница состояния и сводка по наблюдаемым фактам. Работает отдельно от остальных продуктов.

Автоматических команд перезапуска, развёртывания или отката **нет**: помощник показывает факты и шаги для проверки человеком, а ссылка на кабинет хостинга открывает его с обычными правами пользователя.

## Запуск

Требуется Node.js ≥ 22.12. Из этого каталога:

```text
npm ci
npm run build
npm start
```

Открыть http://127.0.0.1:3816. Данные — в `monitoring-data`; порт и каталог меняют `SERVICE_PORT` и `SERVICE_DATA_DIR`. Описание клиента — `/api/client`, библиотечный API — `/api/monitoring`, документация — `/docs` и `/openapi.json`.

`MONITOR_TARGETS_JSON` задаёт разрешённые цели (до 100, не больше 16 KiB); пользователь выбирает готовую цель, а не вводит произвольный URL. Сервер включает один встроенный исполнитель проверок, `MONITOR_EMBEDDED_PROBE=0` его отключает, второй запускается `npm run start:probe`. Обслуживающие узлы — `npm run start:node`. Подробности — в [справочнике](API.md); `.env` автоматически не загружается.

## Роли и демоданные

| Аккаунт | Доступ |
| --- | --- |
| `owner` | Northstar: настройки проверок, команда, инциденты, задачи, сводки |
| `oncall` | Northstar: инциденты и внутренние заметки, задачи, уведомления, сводки |
| `observer` | Northstar: только опубликованные проверки и сокращённая история |
| `outsider` | Владелец отдельной Harbor, без данных Northstar |
| `probe-a`, `probe-b` | Технические исполнители: назначения, получение попытки, отчёт |
| Без входа | Общий статус явно опубликованных проверок |

Пароль демонстрационного аккаунта — `<account>-pass`. Это локальная модель входа, не производственная идентификация; последнего владельца удалить нельзя, технические credentials настраивает оператор.

Сценарий: владелец создаёт проверку из разрешённой цели → исполнитель берёт попытку под аренду и делает ограниченный GET → после порога ошибок открывается один инцидент, одна задача с двумя пунктами и личные уведомления → дежурный принимает инцидент и пишет внутреннюю заметку → возврат сервиса закрывает инцидент, но задачу закрывает человек, выполнив пункты → публичная страница показывает только опубликованные проверки без адресов и заметок.

До создания первой проверки HTTP-запросы не выполняются.

## Границы

- Проверяются только цели из операторского списка: URL, адреса и тело ответа не попадают в представления и публичный статус. Редиректы не выполняются, TLS-проверка не отключается, секретные заголовки приложения не передаются.
- Успехом считается только 2xx. Редирект, слишком большой ответ и тайм-аут не дают ложного `up`; истёкшая попытка записывается как `unknown`.
- Один authority владеет записью, обслуживающие узлы отдают представления, probe-процессы выполняют HTTP. Это разные роли, а не конкурирующие писатели.
- Помощник — детерминированное демо без модели и платных запросов; при отсутствии измерений он прямо говорит, что причину определить нельзя.
- Уведомления остаются внутри приложения: email и Slack не отправляются.
- Пределы стенда: 100 мониторов, 300 наблюдений на монитор, 1000 инцидентов, 100 заметок на инцидент, 500 задач, 2000 уведомлений и записей аудита, 1200 команд в минуту. Длительная эксплуатация требует своей политики архива; постоянный диск не заменяет резервную копию.
- Частные сводки остаются в дисковом журнале: автоматической физической очистки и отдельной политики копий здесь нет.
- `backend/ui-fixture.ts` создаёт явно демонстрационные отчёты для интерфейса, не выполняет HTTP и доказательством доступности не является.

## Проверки

```text
npm run typecheck
npm test
npm run build
```

`npm test` проверяет доменные роли, ревизии, аренды и пороги; настоящий HTTP с привязкой адреса, редиректом, тайм-аутом и лимитами; частную сводку и отмену; **authority с двумя обслуживающими узлами и двумя отдельными probe-процессами**, где оба реально делают HTTP, работа подхватывается после остановки первого, отключение узла сохраняет клиентское состояние, а рестарт продолжает расписание без повторных инцидентов. Отдельная проверка встроенного исполнителя закрывает неверный пароль, отсутствие технической роли, измерение при недоступном внешнем адресе authority и отказ принять запоздалый результат после отзыва членства.

Холодная копия — `npm run test:backup`. Размещение — `npm run test:monitoring` из `apps/hosting`: настоящий 404 открывает инцидент и задачу, обновление сохраняет их и частную сводку, 200 закрывает инцидент, откат сохраняет историю и отзыв дежурного.
