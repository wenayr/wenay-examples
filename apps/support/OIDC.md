# Внешний вход: OpenID Connect

Пример умеет подтверждать внешнюю личность через Authorization Code Flow с PKCE, затем открывать обычную сессию `wenay-common2`. Если провайдер не задан, внешних запросов нет и кнопка внешнего входа скрыта. Платные сервисы для локальной проверки не нужны.

## Граница ответственности

Публичная документация установленного common2 (`doc/RPC-AUTH.md`) относит OAuth/OIDC, пользователей и политику доступа к приложению. Поэтому протокол подключён через опубликованный `openid-client@6.8.8`, а существующая библиотека по-прежнему отвечает за сессии, ролевые фасады, RPC и реактивные представления.

В адаптере нет своего JWT/OAuth протокола. Проверки discovery, PKCE, state, nonce, issuer, audience, времени действия и JWS-подписи выполняет `openid-client`. Включён `enableNonRepudiationChecks`, поэтому проверка реальной подписи ID token через ключи issuer обязательна и проверена тестом с неверной подписью.

## Настройка

Переменные окружения описаны также в `.env.example`:

| Переменная | Значение |
| --- | --- |
| `OIDC_ISSUER` | Точный HTTPS issuer из настроек провайдера. Не URL discovery-документа |
| `OIDC_CLIENT_ID` | Идентификатор зарегистрированного приложения |
| `OIDC_CLIENT_SECRET` | Секрет confidential client, если он нужен. Для public client не задавать |
| `OIDC_ORIGIN` | Публичный origin поддержки, например `https://support.example.com`. По умолчанию используется `SERVICE_PUBLIC_URL` |
| `OIDC_ENDPOINT_ORIGINS` | Дополнительные доверенные origin провайдера через запятую, только если authorization/token/JWKS endpoint находятся не на origin issuer |
| `OIDC_ALLOW_LOOPBACK_HTTP` | `1` только для явно выбранной локальной проверки HTTP на `127.0.0.1`, `localhost` или `::1` |
| `SERVICE_DEMO` | `0` отключает парольный вход и создаёт пустое начальное состояние. Использовать новый `SERVICE_DATA_DIR` |

У провайдера зарегистрировать callback:

```text
https://support.example.com/auth/oidc/callback
```

Запрашиваются только `openid profile`; email, refresh token и права организации не запрашиваются. Поддержан `client_secret_post` либо public client без секрета. Провайдер с другими обязательными методами аутентификации требует явного расширения настройки адаптера и отдельной проверки.

Смена `SERVICE_DEMO` не очищает существующее хранилище и не удаляет старые данные. Для настоящего экземпляра нужен отдельный пустой каталог данных. Никогда не переносить демонстрационные аккаунты в рабочий экземпляр.

Секреты задаются на сервере, не в клиентских Vite-переменных. Не добавлять их в репозиторий, аргументы URL или журналы. Прокси не должен сохранять query callback в access-логах: authorization code приходит по стандартному OIDC callback, хотя сессионный токен приложения в URL никогда не попадает.

При `npm run dev` Vite проксирует `/auth`, `/api` и `/socket.io` к серверу. Для проверки OIDC в этом режиме `OIDC_ORIGIN` должен совпадать с origin вкладки Vite (например `http://127.0.0.1:5180` при явно разрешённом loopback), а callback у провайдера — с этим же origin плюс `/auth/oidc/callback`. Origin backend и origin Vite — разные адреса; callback и POST exchange должны оставаться на адресе вкладки. Для обычной сборки `npm run build` + `npm start` используется публичный origin самого приложения.

## Поток входа

1. `GET /auth/oidc/status` сообщает, настроен ли внешний вход.
2. `GET /auth/oidc/start` создаёт отдельные случайные state, nonce и PKCE verifier. В браузер отправляется только случайный HttpOnly cookie; значения проверки хранятся в памяти процесса пять минут.
3. Провайдер возвращает браузер в `/auth/oidc/callback`. Нужен исходный cookie и совпадающий state. Запись потребляется до запроса token endpoint, поэтому два одновременных callback не выполняют вход дважды.
4. После проверки токена cookie меняется на одноразовый HttpOnly handle со сроком одна минута. Ответ перенаправляет на `/` без токена или кода приложения в URL.
5. Клиент делает `POST /auth/oidc/exchange` с `X-OIDC-Exchange: 1`, тем же cookie и Origin приложения. Чужой Origin или отсутствующий заголовок отклоняются.
6. Сервер один раз сопоставляет подтверждённую личность с аккаунтом и вызывает существующий `leader.identity.login`. Ответ содержит обычный `{token, ...}`. Повторный обмен получает `204`.

На HTTPS cookie имеет префикс `__Host-`, флаги `Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/` и не содержит Domain. HTTP без Secure разрешён только явно включённому loopback. Ответы входа запрещают кэширование и передачу Referrer. Ошибки провайдера, токены и секреты не выводятся в HTML или журнал адаптера.

Исходящие запросы ограничены origin issuer и явно перечисленными `OIDC_ENDPOINT_ORIGINS`. HTTP-редиректы провайдера не выполняются, чтобы credentials не ушли на другой адрес. На сетевую операцию установлен таймаут десять секунд.

## Учётная запись и права

Адаптер принимает `provision({issuer, subject, name})` и `login(account)`. Сервис создаёт стабильный аккаунт из пары `(issuer, subject)` через системную команду `identityProvision`. Имя используется только для отображения. Email или совпавшее имя не объединяют аккаунты и не предоставляют права.

Новая внешняя учётная запись не имеет рабочего локального пароля и не включена ни в одну организацию. Пользователь создаёт собственную организацию или принимает одноразовое приглашение по уже существующим правилам приложения. Повторный вход не восстанавливает отозванные роли.

Обычный клиент не может вызывать `identityProvision`: команда требует системного фасада и дополнительно проверяет `SYSTEM_ACCOUNT` на сервере.

## Масштабирование и ограничения

OIDC start/callback/exchange в этой версии обслуживает authority. Все три пути должны попадать на один процесс через стабильный origin. Serving nodes обслуживают существующий RPC/проекции, но самостоятельная входная страница serving node пока не является отдельным OIDC callback endpoint.

Временные OIDC-записи не реплицируются и не сохраняются на диск: рестарт безопасно заставляет повторить вход. Очередь ограничена 1000 незавершённых потоков/обменов; истёкшие записи удаляются при обращении. Это не обещание бесшовного failover входа между auth-узлами.

Поддержан вход. RP-initiated logout у провайдера, back-channel logout, обновление provider access token и корпоративный SCIM provisioning не реализованы. Выход из поддержки закрывает локальную сессию клиента и не обещает закрыть сессию самого провайдера.

## Проверка

```text
node --import tsx backend/oidc-check.ts
```

Проверка запускает два небольших HTTP-сервера только на loopback: приложение и локальный protocol fixture провайдера. Fixture публикует discovery и JWKS, проверяет реальный S256 verifier, выдаёт подписанный RS256 ID token. Производственный код использует стандартный клиент без подмены протокольных функций.

Проверены успешный вход, неверный discovery issuer, чужой endpoint origin, отсутствие cookie, несовпадение state до обращения к token endpoint, nonce, issuer/audience/expiry/signature токена, отказ провайдера, отказ PKCE, повторные и конкурирующие callback/exchange, чужой Origin, обязательный заголовок обмена, истечение обоих сроков, выключенный адаптер и запрет удалённого HTTP.

Локальная проверка проходит. Подключение реального внешнего провайдера, его экран согласия и HTTPS browser round trip требуют настроенного экземпляра и пока не проверены. Ключи у пользователя не запрашивались.

## Источники

- Официальный [пример OIDC Authorization Code Flow](https://github.com/panva/openid-client/blob/main/examples/oidc.ts) использован как ориентир для PKCE и nonce.
- [Discovery](https://github.com/panva/openid-client/blob/main/docs/functions/discovery.md) рекомендует передавать issuer; прямой URL metadata отключает соответствующую проверку, поэтому адаптер его отклоняет.
- [enableNonRepudiationChecks](https://github.com/panva/openid-client/blob/main/docs/functions/enableNonRepudiationChecks.md) включает проверку JWS-подписей полученных JWT.
