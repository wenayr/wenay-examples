# Каталоги размещения

Каталог включает картографические точки размещения и записи реестров. Наличие номера, доступность для конкретных дат и договор с объектом подтверждает коммерческий поставщик. Метаданные `price` и `photo` этих трёх источников равны `null`. Фотографии с собственной подтверждённой лицензией подключаются отдельно.

| Источник | Что отбираем | Источник и лицензия |
| --- | --- | --- |
| OpenStreetMap contributors | Именованные гостиницы и другие типы размещения внутри прямоугольника курорта. У полигонов координата соответствует центру ограничивающего прямоугольника. | [Данные OpenStreetMap](https://www.openstreetmap.org), [ODbL 1.0](https://www.openstreetmap.org/copyright), [условия общих серверов Overpass](https://dev.overpass-api.de/overpass-doc/en/preface/commons.html) |
| Wikidata | Объекты с классом гостиницы или производным классом и координатами в регионе. Исключены известные даты ликвидации и прошедшая дата закрытия. | [Сервис SPARQL](https://www.wikidata.org/wiki/Wikidata:SPARQL_query_service), [CC0](https://www.wikidata.org/wiki/Wikidata:Licensing) |
| Fáilte Ireland | Отели, B&B, хостелы, гостевые дома и апартаменты с регистрационным номером и координатами из национального реестра Ирландии. | [Государственный реестр и API](https://data.gov.ie/dataset/national-quality-assurance-framework-register-of-accommodation), [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/) |

Каждый файл в `snapshots` — отдельная адаптированная выборка указанного источника. Для выборок OpenStreetMap действует ODbL 1.0, для выборок Fáilte Ireland действует CC BY 4.0. Формат изменён. В рабочем контракте сохраняются идентификатор, происхождение и разрешённые сведения записи. Интерфейс указывает исходный каталог и его лицензию. Соответствие между поставщиками служит навигацией между записями; исходные выборки и их лицензии остаются доступными независимо. Имена владельцев и контакты физических лиц из реестра Fáilte Ireland не импортируются. Время `fetchedAt` обозначает момент получения выборки. При успешном ответе с пустым списком время также сохраняется. Отсутствие полученной выборки обозначается значением null. Записи могут отставать от реального состояния гостиницы.

## Обновление

Из `apps/travel`:

```sh
node backend/places/refresh.mjs
node backend/places/refresh.mjs wikidata phuket
node --test backend/places/places.test.mjs
```

Загрузка разрешена только для регионов в `registry.mjs`. Ограничения одного ответа: до 1000 объектов OpenStreetMap и 350 строк Wikidata до удаления повторов. Отсутствие гостиницы в выборке не определяет её наличие или статус бронирования. CLI обновляет снимки атомарно. При сетевой ошибке ранее сохранённая выборка остаётся на диске. При массовом запуске на один источник приходится один одновременный запрос. Ответ HTTP 429 останавливает оставшиеся запросы к этому источнику в данном запуске. Для регулярного коммерческого трафика учитывайте рекомендации оператора общего сервера Overpass о собственной инфраструктуре.

### Рабочие поколения и индексы

CLI и обновления сервера публикуют один файл на источник и направление в `apps/travel/travel-data/places/`. Для рабочего каталога на другом диске или общего каталога нескольких процессов задайте одинаковый абсолютный `TRAVEL_SNAPSHOT_DIR`. Чтобы результаты переживали перезапуск контейнера, подключите для него постоянный диск. До первой загрузки источник использует комплектный снимок из `backend/places/snapshots/`.

Имя версии содержит монотонную метку публикации и хеш содержимого. Время наблюдения хранится внутри снимка. Она записывается во временный файл и публикуется атомарным переименованием в той же директории. Читатель открывает последнее завершённое поколение. Отложенный ответ на более ранний запрос не откатывает полную версию. Хранятся два последних поколения каждого направления и источника. Для согласованного порядка времени нескольких процессов требуется одна временная шкала и файловая система с атомарным переименованием. CLI и сервер берут эксклюзивную блокировку по региону и источнику до начала запроса. Поэтому два параллельных ограниченных ответа объединяются по очереди. Рабочий каталог рассчитан на процессы одного хоста. Для блокировки используется служебный файл SQLite без строк каталога. ОС освобождает её при завершении процесса, в том числе аварийном. При занятой блокировке ожидание асинхронное, не более 40 секунд или времени переданного запроса. Чтение опубликованных JSON продолжается независимо от блокировки.

При полном ответе источника исчезнувшая строка удаляется из его выдачи. Если ответ OSM или Wikidata достиг известного лимита выборки, новые и изменённые строки дополняют предыдущие. Типовые ошибки HTTP, ответ Overpass с `remark` и CSV без ожидаемых колонок сохраняют последний успешный снимок. Повторный снимок с теми же полями обновляет время наблюдения без события об изменении отеля.

Подготовьте поисковый файл заранее из каталога `apps/travel`:

```sh
npm run catalog:prepare
```

Путь к поисковому файлу можно задать через `TRAVEL_CATALOG_INDEX_PATH`. У подготовки и сервера должны совпадать этот путь, каталог исходных поколений и путь к манифесту фотографий. На старте сервер сверяет версии входных данных. При отсутствии индекса или появлении новых исходных поколений сервер завершает импорт до начала обслуживания HTTP. На большом каталоге `catalog:prepare` позволяет выполнить эту работу заранее. После перезапуска с теми же данными достаточно сверки версий.

Первая страница читает упорядоченный индекс выбранного направления. На экране видны до 12 карточек и общее количество совпадений. Кнопка «Искать в этой области» добавляет границы карты. Обычное перемещение карты оставляет текущую выдачу на экране. Каждому направлению принадлежит отдельный пространственный индекс SQLite RTree, поэтому даже при максимальном отдалении карта ищет только в текущем направлении. Поиск по имени внутри области дополнительно проверяет текст у попавших в неё точек. При поиске по подстроке длиной от трёх символов по всему направлению сервер использует его текстовый индекс FTS5. При одном или двух символах проверяется текст в индексе региона. Для точного общего количества результатов сервер проверяет все подходящие ключи, а полные карточки читает лишь для запрошенной страницы.

Новый полный снимок поставщика требуется прочитать для выявления изменений и снятых записей. На работающем сервере это делает отдельный поток. При замене фотообложки он сверяет новый манифест фотографий с предыдущим и применяет изменения к записям с подходящими идентификаторами. Пока идёт импорт, посетители продолжают получать предыдущую согласованную версию. После фиксации изменений клиенты этого направления получают уведомление SSE. Повторное открытие карточки читает объект по ключу направления и идентификатору отеля.

### Проверка масштаба

```sh
node bench/catalog.ts real
node bench/catalog.ts 750000
```

Первая команда использует комплектные данные 16 направлений. Из 5 513 строк источников получается 5 040 объектов после объединения дублей. Вторая генерирует 750 000 уникальных записей с координатами внутри курортов. Обе команды подготавливают индекс во временном каталоге, запускают новый серверный процесс и выполняют один и тот же HTTP-сценарий в Хургаде. Он включает страницу из 12 карточек, поиск по границам карты и источнику, дополнительный поиск по имени, переход на следующую страницу и получение выбранного отеля по ID. Затем публикуется изменение одного фото и проверяется обновлённая карточка после уведомления SSE. После завершения временные файлы удаляются.

Время HTTP-запроса включает обработку сервером и получение JSON по loopback. Тест выводит число прочитанных полных карточек, их размер, размер HTTP-ответа и RSS процесса. На Linux `processReadCallBytes` берётся из счётчика `rchar` файла `/proc/self/io` с поправкой на размер чтения самого счётчика. Он показывает число байтов, которые системные вызовы чтения вернули всем потокам процесса, включая страницы из кеша ОС. Этот кеш сохраняется между подготовкой и чтением. Сетевые вызовы поставщиков выключены.

В одном прогоне на Linux с Node.js 24.22.1 из 750 000 синтетических отелей 46 875 относились к Хургаде. Подготовка SQLite заняла 91,2 с и 725,7 МиБ на диске. Новый процесс открыл готовый индекс за 10,3 мс, прочитал 61 584 байта и не загрузил ни одной полной карточки. При каждом действии полные карточки читались только из Хургады.

| Действие | Найдено | Прочитано полных карточек | Тело HTTP, байт | Время, мс |
| --- | ---: | ---: | ---: | ---: |
| Открыть Хургаду | 46 875 | 12 | 5 545 | 36,44 |
| Искать в видимой области, источник OSM | 2 080 | 12 | 5 584 | 9,97 |
| Перейти на следующую страницу | 2 080 | 12 | 5 582 | 7,24 |
| Добавить к области и источнику слово «hotel» | 693 | 12 | 5 583 | 7,62 |
| Открыть выбранный отель | 1 | 1 | 457 | 2,27 |
| Вернуться к той же области и фильтрам | 693 | 12 | 5 583 | 5,87 |

На версии `5922547` тот же первый HTTP-запрос извлекал из JSON все 46 875 строк Хургады. Клиент получил те же 12 карточек и 5 545 байт. Время составило 1 102 мс, системные вызовы чтения вернули 5 200 286 байт. В версии с готовым индексом эти вызовы вернули 48 620 байт. При фильтрации по карте для подсчёта и сортировки 2 080 совпадений сервер прочитал 942 080 байт, из них JSON 12 выбранных карточек занял 4 631 байт. После замены фото изменилась одна запись. Сервер передал региональное уведомление SSE через 1,32 с, затем клиент получил обновлённую карточку за 7,91 мс.

На комплектных данных та же последовательность дала 295 объектов в Хургаде, 58 в области с фильтром OSM и 20 после добавления слова «hotel». Каждая страница содержала 12 карточек. Сервер вернул 12 859 байт при открытии Хургады и 430 байт при запросе одной карточки. Идентификаторы, порядок выдачи и размеры ответов в обоих наборах совпали с версией `5922547`.
