# Общий буфер и подписки на цены

Цены TEZ проходят через общий буфер наблюдений, а интерфейс подписывается на изменения нужных ему ресурсов. SQL для промежуточных цен не используется. Карта, поиск, календарь и матрица продолжают работать через прежние HTTP-контракты.

## Три разные обязанности

| Слой | Что делает | Граница |
| --- | --- | --- |
| Адаптер поставщика | Запрашивает и проверяет реальный ответ TEZ, сохраняет условия тарифа и исходное время проверки | Для TEZ подтверждён request/response API; webhook не подключён |
| Буфер источника | Объединяет одинаковую работу, сохраняет последний результат, свежесть, паузу и общий допуск запросов | Hosted: R2 JSON + локальный ограниченный Map; local: память процесса |
| Подписки интерфейса | Обновляют востребованную проекцию один раз на ресурс и рассылают небольшие SSE-уведомления | Это клиентский транспорт, а не push от поставщика |

`listenStore` предоставляет callback-подписки, `createReconciler` объединяет запуски и владеет повторными проверками, `replayListen` хранит ограниченную историю уведомлений одного isolate. Используются опубликованные entrypoints закреплённых `wenay-common2 3.3.3` и `wenay-react2 5.0.0`. Последний `off` сам по себе не закрывает producer библиотеки: предметный владелец явно считает подписчиков и закрывает reconciler.

## Что именно является ключом

Буфер хранит **наблюдение конкретного запроса поставщика**, а не полную таблицу всех тарифов. Ключ — канонический фактический TEZ request: рынок и город вылета, страна/регион, отель при наличии, даты, интервал ночей, состав гостей, валюта и другие параметры источника. Параметры сортируются. Account scope задаёт сервер; секреты в публичные ключи и уведомления не попадают.

Бюджет включён, когда upstream `supplier-minima` выбирает минимум внутри бюджета. Минимум полного диапазона не позволяет восстановить следующий тариф для более высокого нижнего порога цены. Такие ответы нельзя объявлять взаимозаменяемыми. Гостиничные запросы, в которых адаптер действительно запрашивает полный диапазон цен, затем проецируются на выбранные ночи и бюджет. У этой проекции сохраняются ограничения полноты исходного ответа.

Идентичность браузерного ресурса отдельно включает HTTP route, нормализованные query-параметры и контекст видимости агентства. Порядок параметров и `refresh=1` не создают новый ресурс. Viewport, избранное и расположение карточки не дробят общий исходный ответ, если они не входят в реальный upstream запрос.

## Свежесть и ошибки

| Состояние | Поведение |
| --- | --- |
| Достоверный свежий ответ | Возвращается из общего или локального буфера с исходным `checkedAt`/`updatedAt` |
| Подтверждённый отрицательный ответ | Имеет короткую свежесть; не подменяет ошибку транспорта |
| Частичный ответ | Отсутствующая ячейка остаётся неизвестной, а не подтверждённо пустой |
| Ошибка или ограничение поставщика | Последний пригодный результат остаётся с прежним временем, `stale` и `retryAt` |
| R2 недоступен | Hosted-контур закрывает новый допуск: stale/unknown + повторная пауза; скрытого перехода к независимому upstream из памяти нет |
| Срок удержания истёк | Старая цена больше не пригодна для показа как результат; нового времени проверки ей не присваивают |

Ручной refresh проходит общий допуск. В hosted-режиме повторная проверка одного свежего наблюдения ограничена `manualRefreshGapMs=15_000`; повторное использование возвращает cached и исходное время, а не новый live-ответ. Refresh также соблюдает `nextAttemptAt`, паузу после ошибки и provider `Retry-After`. Локальный совместимый режим допускает явный повтор после локальной ошибки, но сохраняет provider cooldown и квоту процесса. Подтверждение конкретного тарифа по-прежнему требует live-ответа; cached/stale/denied не означает подтверждённое наличие.

## Несколько экземпляров Worker

Обычный Map принадлежит одному isolate. Общим источником для разных экземпляров служат R2 JSON records в отдельном prefix `travel-source-buffer/v1/`; профили агентств и заявки остаются в своём пространстве.

Storage adapter создаётся лениво внутри ожидающего read/admit; в сервисе кэшируется готовый объект, а не незавершённый Promise инициализации короткого запроса статики. Весь объединяемый hosted read, включая hash и начальный R2 lookup, с начала работы принадлежит `waitUntil`-владельцу. Тот же operation deadline действует внутри queued R2 task, чтобы отменённое чтение освобождало слот. Это необходимо из-за request context Workers: продолжение умершего владельца может быть отброшено, даже если обычный Node event loop продолжил бы его выполнять.

Допуск поставщика хранится в одном CAS gate: ограничение стартов, минимальный интервал, до шести активных leases и монотонный fencing sequence. Новый старт записывает gate не чаще одного раза в две секунды. Отдельной записи release на каждое завершение нет: следующий допуск проверяет до шести HEAD метаданных снимков и удаляет завершённые leases в своей единственной CAS-записи. Конфликт допуска возвращает `retryAt`, а не запускает горячий цикл повторов.

Интервал относится к времени допуска в координаторе. Сетевые задержки между CAS и fetch не гарантируют точного расстояния между фактическими пакетами к поставщику; одновременно допущенная работа дополнительно ограничена leases и deadline.

Завершение публикует снимок отдельного ключа условной записью по ETag и sequence. Старый владелец не может перезаписать более новый снимок. Это не транзакция нескольких объектов и не обещание exactly-once при сетевом разрыве. После истечения lease/deadline новые операции публикации не начинаются; исходное время ответа не обновляется искусственно.

Provider `429` сохраняет общий cooldown отдельно; локально известная пауза действует немедленно даже при ошибке записи. Завершённый снимок ошибки также несёт cooldown в метаданных lease. Другой экземпляр соблюдает паузу после доступного ему сохранённого общего состояния; ранее допущенные запросы уже могли стартовать. Если общее хранилище не отвечает, новый upstream не допускается.

Достоверные R2 записи используют native conditional put. Node preview содержит совместимый файловый адаптер с HEAD/ETag/metadata и CAS только внутри одного Node-процесса; это не доказательство распределённого CAS платформы.

## Настройка сервера

Профиль выбирается только серверным `TRAVEL_UPDATE_PROFILE`; отсутствие значения означает `demand`. Реестр `providerBufferProfiles` проверяется через `satisfies`. Клиент и настройки отдельного агентства не меняют квоту поставщика.

| Профиль | Автообновление активных ресурсов | Свежесть | Сверка общего снимка | Hosted старты |
| --- | --- | --- | --- | --- |
| `demand` | Да | 120 с | 10 с | До 30/мин, интервал от 2 с |
| `request-only` | Только явные обращения; без регулярного обновления | 120 с | При обращении | До 30/мин, интервал от 2 с |
| `economy` | Да | 300 с | 30 с | До 15/мин, интервал от 4 с |

Общие настройки: manual gap 15 с, удержание результата 15 мин, короткая отрицательная свежесть 30 с, ошибка 10 с, deadline работы 20 с, lease 25 с, не более 6 одновременно допущенных работ. Свежесть — политика пригодности результата, а не гарантия нового ответа каждые 10 секунд: общая квота может отложить обновление.

Generated hosted entry требует `BUCKET`: его отсутствие возвращает API503/Retry-After до создания source-сервиса, а не переключает сайт на память. Локальный/test entry допускает явно обозначенный `process-memory`; его 45 запросов/мин относятся к процессу. Health `/api/travel/health` сообщает профиль, режим, реальные лимиты и транспорт, не выдавая владельцев, supplier keys или приватные query traces.

## Подписка и восстановление интерфейса

На вкладку/экземпляр интерфейса действует один EventSource; разные вкладки имеют собственные подключения. Descriptor содержит общие параметры и различия ресурсов. Разрешены только шесть read routes: packages, поиск отеля, календарь, тренды, матрица и сравнение. Agency, leads, reviews, произвольные URL и booking recheck не подписываются. Ограничения: 48 ресурсов на подписку, фактический URL меньше 8 KB, query до 3 KB. При большем descriptor все ресурсы остаются в общем HTTP-контуре, а не молча исчезают.

На isolate одновременно допускается до 128 клиентов, 192 активных ресурса и 32 разных каналов. Место резервируется до асинхронного открытия; полная ёмкость всех ресурсов проверяется до запуска работы. Отказ возвращает 503 и Retry-After. Эти caps локальны для экземпляра и не являются общей защитой бюджета всего сайта.

Каждый активный ресурс имеет одного владельца обновления и callback-лист. Новый результат того же ресурса немедленно уведомляет его подписчиков. Для другой проекции того же источника используется сверка до 10 секунд в обычном профиле, до 30 секунд в economy. Полной графовой трассировки зависимостей здесь нет. Подключённый клиент получает invalidation и читает обычный HTTP-снимок; общая source-работа при этом не умножается на число клиентов.

Demand определяется видимым контекстом поиска, а не временным `loading`. Фоновая проверка того же контекста сохраняет карточки, мини-матрицу и графики; реальные новые параметры или закрытие страницы отписывают старые keys. Это предотвращает цикл reset → background loading → снятие спроса → новое подключение → reset.

Подпись снимка не зависит от счётчиков чтения или нового generatedAt. Live/cached нормализуются для сравнения; `retryAt` округляется только в fingerprint до шага сверки, чтобы плавающая оценка ожидания не образовывала петлю invalidation → HTTP → invalidation. Оригинальные времена и точный `retryAt` в ответе не меняются.

SSE содержит capability, heartbeat, resource и reset. Браузерный `onopen` ещё не означает рабочий поток: live показывается после проверенного application frame. История seq принадлежит epoch одного isolate; переподключение может получить retained tail, а другой epoch — reset и текущие снимки. История между репликами не выдумывается.

Если gateway не передаёт поток, общий клиентский reconciler переходит на ограниченный HTTP fallback и периодически перепроверяет SSE. Два polling-владельца параллельно не работают. Серверный профиль передаётся также HTTP-заголовками `x-travel-update-profile` и `x-travel-shared-check-ms`, поэтому request-only соблюдается и без SSE; неизвестный профиль не даёт разрешения на фоновый опрос. Текущий режим виден в небольшом статусе карты и DOM `data-live-transport`, `data-live-profile`, `data-live-epoch`, `data-live-resets`.

Последняя отписка/невидимая вкладка закрывает транспорт и регулярные таймеры. Уже допущенная hosted-работа может ограниченно завершиться через `ExecutionContext.waitUntil`, чтобы уход клиента A не отменял ожидание клиента B на другом экземпляре. Это не бесконечная фоновая служба. Необходимые trusted identity headers сохраняются только пока ресурс активен; Cookie/Authorization не копируются в долгоживущие записи. Видимость агентства проверяется сервером на каждом обновлении/новом подключении.

## Память и физическое хранение

Локальный source LRU ограничен 360 записями и совокупным conservative resident budget 12 MiB. Подготовленные индексы и индексы области имеют отдельные weighted LRU бюджеты по 8 MiB; слишком большой индекс не сохраняется в кэше. Оценка учитывает входные данные с запасом и не является измерением всей heap Worker. Ответ поставщика и R2-снимок читаются потоком с пределом 2 MB до JSON.parse; oversized ответ не превращается в свежую пустоту. Число ожидающих разных source keys ограничено 48 до общего чтения/очереди; одинаковое начальное чтение объединяется, одновременно выполняются не более четырёх R2 reads/HEAD/decode. Это отдельные защиты от runtime лимита Worker 128 MB, а не утверждение, что приложение занимает ровно 12 MiB.

`retainMs` ограничивает допустимость использования результата, **не удаляет R2-объекты физически**. Комбинации source keys накапливаются. Автоматический lifecycle для binding текущий проект не provisionит. При эксплуатации следует настроить R2 lifecycle только для prefix `travel-source-buffer/v1/<server-scope-hash>/snapshots/` либо перенести снимки в отдельно управляемое временное хранилище. Control gate/cooldown и agency/leads в такую политику включать нельзя. Full-bucket scans и небезопасного read → unconditional delete здесь нет. До настройки lifecycle физическая очистка не обещается.

## Возможности платформы и источники

В текущем Sites manifest доступны R2 и D1; Durable Objects, Queues и cron не подключены. R2 не является pub/sub. Поэтому используются callback внутри isolate и ограниченная сверка общего хранилища; без клиентов постоянного опроса нет. Production gateway SSE требуется отдельно проверить после публикации; функциональный HTTP fallback обязателен независимо от результата.

- [R2 consistency и atomic conditional operations](https://developers.cloudflare.com/r2/reference/consistency/).
- [R2 Workers API и onlyIf](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/).
- [R2 limits: одна запись одного ключа в секунду](https://developers.cloudflare.com/r2/platform/limits/).
- [R2 event notifications требуют Queue](https://developers.cloudflare.com/r2/buckets/event-notifications/).
- [Workers lifetime, streaming и waitUntil](https://developers.cloudflare.com/workers/platform/limits/).
- [Workers cross-request Promise resolution](https://developers.cloudflare.com/workers/configuration/compatibility-flags/#handle-cross-request-promise-resolution-correctly).
- [Официальный TEZ XML/JSON API](https://www.teztour.ee/page/xml-gate.et.html).

Запросы через браузеры посетителей для обхода блокировки IP не реализованы. Совпадение нескольких клиентских ответов не доказывает их подлинность и не решает CORS, ключи, ограничения поставщика или умножение запросов. Возможный официальный browser SDK требует отдельного договора и проверяемого контракта источника.
