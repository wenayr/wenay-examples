# Профили размещения

Дата: 11 сентября 2026. Задача P02 [плана 3](PLAN3-TASKS.md); закрывает пункт 2 [плана K04](K04-BACKUP-RESTORE-PLAN.md). Здесь три способа запустить пример и то, что каждый из них действительно обещает. Значения взяты из `backend/server.ts`, `.env.example` и проверок приложений, а не из общих соображений.

Общее для всех профилей: **запись принадлежит одному authority**. Обслуживающие узлы распределяют чтения и подключения, отдельные процессы-исполнители выполняют внешнюю работу. Несколько одновременных писателей, автоматическое переключение владельца записи и HA-база не поддерживаются и не проверялись.

## Профиль А — один процесс

Самый простой способ: один процесс, локальный каталог данных, без контейнеров.

```text
cd apps/<пример>
npm ci
npm run build
npm start
```

| Пример | Порт | Каталог данных | Запуск |
| --- | --- | --- | --- |
| pizzeria | 3500 | `data` | `npm start` |
| органайзер пиццерии | 3600 | `organizer-data` | `npm run start:organizer` |
| hosting | 3700 | `data` | `npm start` |
| catalog | 3800 | — (витрина без состояния) | `npm start` |
| support | 3810 | `support-data` | `npm start` |
| documents | 3811 | `documents-data` | `npm start` |
| metering | 3812 | `metering-data` | `npm start` |
| crm | 3813 | `crm-data` | `npm start` |
| booking | 3814 | `booking-data` | `npm start` |
| forms | 3815 | `forms-data` | `npm start` |
| monitoring | 3816 | `monitoring-data` | `npm start` |
| content | 3817 | `content-data` | `npm start` |
| approvals | 3818 | `approvals-data` | `npm start` |

Переменные окружения: `SERVICE_PORT`, `SERVICE_HOST` (по умолчанию `127.0.0.1`), `SERVICE_DATA_DIR`. Файл `.env` **не читается автоматически** — передайте переменные процессу или используйте `node --env-file`.

В каталоге данных лежит всё состояние сервиса: журнал команд и квитанции, ресурсы SC1 (вложения, файлы, частные результаты ИИ, контрольные точки), надгробия удалённых записей, журналы учёта и доставок. Резервная копия — **весь** каталог целиком при остановленном писателе; журнал сам по себе копию вложений не заменяет. Инструменты и границы — [отчёт о копировании](reports/backup-restore.md), состояние по приложениям — колонка «Копия» в [STATUS](STATUS.md).

Секреты сессий `SERVICE_TOKEN_SECRET` и `SERVICE_NODE_TOKEN` задаются независимыми случайными значениями и должны быть стабильными между перезапусками, иначе прежние входы потребуют повторной авторизации. Они не входят ни в образ, ни в резервную копию.

## Профиль Б — authority и обслуживающие узлы

Тот же authority плюс процессы, обслуживающие чтения и подключения.

```text
# authority
SERVICE_PORT=3910 SERVICE_DATA_DIR=<каталог>/authority npm start

# узел, столько раз, сколько нужно
SERVICE_PORT=3911 SERVICE_UPSTREAM=http://127.0.0.1:3910 SERVICE_NODE_ID=node-1 \
SERVICE_DATA_DIR=<каталог>/node-1 npm run start:node
```

Узлу нужны те же `SERVICE_TOKEN_SECRET` и `SERVICE_NODE_TOKEN`, что и authority, собственный `SERVICE_NODE_ID` и собственный каталог данных. Узел отдаёт `/health`, `/api/client` и статику; команды он передаёт владельцу записи. `npm run start:node` есть у support, documents, metering, crm, booking, forms, monitoring, content и approvals; у пиццерии для этого отдельная точка входа `npm run start:organizer:node`.

**Проверено вручную 11 сентября 2026** на support: authority на 3910 и два узла на 3911 и 3912. Authority записал в журнал `mirror node-1 registered at http://127.0.0.1:3911` и такую же строку для второго узла; `/health` ответил у всех трёх (`{"ok":true,"application":"support"}` у authority и `{"ok":true,"application":"support-node"}` у узлов), дескриптор `/api/client` доступен с узла. Того, что клиенты действительно читают через узлы, эта ручная проверка не доказывает — это делает автоматический тест.

Автоматическое доказательство топологии у каждого приложения своё:

| Пример | Что поднимает проверка |
| --- | --- |
| support | `backend/check.ts` — authority и два обслуживающих процесса, потеря узла, рестарт |
| documents | `backend/check.ts` — то же плюс два дочерних обработчика |
| metering | `backend/check.ts` — два клиента API, гонка за остатком квоты, отключение узла |
| crm | `backend/check.ts` — гонка ревизий, отказ узла, восстановление после рестарта |
| booking | `backend/check.ts` — два клиента, истечение удержания, перезапуск authority |
| forms | `backend/check.ts` — 20 параллельных ответов через двух клиентов, остановка узла |
| monitoring | `backend/check.ts` — authority, два узла и **два отдельных probe-процесса** |
| content | `backend/check.ts` — публичные чтения через узлы, offline 503, откат |
| approvals | `backend/check.ts` — полный цикл через разные узлы, отказ узла, отзыв роли |
| pizzeria | `backend/network-check.ts` — независимые заведения и узлы чтения |

## Профиль В — внешний Linux-хост с Docker

Образ собирается из `Dockerfile` приложения после `npm run build`:

```text
cd apps/<пример>
npm run build
docker build --memory 768m --build-arg APP_RELEASE=first -t wenay-examples.local/<пример>:first .
```

Свойства образа: закреплённый по digest `node:24-alpine`, пользователь `node`, данные в `/data`, `SERVICE_PORT=8080`, `SERVICE_HOST=0.0.0.0`, версия релиза в `/health` через `APP_RELEASE`. `.dockerignore` пропускает только `package.json`, `package-lock.json`, `backend`, `shared`, `public` и сам `Dockerfile`, исключая проверки и воспроизведения. Данные, `.env` и секреты в образ не попадают: подключите том к `/data`, а секреты передайте окружением.

Развёртывание, обновление и откат выполняет [пример хостинга](../apps/hosting/README.md) на настоящих контейнерах: `npm run test:<пример>` из `apps/hosting` при собранных образах `first` и `second`. Профиль контейнера в этих проверках — 256 МиБ памяти, 0.5 CPU, readiness по `/health`, постоянный том, стабильный адрес шлюза.

Измерения (моментальные снимки `docker stats` после операций, не пик под нагрузкой):

| Пример | Память при лимите 256 МиБ | Команда |
| --- | --- | --- |
| approvals | 52–54 МиБ | `npm run test:approvals` |
| metering | 54.4–55.3 МиБ | `npm run test:metering` |
| support | около 55 МиБ | `npm run test:support` |
| content | 56.4–57.1 МиБ | `npm run test:content` |
| crm | 57.1 МиБ | `npm run test:crm` |
| documents | 55.6–60.2 МиБ | `npm run test:documents` |
| booking | 59.1–60.2 МиБ | `npm run test:booking` |

Проверка обновления означает совместимые версии с одним форматом данных (`dataVersion` вида `<пример>-1`) — произвольная миграция схемы ею не доказывается. Откат образа возвращает прежний код, но **не откатывает данные**: отозванный доступ и новые записи остаются, а вернуть прежнее содержимое можно только предметной командой.

## Чего профили не обещают

- Нескольких одновременных писателей, автоматического выбора нового владельца записи и репликации между машинами.
- Горячей резервной копии: копия снимается при остановленном писателе.
- Настоящих виртуальных машин и Kubernetes: LXD представлен адаптером и protocol fixture, кластер не запускался.
- Внешних провайдеров: OIDC, платежи и языковые модели настраиваются отдельно и в этих профилях не участвуют.
- Замеров под нагрузкой: приведённые числа — снимки маленьких контейнеров на одной машине.
