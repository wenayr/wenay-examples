# Хостинг VM, системных контейнеров и Kubernetes

## Цель и порядок

Новый общий приоритет определён в [стратегии библиотек](LIBRARY-STRATEGY.md). Для хостинга следующий продуктовый рубеж — размещение органайзера и пиццерии с постоянными данными и рабочими HTTP/WS-адресами (S4), затем проверенное распределение нагрузки (S5). Состояния агентов, лимиты и lifecycle обслуживают этот сценарий; расширение VM/Kubernetes остаётся в резерве до подходящей среды.

Главный критерий каждого этапа — применение публичного API common2/react2 в реальном сценарии. Перед новой обвязкой проверить существующие возможности; найденные дефекты оформлять с воспроизведением, предложения отделять от дефектов. После этапа обновлять [пакет задач библиотекам](library-tasks/README.md). [Аудит хостинга 0.4.0](reports/hosting-library-assessment.md) завершён: существующие snapshot/signals применены, H1/H2/H0 подготовлены как предложения.

Этап 0.4.0 выполнен: постоянный loopback-адрес окружения, привязка активного контейнера по operation ID, завершение старых запросов перед удалением, автоматическая очистка с отчётом common2 и сохранением релизов для rollback. Проверены реальный Docker, HTTP gateway и восстановление архива/агента. [Результат](changes/hosting-0.4.0.md). Следующий лёгкий этап — состояние агента/маршрута и причины ожидания, лимиты числа окружений; реальные VM/Kubernetes остаются отложены из-за бюджета текущего хоста.

Контрольный этап Docker выполнен 9 сентября 2026: настоящий Node → отказ readiness без потери рабочего приложения → Python → rollback Node, перезапуск агента и очистка всех тестовых контейнеров. Подготовка обходится без registry. Новое ограничение пользователя: максимум 3 ГиБ RAM, целевой расход 1–2 ГиБ, последовательные лёгкие проверки. Следующий независимый срез — стабильный маршрут приложения и управляемая очистка старых кандидатов; тяжёлые VM/кластеры отложены до подходящей среды. [Результаты живого прогона](changes/hosting-docker-live.md).

Состояние 0.3.0: добавлен отдельный LXD-срез — команды машин, назначенный агент, создание/питание, панель и перенос архива. [Описание и границы](../apps/hosting/LXD.md). Проверены настоящий common2 RPC и LXD HTTP fixture; реальные VM ещё не запускались. Следующий контрольный этап — рабочий Docker для Node/Python и подготовленный Linux/LXD для контейнера и VM, затем готовность ОС/runtime, снимки и связь машин с версиями приложения. Полный план остаётся открытым.

Самостоятельный продукт в `apps/hosting`: клиент создаёт проект, выбирает ресурсы, подготавливает окружение и развёртывает точную версию приложения; оператор обслуживает физические машины, VM и кластеры. common2 обеспечивает межсервисную связь, роли, команды, receipts, состояние, replay и reconnect; react2 — клиентские подписки, формы действий и управление ресурсами компонентов.

Этот пример становится следующим приоритетом. Проверки длинной доски органайзера остаются в NEXT-STEPS и не блокируют хостинг. Работу вести по законченным срезам, не выдавать заявку в очереди за выполненную установку.

В 0.2.0 установлены Docker Desktop и WSL, добавлен OCI-исполнитель с общим профилем Node/Python и панель на react2. [История первоначального среза и уже устранённого блокера](changes/hosting-0.2.0.md). Живой контейнерный тест теперь проходит; далее стабильная маршрутизация и остальные этапы ниже. Docker не подменяет VM.

## Исходные решения

В соседнем lanaFour найден `infrastructureManager`: LXD/LXC, backend-owned профили установки, история точных Git revisions и receipts вне checkout, проверка health перед активацией, восстановление прерванных операций. Использовать эти сценарии как референс; не переносить его собственные SSE, хранение JSON, transport и frontend polling поверх готовых механизмов common2.

Первый провайдер — LXD, чтобы повторить уже известный сценарий; в модели отдельно `container` и `virtual-machine`. Incus возможен после проверки совместимости требуемых API extensions, без обещания полной взаимозаменяемости. Kubernetes — самостоятельный провайдер приложений, а k3s — первый профиль установки кластера на выделенных VM. Обычные VM не зависят от Kubernetes. LXC разделяет ядро хоста, полноценная VM имеет собственное ядро; уровень изоляции указывать при выборе ресурса.

| [cloud-init: этапы загрузки](https://docs.cloud-init.io/en/latest/explanation/boot.html) | Первичная подготовка гостевой ОС, установка пакетов, настройка; ожидание завершения cloud-init | Готовые cloud-config профили с версией. Проверять завершение подготовки отдельно от доступности SSH и готовности приложения |

Наш слой объединяет действия через ролевые фасады common2 и показывает состояние через react2. Виртуализацию, Kubernetes rollout и начальную настройку ОС выполняют соответствующие готовые системы. У одного объекта должен быть один механизм, отвечающий за его желаемое состояние: включённый Argo CD и наш прямой apply не должны одновременно менять один Deployment.

### Что добавить к модели хостинга по этим примерам

1. **Инвентарь инфраструктуры:** площадка → хост/кластер → ресурс. Storage pool, сеть, образ и backup — самостоятельные сущности со ссылками; окружение приложения ссылается на ресурс размещения. Запись в каталоге не означает успешное создание VM.
2. **Возможности и размещение:** агент сообщает поддержку container/VM, архитектуру, доступные CPU/RAM/storage и сети. Перед выдачей задания резервировать квоту с учётом незавершённых операций. Один недоступный хост не закрывает работу остальных.
3. **Раздельные состояния:** VM запущена, cloud-init завершён, runtime установлен, приложение прошло readiness, маршрут переключён. Каждый этап имеет свой наблюдаемый результат и причину ошибки.
4. **Установка как версия:** fingerprint базового образа, версия cloud-config/профиля, необходимые пакеты/runtime, digest приложения и ссылки на секреты. Пользователь выбирает профиль; набор шагов готовится сервером. Поддержка Node.js приоритетна, общий OCI-профиль уже предусмотрен для Python, Go, Java и других языков; их фактическую проверку отмечать отдельно.
5. **Эксплуатация:** обслуживание хоста, запрет нового размещения при drain, snapshots и проверяемый restore в новый ресурс, отдельный lifecycle постоянных дисков, ограничения сети. Отдельно проверять отказ процесса, хоста и площадки; не приравнивать их друг к другу.
6. **Деплой приложения:** подготовить → запустить кандидата → проверить → переключить стабильный маршрут → убрать старый экземпляр по политике хранения. Rollback приложения не меняет данные постоянного диска/БД без явно предусмотренной процедуры.

### Как принимать заимствованный пример

Для каждого адаптируемого сценария сохранять ссылку на официальный пример, проверяемую версию и локальное воспроизведение: подготовка чистой среды, успешное действие, повтор после потери ответа, ошибка, восстановление и адресная очистка. При переносе кода сохранять требуемую атрибуцию и учитывать лицензию; архитектурный референс сам по себе не требует копирования исходников. Успешная страница документации не заменяет исполнение сценария на стенде.

## Фасады и владельцы состояния

| Сервис | Ответственность | Основные поверхности |
| --- | --- | --- |
| Управляющий сервис | Проекты, роли, ресурсы, желаемое состояние, версии и операции | identity, commands, views через service definition |
| Исполнитель хоста | Проверка возможностей, подготовка, операции LXD и установка runtime | control для типизированных заданий, view/health для наблюдений, resource для LXD/SSH IO |
| Исполнитель Kubernetes | Namespace, workloads, rollout, наблюдение readiness | control.deploy/scale, view.rollout, resource.kubernetes |
| Клиент | Заявка, результат, история и доступные действия | Ролевой descriptor, библиотечные views/commands и react2 hooks |

Сначала один authority управляющего сервиса, затем реальные узлы чтения. Исполнители добавляются по независимым хостам/кластерам. Не выполнять SSH/LXD/Kubernetes IO внутри apply команды состояния: apply фиксирует намерение, исполнитель выполняет эффект и сообщает наблюдение. Внешний вызов может успеть завершиться до потери связи: нужны детерминированный resource name, provider operation ID и сверка состояния перед повтором. Receipt RPC сам по себе не обеспечивает exactly-once внешнего эффекта.

## Роли

- Администратор платформы: физические хосты, агенты, проекты, квоты, доступы.
- Владелец проекта: окружения, версии, деплои и участники своего проекта.
- Оператор проекта: deploy/rollback/scale, диагностика и операции в пределах проекта.
- Наблюдатель: состояние и история своего проекта без мутаций.
- Агент: только назначенные ему окружения и отчёты по операциям; не публикует релизы и не назначает права.

Права фильтруют фасады и повторно проверяются в командах; project/target ownership проверяется предметно. Секреты хоста, SSH-ключи, kubeconfig и registry credentials остаются у исполнителя либо в хранилище секретов. В состоянии только ссылки. Отзыв доступа и отсутствие соединения должны очищать закрытые панели.

## Этап 1. Управляющий сервис — первый срез выполнен

1. Отдельный npm-пакет и lockfile, опубликованный common2, без зависимости от пиццерии.
2. Реестр проектов и окружений: тип ресурса, назначенный агент, ревизия, желаемая и подтверждённая версии.
3. Неизменяемый релиз: проект, версия, OCI reference с SHA-256 digest. Изменение содержимого требует нового релиза. Для установки на VM позже отдельный проверяемый artifact manifest.
4. Запрос deploy/rollback с expected revision, одна незавершённая операция на окружение. Rollback выбирает ранее успешно подтверждённый релиз; не откатывает данные БД автоматически.
5. Начальная безопасная авторизация без встроенных рабочих паролей; ограниченные ролевые проекции. REST/OpenAPI/RPC и архив предоставляет библиотека.
6. Проверки настоящих сетевых клиентов: роли, чужой проект, неизменяемость релиза, конкурентные версии, повтор requestId, чтение с наблюдателя, восстановление очереди после перезапуска.

Критерий: самостоятельный запускаемый API сохраняет заявку и историю. Без исполнителя заявка остаётся queued и не получает фиктивный статус ready.

Состояние: [hosting 0.1.0](changes/hosting-0.1.0.md), typecheck и сетевые проверки проходят. Добавлены контракт получения операции и отчёт назначенного агента; в тестах наблюдения провайдера имитируются. Регистрация и изменение прав в работающем продукте, временные отметки аудита и его retention ещё предстоят. Полный хостинг этим этапом не завершён.

## Этап 2. Исполнитель и LXD

1. Подключение агента к common2, привязка к хосту, ограниченная очередь. Lease/attempt и fencing для устаревшего результата; недоступный агент не означает провал уже отправленного внешнего действия.
2. Read-only preflight: ОС, RAM/disk, виртуализация/KVM, LXD version/API extensions, сеть, storage pool и доступность образа. Показать конкретную причину недоступности VM.
3. Профиль подготовки хоста: точные версии пакетов, проверяемый план изменений, повтор без переинициализации существующего storage/network. Системные изменения выполнять только на выбранном тестовом хосте.
4. Создание контейнера и VM из закреплённого fingerprint, CPU/RAM/disk, cloud-init с публичным ключом, start/stop/restart, наблюдение provider operation и guest readiness.
5. Ограниченные snapshots/backups: checksum, восстановление в новый инстанс, подтверждение конкретной цели для удаления. Квота учитывает также операции в полёте.
6. Реальный Linux-тест: две изолированные машины, повтор заявки, потеря агента между отправкой и ответом, возобновление без дубля, остановка выбранной машины, очистка только созданных тестом ресурсов.

## Этап 3. Подготовка и версии приложений на VM

Backend-owned профили: чистая ОС, OCI runtime, Node/Bun либо systemd. Preflight → подготовка → доставка проверенного артефакта → запуск кандидата → readiness → переключение маршрута → завершение. Фиксировать image digest/Git SHA, версию профиля, конфигурацию и ссылки на секреты. Выполнять pre-install/migration как ограниченные описанные шаги, а не произвольный shell из браузера. Сохранять предыдущую рабочую версию до успешной проверки; явная политика миграции БД и отката данных. Проверить неудачную установку, rollback, рестарт контроллера на каждом рубеже и повтор команды.

## Этап 4. Kubernetes

1. Подключить уже существующий тестовый кластер с отдельным service account и ограниченными namespaces; затем профиль установки закреплённой версии k3s на VM.
2. Управлять Deployment/Service, ConfigMap/Secret references, readiness/startup probes, CPU/RAM requests/limits. Выделить namespace проекта и проверить RBAC плюс сетевые политики.
3. Версии релизов привязать к конкретному digest и manifest; rollout отслеживать по generation/observedGeneration и conditions, не по успешному ответу apply.
4. Deploy, scale, pause/resume и rollback с историей; не смешивать исторический релиз приложения и ревизию Kubernetes Deployment. StatefulSet/PVC и резервные копии — отдельный последующий сценарий.
5. На реальном кластере проверить два экземпляра, плохой образ, readiness failure, rollback, параллельные изменения и потерю узла. Затем второй агент/кластер и независимость отказов.

## Этап 5. Интерфейс на wenay-react2

Экран проекта: окружения, текущая/желаемая версия, состояние операции. Экран ресурса: VM/контейнер/кластер, квота и фактическая загрузка, доступные действия. Релизы: история, изменения и deploy/rollback. Установка: шаги, ошибки, повтор и фактический результат. Для каждой роли отдельные доступные действия и безопасные проекции; общий экран сведений не содержит секретов. Проверить на узком экране, при отзыве роли и смене проекта во время запроса. Доску задач подключать необязательным модулем после работающего хостинга.

## Этап 6. Эксплуатация и результат

Структурированный ограниченный журнал без секретов, метрики задач/агентов, backup/restore управляющего состояния, ротация служебного доступа, drain агента, повтор после сбоя, проверка лимитов. Второй узел чтения common2 должен реально обслуживать клиент и восстанавливать подписки. Межмашинный HA writer не заявлять без отдельного решения и теста. По каждому срезу отчёт: сколько предметного кода, какую обвязку убрала библиотека, какие её ограничения подтверждены воспроизведением.
