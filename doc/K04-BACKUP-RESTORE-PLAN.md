# K04 — профили размещения и проверяемое восстановление

План следующего ограниченного этапа. Это ещё не отчёт о выполнении новых backup-тестов.

## Что уже есть

- Самостоятельные приложения и scaffold с точными опубликованными зависимостями.
- Проверенные обновление/откат контейнеров через существующий хостинг, общий именованный том, стабильный gateway и `dataVersion`.
- `apps/hosting/backend/stateful-live-check.ts` уже останавливает собственного писателя, копирует его том в отдельный том ограниченным helper-контейнером и восстанавливает organizer/pizzeria. Переиспользуем этот способ остановки и изоляции вместо нового менеджера развёртываний.
- Публичный `createServiceLeaderHost` сохраняет основной `<service>.jsonl` и отдельный `<service>.control.jsonl`; частные файлы, AI checkpoints и результаты принадлежат ресурсам приложения. Сохранить только workspace/keyframe недостаточно для вложений, receipts и отозванных сессий.

## Предлагаемый результат

Небольшие описания профилей и прикладной инструмент **холодной** копии с проверкой целостности. Первая версия требует остановленного писателя и его фоновых ресурсов. Горячий согласованный snapshot нескольких журналов, HA authority и автоматические миграции в этот этап не входят.

1. **Инвентаризация данных.** Для каждого готового приложения записать сервисный ID, каталог данных, `dataVersion`, обязательные журналы/подкаталоги, внешние настройки и секреты. Состав проверить по реальным `server.ts`, runtime и ресурсам. В список включить control journal, bytes вложений/выгрузок, частные AI-результаты, tombstones, usage ledger и provider/webhook journal. Предпочесть весь разрешённый каталог данных приложения, чтобы новые ресурсные файлы не потерялись из-за слишком узкого glob.
2. **Три профиля размещения.** **Выполнено 11 сентября 2026** — [профили размещения](DEPLOYMENT.md), задача P02 плана 3. Локальный один authority с лёгким исполнителем; один authority + два serving nodes + отдельные прикладные исполнители; внешний Linux/Docker-хост. Указать порты, CORS/public URL, постоянный том, UID, память/CPU, секреты вне образа, точные образы/пакеты и единственного писателя. Профиль нескольких узлов не должен обещать нескольких одновременных писателей.
3. **Формат копии.** Каталог с данными и небольшим manifest: версия формата backup, приложение, dataVersion, версии библиотек/образ, время точки копирования, список относительных путей, размеров и SHA-256. Файлы копируются потоково. Manifest не содержит значения секретов и пользовательский текст. После копирования повторно проверить файлы и записать признак завершённой копии последним; неполная копия не восстанавливается.
4. **Остановка и согласованность.** Для Docker использовать известный owner/environment и существующий stop/remove путь, затем readonly mount исходного тома. Для локального процесса инструкция требует завершения собственного host и фоновых исполнителей; недоступный HTTP-порт сам по себе не доказывает отсутствие писателя. Не придумывать несуществующий публичный `flushAll` и не считать неизменный размер файлов гарантией горячей согласованности.
5. **Восстановление в новое место.** Только новый пустой каталог/том и совместимый dataVersion. Проверить manifest и hashes до запуска, исключить абсолютные пути, `..`, symlink/junction, дубли путей и пересечение с источником. Не перезаписывать работающие данные. Чужие каталоги/контейнеры не останавливать. Копия остаётся доступной после неудачного восстановления.
6. **Секреты и внешние действия.** Операторские token/node secrets восстанавливаются отдельно; manifest перечисляет требуемые имена, а не значения. При сохранении прежних токенов проверяется также восстановленный control journal с отзывами. В данных могут законно находиться частные заметки, bytes и webhook signing material, поэтому backup — закрытый артефакт, не публичный scaffold. Собственную систему шифрования не создавать. Тестовое восстановление запускается без платных ключей и внешних отправок, на локальных разрешённых целях.
7. **Живые доказательства.** Сначала документы (метаданные + raw bytes + одобренная версия + экспорт + приватный результат) и учёт (quota/ledger/semantic eventId + отозванный API-key). Затем Forms (публикация/ответы/агрегат/группы и удалённый tombstone) как проверка взаимодействия backup с удалением. Остальные приложения получают общий профиль и короткую доменную smoke-проверку согласно своим данным.
8. **Инструкция и отчёт.** Пример создания, проверки и восстановления копии, порядок обновления/отката, ограничение совместимости, фактически измеренные размер/время копии и восстановления. Не обещать RPO/RTO из маленького локального прогона. Показать, как отдельно проверять восстановление копий, а не только успешное создание архивов.

## Критерии приёмки

- Восстановленный сервис запускается на новом пути и порту с прежним состоянием, файлами, receipts и ограничениями доступа; исходный сервис/том не изменён.
- Повтор ранее принятого бизнес-события не удваивает расход или запись; потерянный/отозванный доступ не возвращается из-за неполной копии.
- Для Forms удалённый ответ из **новой** копии не возвращается повтором nonce. Старая копия до удаления может содержать старый текст: это явно описывается и учитывается отдельной политикой хранения backup.
- Повреждённый файл, отсутствующий blob/control journal, неподходящий dataVersion, незавершённая копия и опасный путь отклоняются до запуска восстановленного приложения.
- Операции копирования не читают весь архив в память. Проверки идут последовательно с прежним бюджетом: helper до 64–128 MiB, приложение до 256 MiB, без тяжёлых соседних сервисов.
- Scaffold не начинает переносить пользовательские данные или секреты вместе с исходниками.

## Граница библиотек

Использовать существующие public host/replay/identity/resource APIs и текущие файловые форматы без своей RPC, системы receipts или мигратора store. Остановка процессов, Docker volumes, manifest копии и требования конкретных файлов — прикладная эксплуатация примеров. Задание библиотеке понадобится только при воспроизводимом дефекте закрытия/восстановления публичного host либо подтверждённой потребности в общей согласованной точке snapshot; сначала проверить холодный путь, не переносить Docker и предметные схемы в common2.
