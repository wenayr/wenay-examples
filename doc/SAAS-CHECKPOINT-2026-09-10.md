Зафиксировано 10 сентября 2026, около 23:30 МСК. **Работа поставлена на паузу по просьбе пользователя. Продолжать только после его сообщения.** Новых агентов, тестов, сборок и развёртываний не запускать.

## Что библиотека действительно дала

| Механизм | Фактическая выгода |
| --- | --- |
| `schemaCommand`, `InferInput`, `buildInputValidate`, `inputJsonSchema` | Типы, проверка входа и документация выводятся из одной схемы. Формы строят проверку динамических вопросов без Zod; продуктовые HTTP API используют те же схемы для OpenAPI |
| Service definition, ролевые фасады и SC1 resources | Одни команды/контракты для клиентов, закрытые ресурсы файлов/AI/публикаций. Серверная проверка организации остаётся явной внутри операции |
| `createServiceClient`, Store/views/replay, leader/node host | Не написаны свои RPC, reconnect или репликация. Реально проверены два обслуживающих узла, отключение узла и восстановление состояния клиента |
| Receipts и долговечное состояние | Повтор команды не создаёт второй эффект в проверенных сценариях. Предметные semantic id и защита от устаревших версий дополняют библиотеку там, где одинаковая работа может прийти разными командами |
| `createAiRunHost`, checkpoint/recovery | Общая история выполнения, отмена, прогресс и явное восстановление. Приложения подставляют своих исполнителей вместо отдельного движка заданий для каждого экрана |
| `createReconciler`, `createResourceScope`, очереди/процессы/blob | Планирование, повторная сверка, ограничение исполнения и освобождение ресурсов опираются на готовые механизмы. Проверены webhook, расписания, probes и отдельный Python |
| React `useOwnedClient`, `useClientStore`, `useStoreReplayMirror`, `useServiceCommands`, `useAsyncAction` | Владение соединением, подписки, pending/error и смена ресурса не реализуются с нуля в каждом компоненте |
| `useReorderBoard`, `useReorder`, `Overlay`, `AgGridTable` | Готовые переносы карточек/блоков, клавиатура, фокус модальных окон и таблицы. Проверены реальные взаимодействия, а не только импорты |

Выигрыш подтверждается отсутствием отдельных транспортов и фактическим повторным использованием. **Процент экономии времени или строк не измерен**, поэтому утверждения «в десять раз быстрее» здесь нет.

## Использован ли функционал максимально

Основные инфраструктурные преимущества использованы широко. **Полный аудит оптимальности не завершён; утверждать «всё применено максимально» нельзя.** Использование каждого экспорта само по себе не является целью.

Есть конкретные места для следующей проверки:

1. В helpdesk сообщения сейчас входят в домен обращения и обслуживаются новым ресурсом страниц. В библиотеке существует `createConversationHost`, уже используемый старым чатом органайзера. Нужно сравнить композиции и либо переиспользовать его без второго журнала/двойной записи, либо документировать, почему транзакционная связь обращения и сообщения полезнее. До этого H02 нельзя считать окончательно оптимизированным по повторному использованию чата.
2. Обработка документов построена вокруг `createAiRunHost`; доступен и `createFileJobHost`. Общий AI runtime дал отмену/восстановление, но выбор относительно специализированного файлового runtime требует отдельного короткого сравнения, а не механического переписывания.
3. `useStoreSelect`/точечные подписки react2 применены не системно. Большие представления местами читаются целиком. Сначала измерить лишние перерисовки, затем заменить широкие подписки там, где это даёт эффект.
4. Некоторая ручная UI-обвязка уже оказалась лишней: окна CRM заменены на публичный Overlay. Аналогичный короткий аудит остальных модальных окон и async-resource компонентов ещё полезен.

## Подтверждённые замечания библиотекам

Открыты **три воспроизведённые задачи common2**, а не список произвольных пожеланий:

- [AI-POLICY-INVALIDATION](library-tasks/AI-POLICY-INVALIDATION.md): ранее открытый AI fragment может при новом чтении отдать результат после внешнего изменения policy. Нужен поддерживаемый способ актуализировать разрешённые проекции. В примерах приватный текст читается отдельно с текущим ACL и версией источника.
- [AI-RESOURCE-LIFECYCLE](library-tasks/AI-RESOURCE-LIFECYCLE.md): позднее завершение replay при отзыве SC1 может дать необработанное исключение специализированного AI-клиента. Временная проверенная композиция использует публичное state replay с обработкой ошибки и нового поколения ресурса.
- [STORE-NESTED-REPLACEMENT](library-tasks/STORE-NESTED-REPLACEMENT.md): сохранение proxy-элементов массива при замене родительского объекта вызывает рекурсию `snapshot()`. Обход в приложениях — отделение обычных данных исторических версий.

У каждой задачи есть точная версия, воспроизведение и критерии исправления. **Новых подтверждённых дефектов react2 сейчас нет.** Старый пакет исправлений библиотек уже принят, повторно открывать его не нужно. Общий указатель — [CURRENT-HANDOFF](library-tasks/CURRENT-HANDOFF.md).

Ошибка встроенного probe в Docker была **нашей проблемой композиции**: внутренний клиент пытался использовать внешний адрес gateway. Исправлено разделением общего цикла проверки и адаптеров: внешний worker использует service client, встроенный — публичный login/corridor/разрешённую проекцию. Это не отправлено библиотеке как доказанный дефект.

## Что можно упростить в нашем коде

Первые действия после возобновления стоит направить на сокращение повторений, а не на новый продукт:

- Свести одинаковую HTTP bearer-обвязку Support/Documents к одному небольшому копируемому исходнику с проверкой синхронности. HTTP/OpenAPI уже предоставляет библиотека; новый серверный framework не нужен.
- Проверить повторяющиеся блоки открытия SC1, состояния готовности и защиты запоздалого ответа. Выделять общий helper только после сравнения реальных различий. Если публичные hooks уже закрывают задачу, убрать собственную обвязку.
- Хранить один исходник действительно общего task-domain и React-адаптеров в каталоге примеров, а scaffold выдавать автономную копию. Сейчас физические копии удобны для самостоятельности, но повышают риск расхождений.
- Удалить неиспользуемые файлы, оставшиеся от исходных шаблонов, и проверить минимальность зависимостей. Внутри root-примеров такие остатки ещё встречаются; явный scaffold manifest уже уменьшает их попадание в новые проекты.
- Свести устаревающие списки статусов к одному паспорту примера. Документы местами отставали от реализации — это моя недоработка процесса, а не недостаток библиотеки.
- Объединять финальную проверку образа после логически законченной серии изменений. Частые повторные упаковки и широкая параллельная работа расходовали лишний бюджет. Агенты наследовали модель; дешёвый профиль явно не задавался. Измерения стоимости отдельно по агентам нет.

Рецептуры, capacity бронирования, правила согласования, FEFO, политика HTTP-целей, Docker volumes и роли конкретного продукта остаются в приложениях. Исправление общих lifecycle/Store-гарантий — обоснованная задача библиотек.

3. Закончить Approvals K08 и измерить фактическое повторное использование. Это пока код в работе, а не готовая девятая демонстрация.
4. Реализовать и проверить K04: холодная резервная копия всего набора данных, manifest/hashes, восстановление в новый пустой каталог, сохранение отзывов/receipts/файлов. Сейчас есть [подробный план](K04-BACKUP-RESTORE-PLAN.md), реализации ещё нет.
5. Завершить K06: каталог уже есть на3800, но карточки пока используют явно обозначенные схемы, не полный набор настоящих снимков. Актуализировать Folio/Signal и проверить витрину.
6. Отдельно решить оставшиеся границы: машинные credentials продуктовых API пока не тождественны ключам Metering; действие мониторинга в хостинг пока только переход в кабинет; настоящий OCR/качество модели, внешние платежи/OIDC и межмашинная сеть не подтверждены локальными тестовыми исполнителями.
7. По новым опубликованным исправлениям библиотек обновлять точные npm-пакеты и повторять соответствующие repro, а не всю тяжёлую приёмку без причины.

Горизонтальная проверка сейчас означает **один владелец записи + несколько обслуживающих узлов**, а у мониторинга — ещё независимых обработчиков. Это не доказательство нескольких одновременных писателей, автоматической HA базы или произвольной нагрузки. Замеры маленьких Docker-контейнеров не являются замерами пика всей машины.
