# Поддержка и документы: отдельный учёт потребления

Три приложения запускаются независимо. Поддержка и документы **по умолчанию не требуют metering**. Для подключённой организации успешная подготовка материала и извлечение одного документа расходуют по одной условной единице. Это демонстрационная политика потребления, не деньги или стоимость настоящей модели.

## Настройка

1. Запустить `apps/metering`: `npm ci`, `npm run build`, `npm start`, открыть http://127.0.0.1:3812.
2. Войти владельцем, создать ключ организации Northstar с правом `usage:write`. Секрет показывается один раз.
3. В окружение **сервера** поддержки или документов передать `METERING_CONNECTIONS_JSON` — JSON-карту локальных организаций. Например форма значения:

```json
{"northstar":{"url":"http://127.0.0.1:3812","account":"key:ID_ВЫДАННОГО_КЛЮЧА","secret":"ОДНОКРАТНО_ПОКАЗАННЫЙ_СЕКРЕТ"}}
```

Переменная не должна попасть в браузер, образ или коммит. `.env` автоматически не загружается. До восьми организаций задаются отдельно; при включённом учёте отсутствие настройки нужной организации блокирует её обработку. Имя организации в локальном продукте должно совпасть с подтверждённым `orgId` ключа metering. Это явная связь конфигурации; общей базы пользователей у приложений нет.

## Порядок операции

`createServiceClient` получает стандартную сессию по API-ключу. Защищённый ресурс `usage.control.identity` подтверждает организацию и полномочия. Затем команда `usageReserve` атомарно проверяет период, свободные единицы и параллельность. Только новый резерв разрешает запустить обработчик. После его ответа `usageSettle` фиксирует расход.

Стабильный `eventId` берётся из идентификатора запуска продукта; идентификатор команды резервирования новый для каждого отдельного намерения исполнения. Это важно: стандартная квитанция повтора команды возвращает первоначальный ответ, а предметный ledger при новой команде с тем же событием сообщает, что оно уже существует. Повторное выполнение обработчика в таком случае отклоняется.

Если операция прервалась после запуска, резерв помечается неопределённым. Потерянное подтверждение может оставить уже учтённый расход или ещё открытый резерв; его нужно сверить. Ключ/сеть могут помешать даже записи неопределённости — оставшийся резерв остаётся видимым владельцу. Автоматическое освобождение денег/единиц после неизвестного исхода не выполняется. Перезапуск AI runtime не запускает прежний внешний вызов повторно.

Это не распределённая транзакция между результатом продукта и журналом потребления и не обещание exactly-once внешнему провайдеру. Резервирование и подтверждение принадлежат authority metering; результат и его версия — authority соответствующего продукта. Данные обращения, статьи и строки документа в metering не передаются, только идентификатор ссылки, метрика и целое количество единиц.

## Повторяемый код и проверка

Два продукта используют одинаковые небольшие `backend/metered-execution.ts` и `metering-contract.ts`. Это прикладная копируемая интеграция, не новый SDK или отдельная библиотека. Исходная таблица входов `apps/metering/backend/client-contract.ts` используется самим сервером в `schemaCommand`. Тест проверяет совпадение копий; нет второй системы схем или транспорта.

Из `apps/metering`: `npm run test:integration`. Нужны установленные зависимости поддержки и документов. Проверка поднимает три реальных локальных сервиса: подготовка материала по источникам и настоящий CSV дают два расхода в одном ledger; повтор не вызывает обработчик, неправильная организация отклоняется до работы, неизвестный исход виден, отозванный ключ блокирует потребителя. Отдельный `npm test` проверяет authority + два обслуживающих процесса, гонку за последнюю квоту и рестарт.

Ограничения: единая запись metering, ограниченный локальный журнал, расходы заданы целыми тестовыми единицами. Отдельные внешние биллинговые платформы, реальный платёжный sandbox и промышленная межрегиональная топология этой проверкой не подтверждаются.
