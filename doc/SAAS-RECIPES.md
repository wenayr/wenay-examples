# Самостоятельные SaaS-копии и задания для ИИ

Этот каталог нужен для быстрого запуска следующего продукта на `wenay-common2` и `wenay-react2`. Копия приложения остаётся самостоятельным проектом: отдельный каталог, npm lockfile, исходники, правила и данные. Общий сервис регистрации проектов или обязательный SDK для всех примеров не создаётся.

## 1. Создать основу нового проекта

Из корня `wenay-examples`:

```text
node scripts/create-saas-example.mjs support work/client-care --name client-care
node scripts/create-saas-example.mjs documents work/document-desk --name document-desk
node scripts/create-saas-example.mjs metering work/usage-console --name usage-console
node scripts/create-saas-example.mjs crm work/sales-desk --name sales-desk
node scripts/create-saas-example.mjs booking work/rental-desk --name rental-desk
node scripts/create-saas-example.mjs forms work/feedback-desk --name feedback-desk
node scripts/create-saas-example.mjs monitoring work/uptime-desk --name uptime-desk
node scripts/create-saas-example.mjs approvals work/request-desk --name request-desk
```

Назначение — отсутствующий или существующий **пустой** каталог. Путь можно указать абсолютный, например отдельный каталог в `WebstormProjects`. Параметр `--name` необязателен: по умолчанию используется имя конечного каталога в нижнем регистре.

Скрипт переносит явный список исходников и проверяет их локальные импорты, исполняемые файлы и npm scripts до записи. Не переносит `node_modules`, `public`, пользовательские каталоги данных, настоящие `.env`, ключи, произвольные JSON, временные каталоги и неизвестные новые файлы. `.env.example` разрешён явно. Символические ссылки и Windows junction на копируемом пути или пути назначения отклоняются. Файлы создаются исключительно через `wx`: существующие данные не перезаписываются.

Имена обновляются согласованно в `package.json` и двух корневых полях `package-lock.json`; версии зависимостей сохраняются. Исходные идентификаторы сервиса, store и маршрутов намеренно не переименовываются автоматически. Если две копии будут работать в одной сети сервисов, задайте им отдельные идентификаторы и credentials до объединения.

Копируется небольшой `shared/react` текущего приложения: адаптеры сессии, представления, команд, async actions и replay. Это исходники данной копии, а не новая инфраструктурная библиотека. Они продолжают использовать публичные механизмы common2/react2.

Скрипт не устанавливает зависимости, не запускает процессы, не создаёт git-репозиторий, не публикует приложение и не переносит секреты автоматически. При ошибке записи после начала копирования возможен частичный каталог; он не удаляется скриптом, чтобы не затронуть файлы другого процесса.

## 2. Проверить чистую копию

Выполнять последовательно из корня репозитория:

```text
npm ci --prefix work/client-care --no-audit --no-fund
npm run typecheck --prefix work/client-care
npm test --prefix work/client-care
npm run build --prefix work/client-care
npm start --prefix work/client-care
```

Так проверяется любая копия: подставьте её каталог вместо `work/client-care`. Не запускать полные тестовые наборы и Docker параллельно на машине с ограниченным запасом памяти.

Копия наследует порт своего донора: support 3810, documents 3811, metering 3812, crm 3813, booking 3814, forms 3815, monitoring 3816, approvals 3818. Если исходное приложение уже работает, задайте копии другой порт переменной `SERVICE_PORT` при запуске и в `frontend/vite.config.ts` для разработки. Переменные `.env` не читаются автоматически: передавайте окружение процессу либо явно используйте Node `--env-file`.

Прежние результаты проверок чистых копий (10 сентября 2026) — в [хронологии](changes/handoff-2026-09-10.md#проверки-чистых-копий).

Для Python-проверки документов задаётся `DOCUMENT_PYTHON` с действительным путём к Python 3. Отсутствие этой проверки должно быть явно отражено в отчёте; Node-парсинг не считается доказательством Python-ветки. Поддержка дополнительно имеет локальную OIDC-проверку:

```text
node --import tsx backend/oidc-check.ts
```

Последняя команда запускается из каталога копии поддержки. Она использует локальный protocol fixture, не внешний аккаунт.

В репозитории проверка самого копировщика:

```text
node scripts/scaffold-check.mjs
```

Она проходит по всем шаблонам копировщика и проверяет неперенос секретных тестовых маркеров, данных, сборки и зависимостей, запрет перезаписи, пересечения с источником, junction/symlink, выходящих за приложение и пропущенных импортов. Для metering дополнительно проверяет сохранение основного `npm test` и исключение межпроектного `test:integration`; для booking — наличие Temporal и исходников расписания/помощника/сети. Чистые `npm ci/typecheck/build` — отдельная проверка: успешный файловый тест её не заменяет.

## 3. Карта точек расширения

| Потребность | Поддержка | Документы |
| --- | --- | --- |
| Собрать приложение | `backend/runtime.ts` → `createSupportRuntime` | `backend/runtime.ts` → `createDocumentRuntime` |
| Команды и ограничения | `backend/domain.ts` → `createSupportDomain`, `authorizeOrganization` | `backend/domain.ts` → `createDocumentDomain`, `organizationAccess`, `documentAccess` |
| Ролевое представление | `workspaceView`, тип `SupportWorkspace` | `documentWorkspace`, тип `DocumentWorkspace` |
| Внешний исполнитель | `assistant-resource.ts` → `DraftProvider.draft` | `processing-resource.ts` → `DocumentProcessor.extract` |
| Файлы | `createSupportFiles`, ресурс `files`, `control.upload/download` | Ресурс `processor`, `control.upload/download/detail/export` |
| Жизненный цикл задач | `createSupportAssistant`, ресурс `assistant` с `ai` и проверенным чтением результата | `createDocumentProcessing`, ресурс `processor` с `ai` и системными `processing*` командами |
| React | `frontend/main.tsx`, `inbox.tsx`, `workspace.tsx`, `assistant.tsx` | `frontend/main.tsx`, `studio.tsx` |
| Вход | `createOidc` + системный `identityProvision`, описание `OIDC.md` | Пока демонстрационные аккаунты примера |

Типы читать из фактических экспортов установленной копии. Не строить параллельный контракт «по памяти» и не импортировать исходники соседнего приложения.

## 4. Готовые задания для ИИ: поддержка

### Рецепт S-A: вертикальный продукт из поддержки

```text
Работаем в самостоятельной копии support. Прочитай AGENTS.md, doc/CODE-RULES.md,
README.md, backend/runtime.ts, backend/domain.ts и frontend/inbox.tsx.

Преврати пример в клиентскую поддержку небольшой дизайн-студии. Сохрани
организации, роли owner/lead/agent/customer, приватные заметки и текущую
авторизацию. Добавь категории «Доступ», «Счёт», «Проект», выбираемые при
создании обращения, фильтр категории и назначение ответственного по явному
правилу организации. Владелец должен менять это правило отдельной командой.

Используй createSupportDomain/schemaCommand и workspaceView. Проверяй права
и актуальную ревизию на сервере. Типы интерфейса выводи из реализации.
Нельзя добавлять Zod, второй WebSocket, собственный reconnect или соседние
импорты из wenay-examples. Данные нового поля должны переживать рестарт;
старые записи без категории должны оставаться читаемыми.

Сначала опиши конкретные изменения и критерии. Затем реализуй полный поток
клиент → специалист → руководитель, включая ошибки и пустые состояния.
Проверь отказ чужой организации, конкурирующую правку настройки и отзыв роли.
Запусти typecheck, релевантные доменные проверки, сетевую проверку и build.
В конце перечисли добавленный предметный код, повторно использованные API
библиотек и только воспроизведённые библиотечные недостатки.
```

Готовность: категорию видно клиенту и сотрудникам, автоматическое назначение действительно изменяет обращение, правило ограничено организацией, прежние записи не ломаются. Новое правило назначения — код продукта, не заявка в common2.

### Рецепт S-B: настоящий помощник по источникам

```text
Работаем в копии support. Прочитай createSupportAssistant, DraftProvider,
backend/ai-checkpoint.ts, frontend/assistant.tsx и текущие проверки ресурсов.

Подключи заменяемый серверный DraftProvider к выбранному владельцем проекта
ИИ-провайдеру. До появления конфигурации сохраняй честно обозначенный
тестовый исполнитель. Не делай платных запросов автоматически и не запрашивай
ключ в чате. Используй серверную переменную окружения и документируй её имя.

Провайдер получает только разрешённый вопрос, опубликованные источники
текущей организации и AbortSignal. Текст статьи — данные, не инструкции
на получение дополнительных прав. Ответ и источники должны пройти существующую
проверку актуальных прав/версий перед чтением и вставкой в черновик.
Отправка клиенту остаётся отдельным действием сотрудника.

Проверь отмену, тайм-аут, отсутствие источников, смену версии статьи,
отзыв роли во время ответа и рестарт с неизвестным исходом операции.
Не обещай exactly-once вызов внешнего провайдера и не воспроизводи такой
запрос автоматически после неопределённого результата.

Проверь публичные API установленного common2/react2 прежде чем писать
обёртку. Для подтверждённого общего дефекта подготовь минимальное
воспроизведение с версиями; провайдерские промпты и бизнес-правила оставь здесь.
```

Готовность: есть проверяемый серверный адаптер, воспроизводимые проверки ошибок без оплаты, документирован отдельный opt-in live smoke. Прохождение тестового исполнителя не выдаётся за качество ответа модели.

### Рецепт S-C: внешний вход без демонстрационных аккаунтов

```text
Работаем в копии support. Прочитай OIDC.md, createOidc, identityProvision
в createSupportRuntime и frontend/oidc-login.tsx.

Подготовь запуск с SERVICE_DEMO=0 и новым каталогом данных. Провайдер
настраивается исключительно серверным окружением. Не создавай собственный
OAuth/JWT протокол и не связывай аккаунты по совпадению email или имени.
Пара issuer+subject остаётся идентификатором внешней личности, а роли выдаются
только существующими командами организаций и приглашений.

Пройди локальный oidc-check и проверь onboarding: первый вход без организаций,
создание собственной организации, принятие приглашения и повторный вход
после отзыва роли. Без настроенного провайдера не заявляй live HTTPS-проверку.
Все /auth/oidc/* маршруты должны обслуживаться одним authority-процессом.
Документируй поведение после рестарта и отдельность выхода из приложения
от выхода из самого провайдера.
```

Готовность: новый аккаунт не получает чужие организации, не имеет рабочего локального пароля, а повторный вход не возвращает отозванный доступ.

## 5. Готовые задания для ИИ: документы

### Рецепт D-A: студия проверки реестров

```text
Работаем в самостоятельной копии documents. Прочитай AGENTS.md,
doc/CODE-RULES.md, createDocumentDomain, documentWorkspace,
createDocumentProcessing и frontend/studio.tsx.

Преврати пример в проверку реестров заявок. Пользователь загружает CSV,
видит извлечённую таблицу рядом с исходным документом, исправляет ячейки
с комментарием, передаёт проверяющему и получает утверждённый экспорт.
Добавь предметную проверку обязательных колонок и дубликатов номера заявки,
отображение проблем по строкам и запрет утверждения до их устранения.

Сохрани DocumentProcessor.extract, существующий AI-run жизненный цикл,
blob storage, системные processing* команды и revision/sourceVersion/attempt.
Не записывай результат фонового процесса прямо в состояние в обход фасада.
Утверждённая версия должна оставаться неизменной при последующей правке.

Проверь загрузчика, проверяющего и владельца в своей организации, чужую
организацию, конкурирующую правку, отмену, повтор, поздний результат,
повторное открытие и CSV-экспорт с потенциальными формулами.
Пройди typecheck, доменные и сетевые проверки, build. Отдельно укажи,
проверялся ли реальный Python через DOCUMENT_PYTHON.
```

Готовность: проверка данных действительно управляет возможностью утверждения, права и прошлое утверждение сохраняются, экспорт защищён от формул. Эти правила реестра остаются в продукте.

### Рецепт D-B: новый обработчик документов

```text
Работаем в копии documents. Прочитай DocumentProcessor, createDocumentProcessor,
createDocumentProcessing, backend/pdf-processor.mjs и backend/processor.py.

Добавь один новый конкретный тип обработки через DocumentProcessor.extract,
сохранив общий интерфейс загрузки, прогресса, проверки результата и экспорта.
Сначала зафиксируй поддерживаемый формат и его ограничения. Для OCR или
ИИ оставь серверный порт с явным opt-in; не устанавливай тяжёлую локальную
модель и не выполняй платные запросы без отдельного разрешения.

Используй createProcessResource для дочернего процесса и существующий
AbortSignal. Ограничь время, вход, выход и конкурентное число заданий.
Временный файл должен удаляться после успеха, отказа и отмены.
Проверяй результат через предметный validateTable, не добавляй параллельную
схемную систему. Обнови допустимые значения выбора обработчика там, где
они уже проверяются, и добавь UI-объяснение его возможностей.

Проверь настоящий небольшой вход, повреждённый вход, тайм-аут, завершение
процесса, два конкурентных документа и поздний результат отменённой попытки.
Не выдавай PDF text extraction за OCR или точное восстановление любой таблицы.
```

Готовность: обработчик выполняет настоящую работу в пределах лимитов, очищает ресурсы и использует тот же продуктовый поток. Нативный Python-клиент common2 не заявляется: Python в этом примере — дочерний исполнитель с узким протоколом ввода/вывода.

### Рецепт D-C: совместная работа и восстановление

```text
Работаем в копии documents. Прочитай backend/node.ts, backend/check.ts,
createDocumentRuntime и публичные service/host API установленной библиотеки.

Проверь продукт через один authority и два обслуживающих узла. Клиенты
действительно должны читать/получать обновления через разные узлы.
Пройди отзыв роли при активном просмотре, остановку узла, переподключение,
изменение документа и восстановление после рестарта authority.

Для файлов учитывай существующего владельца ресурса: обслуживающий узел
проксирует файл к authority, а не становится вторым независимым владельцем
того же локального каталога. Не подключай общий JSON-файл нескольким писателям.
Не обещай автоматическую миграцию владельца или exactly-once обработку,
если это не подтверждено реальной топологией и проверками.

Измерь длительность и память небольшого сценария, сохрани фактические значения.
Локально используй последовательно лёгкие процессы, общий запас до 3 ГиБ.
Новые общие библиотечные потребности оформляй с минимальным воспроизведением,
а топологию и правила конкретного продукта — в документации приложения.
```

Готовность: описано, какие узлы реально обслуживали клиентов, что сохранилось после отключения и что остаётся ограничением текущего владельца файлов.

## 6. Как оценивать пользу каталога

На каждой чистой копии записывать: выбранный исходный пример, число изменённых предметных файлов, время до первого рабочего пользовательского сценария, использованные фасады библиотек, пройденные роли и восстановление, добавленные адаптеры и их реальных потребителей.

Это материал для будущего уменьшения копируемого кода. Повторение небольшой адаптации в двух продуктах — повод проверить готовый публичный механизм и лишь затем предложить минимальное библиотечное дополнение. Категории обращений, формулы проверки реестров, тарифы и маршруты конкретного продукта не становятся задачами библиотеки автоматически.

Список поддерживаемых шаблонов задаёт сам копировщик (`node scripts/create-saas-example.mjs` без аргументов его печатает). Наличие шаблона не означает завершение всех продуктов и задач стратегического плана.

## 7. Самостоятельный учёт API

Manifest metering переносит ровно следующие группы:

| Группа | Файлы |
| --- | --- |
| Предметная модель | `backend/domain.ts`, `model.ts`, `client-contract.ts`, `billing-domain.ts`, `billing-model.ts`, `identity.ts` |
| Композиция и ресурсы | `backend/service.ts`, `runtime.ts`, `server.ts`, `node.ts`, `process-resource.ts`, `webhook-resource.ts`, `provider-http.ts` |
| Самостоятельные проверки | `backend/domain-check.ts`, `webhook-check.ts`, `check.ts` |
| Интерфейс | `frontend/main.tsx`, `contracts.ts`, `keys.tsx`, `playground.tsx`, `ledger.tsx`, `webhooks.tsx`, `style.css`, `index.html`, `env.d.ts`, `vite.config.ts` |
| Прикладные React-адаптеры | `shared/react/command-action.ts`, `replay-view.ts`, `service-action.ts`, `service-session.ts`, `service-view.tsx` |
| Конфигурация и правила | `package.json`, `package-lock.json`, `tsconfig.json`, `Dockerfile`, `.dockerignore`, `.env.example`, README, сгенерированные `.gitignore`/`AGENTS.md` и `doc/CODE-RULES.md` |

`backend/integration-check.ts` и `npm run test:integration` связывают соседние приложения исходного репозитория и не переносятся. Основной `npm test` сохранён: домен, локальный подписанный provider/webhook протокол, authority + два serving nodes. Копия не требует поддержки, документов, Python, PDF или OIDC. Обязательные React-адаптеры остаются принадлежащими приложению исходниками.
