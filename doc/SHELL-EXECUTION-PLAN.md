# wenay-shell: подробный план исполнения

27 сентября 2026. Версия плана 1.0. Автор общей композиции и интегратор — root.
Исполнители — GPT-6 Sol high; одновременно root и не более трёх подагентов.
Сначала фиксируется этот план, затем запускается первая волна.

Это уточнение [общего плана](APP-SHELL-PLAN.md). Главная новая граница:
**продукт собирается из разделов, подразделов, представлений и рабочих блоков**.
Чат, видео, CAD и документы — разные возможности такого продукта. Чат может быть
главным экраном выбранной сборки или помощником рядом с другим главным разделом.
Прежнее требование удобного чата сохраняется, но ядро не зависит от наличия чата.

Правила реализации — [CODE-RULES](CODE-RULES.md).
Границы контрактов — [SHELL-CONTRACTS](SHELL-CONTRACTS.md).
Постановки исполнителям — [SHELL-AGENT-BRIEFS](SHELL-AGENT-BRIEFS.md).
Статусы здесь не дублируются: после запуска единственный журнал выполнения —
`wenay-shell/docs/BOARD.md`. Задача без принятого результата в журнале не выполнена.

## 1. Результат и границы поставок

Новый самостоятельный репозиторий: `C:/Users/wenay/WebstormProjects/wenay-shell`.
Первая ветка: `codex/shell-foundation`. Существующие examples и Dynamic не переделываются.
Существующий Chat integration используется как источник проверяемых решений, а не целиком
копируется вместе с демо-пользователями, фиксированными workspace и ответом-заглушкой.

Целевые поставки: backend, браузер, CLI, установленные Android/iOS приложения;
настольное приложение — дополнительная поставка по предыдущему поручению.
Они используют общие аккаунты, проекты, документы, задания и историю.
CLI не является автоматически удалённым исполнителем; daemon/agent имеет отдельные права.

| Контрольная точка | Действительный результат | Что её не заменяет |
| --- | --- | --- |
| F0 | Публичные библиотеки проверены исполняемыми пробами; композиция разделов работает без чата; web imports собираются | Чтение README, наличие типов, картинки интерфейса |
| F1 | Backend + web + CLI: серверный проект, разговор/документ, история, reconnect и смена аккаунта | Несвязанные локальные состояния клиентов |
| F2 | Два разных модуля, подразделы/блоки и starter; третий модуль добавлен без предметных изменений ядра | Меню с захардкоженными `if cad/video` и пустые страницы |
| F3-CAD | Настоящий CAD-документ, сохранение/восстановление, единые ручные/машинные команды и графическая поверхность | Картинка чертежа вместо исходника или две разные сцены |
| F3-VIDEO | Проект видео с исходником, параметрами монтажа и проверенным выходным видеофайлом | Прогресс без исполнителя или сообщение «видео готово» |

| F5 | Реальный AI provider, tools, cancel, receipts, политика доступа и учёт расхода | Тестовый provider или только законченный текстовый ответ |
| F6-P / F6-A | Воспроизводимая базовая / AI-поставка с обновлением и восстановлением | Запуск на машине разработчика без сохранённых данных |

F3-CAD и F3-VIDEO — независимые ветви. Базовая поставка может сначала принять один
сложный модуль вместе с простым текстовым; в релизной матрице явно указывается состав.
Неготовый модуль не показывается как работающая функция. AI и удалённое исполнение
не являются скрытыми условиями ручной работы, навигации и поставки plain-каркаса.

## 2. Решения, обязательные для всех исполнителей

1. `wenay-common2` даёт публичные service/RPC, state/replay, conversation, AI run и другие
   проверенные механизмы. `wenay-react2` используется в React-представлениях.
   Не создавать второй транспорт, общий журнал, reconnect, retry engine или схемы Zod.
2. Начальный точный baseline: common2 **3.1.1**, react2 **5.0.0**.
   `npm view` 27 сентября подтвердил эти версии; Node **24.18.0** доступен.
   Установка из registry с lock; ни `npm link`, ни импорт соседних `lib/`.
3. Проект владеет документами/артефактами независимо от чата. Представления ссылаются
   на ID и revision. Пользователь и ИИ вызывают одну предметную команду.
4. Профиль приложения определяет включённые модули, разделы, их порядок, стартовую
   страницу и расположение помощника. Смена профиля не мигрирует предметные данные.
5. Раздел — навигационная группа; подраздел — часть её маршрута; представление — экран;
   блок — часть экрана. Их нельзя смешивать с persisted document или серверным job.
6. Первый registry содержит доверенные модули выбранной сборки. Runtime-магазин чужого
   кода, произвольное выполнение JS и универсальный конструктор окон в F0/F1 не входят.
7. Root владеет общими контрактами, package/lock, конфигурацией workspace, переносом
   кода между областями, интеграционными командами и коммитами.
8. Клиентские данные/permissions не являются авторитетом доступа. Backend проверяет
   identity/workspace/project/document и текущие права, также при retry и после IO.
9. Базовый сервер имеет одного владельца записи. Несколько клиентов не означают
   несколько писателей или принятую распределённую БД.
10. Поле «готово» выставляется после проверок потребителя, а не по уверенности автора.
    Build, unit, runtime, browser, installed-device и production имеют разные статусы.

## 3. Карта репозитория и владельцы

Каталоги появляются по мере реальных потребителей. Это карта ответственности,
а не требование создать все пустые пакеты на первом шаге.

| Область нового репозитория | Владелец роли | Содержание |
| --- | --- | --- |
| root package/lock, tsconfig, scripts, AGENTS, docs/BOARD | R: root | Публикуемые зависимости, сборка, проверочные команды, контракты, принятие |
| packages/composition | M: композиция | Registry модулей/разделов/представлений, профиль приложения, разрешение маршрута |
| packages/server, apps/server | B: backend | Identity, workspace/project, module instances, document/artifact/command resources |
| packages/client | C: клиент | Headless ownership, scope switch, native clients, чтение/команды/состояния |
| packages/ui, apps/web | U: интерфейс | Навигация, layouts, диалог, slots/blocks, lazy imports и доступность |
| modules/text | M | Первый небольшой реальный документ, пригодный для проверки границ |
| modules/cad | D: CAD | Scoped bridge и editor integration, без изменения соседнего Dynamic |
| modules/video | V: видео | Материалы, timeline/параметры, renderer job, результат-файл |
| apps/cli | C | Команды пользователя, JSON/stdout/stderr, exit codes, watch/cancel |
| apps/mobile, apps/desktop | P: платформы | Пакетирование, credential/file/lifecycle adapters, установки |
| apps/agent | A: исполнитель | Отдельный daemon с project grant и ограниченными операциями |
| tooling/module-starter | X: удобство разработки | Создание модуля/подраздела и проверка совместимости |
| tests/integration, tests/acceptance | Q: проверка | Сценарии через публичные границы, не зеркала внутренних функций |

Роли обозначают ответственность, а не постоянно запущенные 12 агентов.
На каждой волне root назначает до трёх конкретных исполнителей на непересекающиеся области.
Изменение общей границы сначала оформляется root как короткое решение с потребителями.

## 4. Каталог работ

Каждая строка — отдельное задание. Колонки задают предшественников, владельца,
ограниченный результат и достаточную приёмку. Подробные ограничения путей для текущей
волны добавляются в постановку; они могут сужать, но не расширять область без root.
`—` означает отсутствие технического предшественника, а не отсутствие правил репозитория.

## 6. Приёмка, артефакты и ограничения выполнения

Для каждого задания сохраняются ID, commit/source, точные package+lock, изменённые
пути, выполненные команды с exit code, реальные сценарии и отдельный список skipped.
Агент сначала пишет краткий прогресс в своей области, затем отдаёт root результат
и точную команду проверки. Root не принимает результат только по финальному сообщению.

Проверять цепочку: библиотечный ресурс → предметный фасад → общий клиент → UI/CLI →
многоклиентский сценарий → установленная платформа → поставка. Проверка вышестоящего
слоя не заменяет проверку границы, на которой обнаружено несоответствие.

Тяжёлые build/runtime/device/Docker проверки выполняются последовательно root либо
одним назначенным исполнителем. Цель дополнительной RAM 1–2 GiB, максимум 3 GiB.
Один shared package/lock редактирует root. Изолированное новое test data принадлежит
задаче; чужие процессы, данные, Docker volumes и соседние checkout не очищаются.

Глобальные статусы задач: `planned`, `active`, `review`, `accepted`, `blocked-library`,
`blocked-environment`, `failed`. `accepted` требует критериев строки и root review.
Блокер одной ветви не останавливает независимые готовые задачи.

Важные негативные сценарии объединяются по границе, не копируются сотнями по экранам:

- server/account/workspace/project/document switch при медленном ответе;
- повтор прежнего requestId после изменения payload/прав;
- close UI против cancel durable job;
- отключение/обновление модуля при открытом блоке и выполняющемся задании;
- stale revision, неизвестная версия формата, отсутствующий pack;
- reconnect/restart/lost response и неизвестный исход внешнего действия;
- два настоящих клиента, отдельные accounts и сохранённый файл/документ;
- native mobile suspend и внешняя HTTPS среда — самостоятельные проверки.

Основные риски уже известны: AI/conversation lifecycle/receipt ACL в common2 3.1.1,
private CAD package и различие library versions, headless/DOM/native несовместимость,
CAD in-memory receipts и отдельные browser/host documents, отсутствие принятого video
encoder/provider. Их обходы не превращаются в новый общий framework внутри приложения.
