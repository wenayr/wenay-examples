## Библиотеки и установка

- **[wenay-common2](https://www.npmjs.com/package/wenay-common2)** — серверные и клиентские механизмы: RPC, фасады, реактивное состояние, replay, репликация и инструменты построения сервисов.
- **[wenay-react2](https://www.npmjs.com/package/wenay-react2)** — React-интерфейсы: подписки на состояние и replay, контроллеры, таблицы, окна, настройки и другие общие компоненты.

**Зависимости устанавливаем из npm registry. Соседние локальные репозитории, локальные сборки, `npm link` и локальные архивы пакетов не используем.** Примеры должны собираться у человека, у которого есть только этот репозиторий и доступ к npm.

При создании примера или плановом обновлении проверяем последние опубликованные версии и устанавливаем их в каталоге приложения:

```sh
npm view wenay-common2 version
npm view wenay-react2 version
npm install --save-exact wenay-common2@latest wenay-react2@latest
```

После обновления проверяем совместимость, сборку и рабочие сценарии. Сохраняем точные версии в `package.json` и коммитим `package-lock.json`. Для повторного запуска и развёртывания используем `npm ci`: актуальность проверяется при обновлении, воспроизводимость обеспечивается зафиксированными зависимостями.

Используем только публичные экспорты и документированные возможности установленных пакетов. Если необходимой функции ещё нет в npm-релизе, фиксируем ограничение и потребность в изменении библиотеки. Подключение неопубликованной локальной реализации не считается завершением примера.

## Какие примеры здесь нужны

Основной формат — небольшое, но целостное приложение, которое можно взять за основу нового проекта. Предметная область помогает показать работу системы: пиццерия, аренда жилья или другой сервис могут быть удобным сценарием, но каталог ими не ограничивается.

Особое внимание уделяем типовым SaaS-задачам:

- аренда хостинга, создание и управление экземплярами приложений;
- развёртывание, обновления, наблюдение за состоянием и откат;
- горизонтальное масштабирование: добавление узлов или экземпляров, распределение нагрузки и работа при отключении узла;
- вертикальное масштабирование: изменение доступных ресурсов экземпляра, применение настроек и проверка результата;
- выделение публичного API из фасада сервиса с явным выбором доступных операций;
- описание API через OpenAPI и доступная Swagger UI для изучения и выполнения запросов;
- роли, разрешения, изоляция клиентов, сохранение данных и живые обновления интерфейса.

Это направления развития, а не заявление о том, что все перечисленные сценарии уже реализованы. Каждый готовый пример описывает собственные возможности и проверенные границы.

## Профессионально, с минимальным объёмом

Мы стремимся к профессиональному качеству структуры и пользовательского сценария при небольшом объёме приложения. Допустимы минимум контента, несколько демонстрационных записей и узкий набор функций. Пустые состояния должны быть понятными и объяснять следующий шаг.

Пользователь должен быстро пройти законченный путь: создать сервис, открыть его, изменить настройку, добавить экземпляр, увидеть состояние операции и проверить результат. В примере API — выбрать публичные операции фасада, получить доступный API, открыть Swagger UI и выполнить запрос. Конкретные шаги зависят от задачи, но должны быть видны и в интерфейсе, и в инструкции.

За каждым действием стоит настоящий результат: запущенный процесс, сохранённая настройка, изменённое число экземпляров или реально доступный маршрут API. Кнопка масштабирования не должна только менять цифру на экране. Если действие требует внешней инфраструктуры, пример явно описывает её, способ подключения и ограничения локального запуска.

Упрощаем объём продукта, сохраняя существенное поведение: серверную проверку разрешений, обработку ошибок, состояние выполнения, сохранение данных и освобождение ресурсов. Демонстрационные адаптеры обозначаем явно. Учебный пример сам по себе не означает готовность к публичной эксплуатации с реальными клиентами.

## Подход к реализации

Опираемся на распространённые способы реализации SaaS-продуктов. При необходимости изучаем существующие решения, официальную документацию и примеры в интернете; полезные источники и принятые решения указываем в документации приложения. Наша задача — показать, как привычный сценарий становится проще с нашими библиотеками.

Перед добавлением механизма проверяем, нет ли его уже в публичном API библиотек. Используем готовые возможности и небольшие адаптеры вокруг них. Не создаём внутри примеров параллельные реализации транспорта, reconnect, replay или другой инфраструктуры, которую уже предоставляет библиотека.

Предметные правила, продуктовые сценарии и политика доступа принадлежат приложению. Универсальные механизмы, полезные нескольким проектам, становятся кандидатами на развитие библиотек. Не создаём пустые приложения ради структуры каталога и не строим общий фреймворк до появления конкретной потребности.

## Как примеры развивают библиотеки

Каждый пример — практическая проверка удобства и полноты библиотек. По мере реализации фиксируем:

1. Какой пользовательский или эксплуатационный сценарий требуется выполнить.
2. Какие публичные API и версии пакетов используются.
3. Где обнаружено ограничение, неудобство или повторяющийся код.
4. Какое минимальное общее улучшение нужно и почему оно относится к библиотеке.
5. Как воспроизвести проблему и проверить результат после выпуска исправления.

Изменения библиотек выпускаются в их собственных репозиториях. Здесь обновляем npm-зависимости после публикации и повторно проверяем сценарий. Ограничения, временные решения и результаты проверок документируем; изменения приложений отражаем в changelog.

## Организация репозитория

Каждый пример находится в `apps/<name>` и запускается самостоятельно. Приложение содержит frontend и backend, необходимые настройки, проверки и инструкцию запуска. Общие ресурсы допустимы, если не мешают самостоятельному использованию примеров.

Документация приложения должна объяснять назначение, последовательность действий, зависимости от инфраструктуры, хранение данных, способ развёртывания и ограничения. Масштабируемые сценарии дополнительно описывают топологию, владельца состояния и поведение при отказах. Возможность считается показанной после проверки реального результата, а не только успешной сборки.
