# Принятие common2 2.21.0

10 сентября 2026. В пиццерии/органайзере и хостинге установлены точные npm-зависимости common2 **2.21.0**, react2 **3.4.0**, обновлены оба lock-файла. **H1/H2 приняты и закрыты.**

## Что заменено

Docker- и LXD-агенты используют публичные `createReconciler` и `createResourceScope`. Проверена и применена миграция из опубликованного пакета; приватных импортов и подмен npm нет. Из двух фабрик удалены собственные busy/dirty/running, хранение таймеров, ручная отписка и согласование нескольких close. Суммарно фабрики сократились на 50 строк.

Исполнитель читает `Store.snapshot()` перед проходом и объединяет уведомления во время IO. Docker сохраняет причины повтора по операции/маршруту, LXD — общую причину assignments; задержка 5 секунд остаётся политикой приложения. Свежий проход снимает прежние таймеры и заново назначает только необходимые. Проход, назначивший повтор, откладывает накопленные уведомления до повтора; новое уведомление после завершения может запустить сверку раньше. Это документированный контракт, а не очередь всех уведомлений.

Область владения охватывает получение и запись lock, создание клиента, gateway и исполнителя. Ошибка старта освобождает приобретённое, сохраняя исходную причину. Остановка IO и исполнителя объединена в явную параллельную группу, чтобы закрытие соединения разблокировало ожидающий RPC. Lock освобождается после завершения группы. В агентах нет искусственного таймаута, выдаваемого за завершённое IO.

Назначения, immutable releases, идентичность внешних операций, ограничения ресурсов, проверка текущего состояния перед очисткой и правила готовности остались в хостинге. Локальный исполнитель не обещает distributed fencing или exactly-once внешнего провайдера.

## Проверки

- Hosting: полный `npm test` существующих ролей, Docker/LXD protocol fixtures, RPC агента, gateway и WebSocket — прошёл; `test:library-audit`, `typecheck` и сборка — прошли.
- Новый `test:orchestration` включён в обычный `npm test`: 100 уведомлений до и 100 во время IO, один свежий следующий проход без параллельного выполнения; повтор, удаление ненужного таймера, observable error, отписка, общий close, отмена активного прохода с ожиданием его фактического завершения.
- H2: исходная ошибка запуска при ошибке disposer, продолжение обратной очистки, поздний ресурс после abort, отличие close deadline от settlement, параллельное освобождение IO перед lock.
- Обе настоящие фабрики агентов: HTTP 503 при чтении descriptor сохраняет причину и удаляет lock; повторный запуск снова доходит до descriptor, а не падает на оставшемся lock.
- Pizzeria: `typecheck`, полный `npm test` (сеть, роли, склад, органайзер, peer/SC1, доска, чат, A1 persistence и M1 regression), обе production-сборки — прошли. Платных запросов не было.
- Docker Engine 29.7.2: Node → Python → откат Node через common2 2.21.0; перезапуск агента, стабильный gateway, очистка предыдущих кандидатов, отказ readiness с сохранением рабочего Node — прошли.

Первый Docker-прогон завершился статусом failed на первом развёртывании. Прежний assertion не показывал detail, временные ресурсы были очищены, точная причина не установлена. Assertion теперь выводит detail. Следующий полный прогон прошёл без изменения агента или образов. Это наблюдение стенда, не доказанный дефект библиотеки; при повторении проверять detail перед выводами.

Каждый тестовый контейнер ограничен 64 МиБ/0.25 CPU. Отдельные замеры vmmemWSL дали 269 и 613 МиБ; это не непрерывное измерение пика всей системы. Тестовые контейнеры удалены, существующий пользовательский контейнер сохранён. Реальные VM/LXD/Kubernetes не запускались. Нового браузерного прогона и повторной сборки OCI-продуктов для этого релиза не заявляем; браузерный R4 принят на предыдущем этапе, UI-сборки не изменили содержимое.

## Текущий результат

Библиотека заменила повторённую оркестрацию в двух разных исполнителях, сохранив их предметные различия. В [текущем пакете обеим библиотекам](../library-tasks/CURRENT-HANDOFF.md) открытых обоснованных заданий больше нет. Это завершение накопленного пакета, не полный аудит всех возможностей.

Следующие новые потребности следует получать из реальной межмашинной работы, проверки устройств и сценария нескольких исполнителей одного пула. До конкретного воспроизведения не заказывать библиотеке универсальный планировщик или распределённое владение операциями.
