# S3–S8: экран, общение, голос и размещение своих приложений

**Обновление:** [common2 2.20.0 принят](common2-2.20.0.md), H3/M1/A1 закрыты. Размещённые приложения теперь проверены через RPC и в браузере; AI checkpoint/recovery подключён. Ниже — отчёт исходного этапа на 2.19.0, его библиотечные блокеры больше не актуальны.

10 сентября 2026. Опубликованные `wenay-common2@2.19.0` и `wenay-react2@3.3.0`, без локальных подмен, Zod, отдельного RPC или собственного reconnect. Пользователь выбрал **без платных запросов**. Вся независимая от выявленных блокеров реализация выполнена; полную исходную приёмку нельзя считать закрытой до H3/A1 и ручной проверки устройств.

## Границы приложения и библиотеки

Новые файлы основного поведения в `apps/pizzeria/organizer`: `screen-resource.ts`/`screen.tsx`, `chat-journal.ts`/`chat-resource.ts`/`chat.tsx`, `assistant-resource.ts`/`assistant.tsx`, `voice-record.tsx`, `proposal-domain.ts`. Две service-фабрики подключают одни модули к своим ролям и проекциям. `wenay-react2` используется непосредственно: `useOwnedClient`, `useClientStore`, `useMediaSource`, `useAiRunClient`, существующие board/action hooks.

SC1 предоставляет срок жизни и защиту ресурсного фасада. Conversation host владеет сообщениями, фактами и receipts; дисковый адаптер записывает публичные события с fsync до подтверждения. Факты описывают состав разговора, привязку задачи, исправления, прочитанное и готовые предложения. Текущие участники видят историю целиком; удалённые теряют последующий доступ. Исходные сообщения остаются аудитом, «удалить» создаёт видимую надпись вместо прежнего содержимого. Это не физическое стирание истории/файлов.

Файл читается только через авторизованный RPC и только при наличии ссылки в доступном неудалённом сообщении. При закрытии UI освобождаются Blob URL. Уже законно скачанный файл невозможно отозвать у пользователя. Один каталог данных принадлежит одному authority; multi-writer журнал не заявлен.

Предложение не имеет специальных привилегий. Пользователь правит сроки/исполнителей и подтверждает весь набор через `workApplyProposal`. Сначала проверяются все элементы и текущие права, затем создаются задачи. Повтор того же предложения сохраняет прежние ID, а изменение уже применённого набора отклоняется. Архив обычного сервиса сохраняет задачи и индекс принятых предложений.

## Экран и голос

Экран: не более 1280×720, до 5 JPEG кадров/с, размер пакета до 180000 байт, один RPC в полёте и пропуск промежуточных кадров. Epoch исключает старые кадры, inactivity 12 секунд освобождает источник. Переподключение не начинает новый захват автоматически. Показ без звука, хранения записи и обещания высокой частоты для кино/игр.

`getDisplayMedia` вызывается только кнопкой. Встроенный браузер открыл ожидание системного выбора; тест завершён перезагрузкой страницы, источник не выбран. Поэтому это не положительная приёмка настоящего экрана. Отдельный `test:media-browser` проверяет настоящую передачу/декодирование синтетического canvas через два клиента; после остановки источник и подключения закрываются. Требования явного выбора описаны в [MDN](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getDisplayMedia).

Голос: mono PCM16 WAV, до 12 секунд и 480000 байт PCM (при большей фактической частоте устройства лимит размера наступит раньше). Прослушивание перед отправкой, отдельная отправка и удаление черновика. Перед провайдером сервер проверяет WAV-заголовок, длину, формат и длительность. Файлы иных форматов можно хранить как вложения, но этот adapter их не транскрибирует.

## ИИ без оплаты

По умолчанию внешнего провайдера нет. `demo-tasks` делит вручную введённый текст на пункты; `demo-summary` показывает выдержку последних сообщений. Оба режима явно помечены тестовыми. Это проверка механизма работы, не оценка качества ИИ. «Распознать» без настройки возвращает понятную ошибку, сеть к ИИ не используется.

Заменяемый server-side `AssistantProvider` можно передать в service factory. Опциональный HTTP adapter включается только явной серверной переменной `AI_TRANSCRIBE_URL`; `AI_TRANSCRIBE_TOKEN` остаётся на сервере. Его контракт: POST `audio/wav`, необязательный Bearer, ответ JSON `{text: string}`. HTTPS либо localhost HTTP, timeout 60 секунд, ответ до 64 КБ/текст до 8000 знаков, без автоматического повтора. Это общий endpoint адаптера, не готовая совместимость с произвольным API провайдера. Сейчас переменные не настраивались и оплачиваемых запросов не было.

Один активный run на экземпляр, до 100 запусков в памяти. Отмена и отзыв доступа вызывают AbortController; после IO актуальность проверяется повторно. Уже сохранённый факт результата может остаться при отмене после точки записи, но задачи без подтверждения не создаются. Провайдер должен поддерживать abort; отсутствие ответа ограничивается timeout HTTP adapter.

Готовые результаты сохраняются в conversation journal. Незавершённые run/approval/input не восстанавливаются: публичному AiRunHost не хватает контракта A1. Пример не подделывает его внутренний Store и не повторяет потенциально оплаченный запрос после рестарта.

## Размещение и ресурсы

`apps/pizzeria/Dockerfile` содержит оба режима приложения, выбираемые `APP_MODE`; базовый Node 24 Alpine закреплён digest. Runtime запускается непривилегированным пользователем, данные в `/data`. `prepare:products` последовательно собирает четыре локальных образа и сохраняет фактические digest в `apps/hosting/data/product-images.json`. Образы не отправляются в registry.

Версии first/second имеют разные конфигурации OCI, но одинаковый прикладной код: проверяется совместимая замена версии, а не миграция между разными реализациями. Агент хранит два runtime-секрета отдельно от образа и повторно использует их; текущий gateway origin передаётся в CORS. Атомарное имя writer-контейнера запрещает два активных writer одного окружения. Новый выпуск останавливает прежний контейнер, поэтому есть простой. Автоматическая HA и распределённые leases не заявлены.

Backup проверен на остановленном writer: содержимое именованного тома копируется в отдельный том и новое окружение. Это воспроизводимый сценарий в live-check, не готовый GUI-каталог резервных копий, шифрование или расписание. Обычный rollout том не удаляет; тест очищает только свои объекты.

Приложение в тесте ограничено 256 МиБ/0,5 CPU, helper копирования 64 МиБ. WSL после последовательных сборок наблюдался около 1,1–1,5 ГиБ; это снимки, не измеренный максимум всей системы. Сборки и стенды выполнялись по очереди. Посторонний пользовательский контейнер не останавливался, Docker prune не выполнялся. Настоящие VM/Kubernetes/локальные модели не запускались. Имеющийся OCI/Python пример сохранён; новые возможности постоянных томов не зависят от языка приложения.

## Проверки и измерения

Пройдены typecheck обоих приложений, полный `npm test` пиццерии (роли, склад, host, сеть, organizer, peer, SC1, canvas), `test:communication`, полный `npm test` хостинга, `test:gateway-ws`, production-сборки пиццерии/органайзера/хостинга. Две новые положительные группы затем добавлены в общий `npm test`; их код проверен отдельно теми же командами. LXD в общем тесте — HTTP fixture, без запуска VM. Ошибки тестовых дублей не выдаются за результаты реальных провайдеров.

В последнем локальном сетевом прогоне: 20 последовательных RPC чтений principal — p50 0,2 мс, p95 0,9 мс; потеря serving node → подключение замены 70 мс; плановый scale-to-zero/fallback 2072 мс. Координатор теста RSS 137 МиБ, это не сумма дочерних процессов. Эти малые измерения не показывают предел пропускной способности и не гарантируют такие задержки в сети.

Docker live-check обоих приложений проверяет deploy/update/rollback, архив, рестарт агента, несовместимый dataVersion, восстановление после плохой readiness и backup/restore. Через REST проверки проходят. Отдельный положительный Socket.IO тест подтверждает HTTP upgrade, двусторонние сообщения, drain и reconnect за неизменным gateway. `repro:public-address` воспроизводит H3 и намеренно завершается ошибкой на common2 2.19.0; он не включён в обычный положительный test.

Сборки Vite предупреждают о размере общего JS >500 КБ и будущей загрузке конфигурации. Размер organizer около 593 КБ / 188 КБ gzip, пиццерии 630 КБ / 197 КБ gzip. Разбиение по ленивым экранным модулям остаётся оптимизацией приложения, не новым требованием библиотеке.

## Что передать библиотекам

Единый документ для передачи — [CURRENT-HANDOFF](../library-tasks/CURRENT-HANDOFF.md).

- **H3 common2**: trusted advertised URL отдельно от listen URL в готовом host runtime. Сейчас размещённый сервис публикует localhost:8080 вместо gateway, клиент получает `no eligible endpoint`. Это первый блокер продолжения размещённого UI.
- **M1 common2**: запоздавший MediaRecorder chunk пересекает stop/start. Изолированный repro подтверждён; текущий PCM-путь от него не зависит.
- **A1 common2**: поддерживаемое восстановление AI runs/receipts и политика неопределённого внешнего исхода; не незаметный повтор оплачиваемого действия.
- **H1/H2 common2 и R4 react2**: прежние предложения остаются. Нового подтверждённого дефекта react2 этот этап не выявил.

Использование библиотек оправдало себя: service runtime, типизированные роли, ресурсные поколения, replay, conversation host, blob storage, media codec/relay, AI host/client и React ownership уже существуют. Добавлялась главным образом предметная политика и адаптеры IO. Достоверную экономию в процентах не измеряли; ограничения H3/A1 существенно мешают именно завершённым инфраструктурным сценариям. Новые общие библиотеки чата, доски, ИИ или Docker не предлагаются.

Следующее действие после публикации исправлений: exact npm + lock, H3 без REST-обхода и с ресурсами экрана/чата, M1 `--expect-fixed`, A1 restart/uncertain-outcome через новый публичный port. Затем ручная приёмка устройств и проверка между машинами. Непройденные проверки не скрыты за завершением независимой реализации.
