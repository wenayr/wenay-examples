В поддержке текст и источники вынесены в отдельное чтение с актуальными ACL; подробности и критерии находятся в задаче. Ниже сохранена история предыдущего пакета.

Проверена временная композиция публичного state replay с `onError`, восстановлением нового generation и отменой задания.

Также воспроизведён [STORE-NESTED-REPLACEMENT](../library-tasks/STORE-NESTED-REPLACEMENT.md): сохранение proxy-элементов массива при замене родителя вызывает рекурсию snapshot. В примере применяется отделение обычных данных версий. Предыдущий пакет закрыт; три новые задачи common2 выше открыты. Новых подтверждённых задач react2 пока нет.

## Задание исполнителю

Повторно выполнять H1/H2/R4/H3/M1/A1/SC1/PC1/PC2/H0 не нужно. Новое задание оформлять только по конкретному повторению или воспроизведённому дефекту следующего сценария. Сначала проверять композицию публичных механизмов. Предметные правила приложений оставлять в примерах.

Используйте существующие RPC, replay, права, типизацию, ресурсы и hooks. Не вводите второй транспорт, систему схем, глобальное подавление ошибок или копию service runtime в каждом приложении. Примеры принимают только опубликованные точные npm-версии; локальные подмены зависимостей не закрывают задачу.

### PC1. Закрытое peer-подключение продолжает действовать

**Закрыто в 2.18.2.** Далее сохранено исходное поведение 2.18.1 и критерии regression-проверки.

После `connection.close()` участник исчезает из presence, но сохранённые `fragment.publish`, `publishBatch` и `signal.send` продолжают менять relay и доставлять сигналы. Сигнал, ожидавший асинхронную авторизацию, также доставляется после закрытия. Через реальный RPC закрытый комнатный фасад меняет курсор наблюдателя на `777`.

Ожидание: закрытое подключение не производит новых эффектов; проверить состояние также после `await authorize`. Другие подключения, включая вторую сессию того же аккаунта, продолжают работать. Родительский RPC может оставаться открытым для остальных функций приложения. Это не доказанный обход отозванного RPC principal и не проверка настоящего WebRTC-медиапотока.

Воспроизведение из `apps/pizzeria`: `npm run repro:peer-close`; сетевой вариант — `npm run repro:peer-network`. Приёмка после исправления: локальный вариант с `--expect-fixed` проходит; сетевой — после исправления также PC2. Покрыть одиночную/пакетную публикацию, сигнал после close, ожидающую авторизацию, повторный close и сохранение другой сессии.

### PC2. Завершение peer/RPC оставляет unhandled RPC_ABORT

**Закрыто в 2.18.2.** Далее — исходное воспроизведение 2.18.1. `npm run test:peer` теперь проверяет исправленное поведение и включён в обычный `npm test`.

В готовом сетевом клиенте вызовы `peerClient.close()` и сразу `hub.close()` оставляют две необработанные ошибки `RPC_ABORT / RPC hub closed`. Без диагностического обработчика Node завершается с `ERR_UNHANDLED_REJECTION`. Дефект воспроизведён независимо от публикации после закрытия из PC1.

Воспроизведение из `apps/pizzeria`: `npm run repro:peer-network -- --shutdown-only`. Приёмка: тот же запуск с `--expect-fixed` проходит с нулём необработанных ошибок. Проверить завершение до/после готовности подписки, при обновлении и обрыве транспорта. Исправлять владельца Promise в peer/RPC; приложение не должно ставить случайные задержки между close или перехватывать глобально все ошибки.

Полные детали PC1/PC2, границы и ожидаемый вывод: [peer-lifecycle.md](../library-tasks/peer-lifecycle.md). Внутренняя причина PC2 пока не локализована до одной функции; подтверждён дефект композиции peer/RPC.

### SC1. Подключение ресурсного фасада к готовому service runtime

**Закрыто в 2.19.0.** Публичные `definition.resources`, `ServiceResourceContext`, `client.resources.open()` применены к доске. `resourceId` разделяет владельцев; ресурс остаётся на authority при смене serving node. Отдельная проверка подтверждает отзыв динамической `noStrict` peer-подписки без закрытия общей линии другого участника. Команды проверки: `npm run test:collaboration` в `apps/pizzeria`. Ниже сохранена исходная постановка для 2.18.2; утверждения об отсутствии API относятся к той версии.

**Уточнённая постановка первой версии:** [service-session-facets-v1.md](../library-tasks/service-session-facets-v1.md). Реестр фабрик фиксирован при запуске, создаются экземпляры подключений; горячая загрузка кода, плагины и деплой не входят. Выбраны authority-размещение, новый remote на каждое поколение и отдельный этап доказательства отзыва динамических RPC-подписок. Матрица A/B/C/T/D определяет проверку до объявления механизма готовым.

Существующий сервис имеет команды, views, токен и текущие права. Требуется добавить типизированный peer-фасад с жизненным циклом подключения. Далее та же общая точка должна подойти для conversation или AI, без специального runtime для каждого модуля.

Проверены definition, descriptor, host mount и service client: готовой публичной композиции дополнительного защищённого сессионного фасада в них не объявлено. Низкоуровневые `createHostResource`, RPC и service leader уже позволяют собрать сетевой стенд. Нужно повторно использовать эту основу и существующие auth/reconnect/permissions, а не копировать их в приложение.

Приёмка: проверенный principal, серверный ID сессии, вывод типа удалённого фасада, безопасный descriptor, создание/освобождение ресурса, отзыв текущих вызовов и подписок, reauth/reconnect без прежней личности. Явно определить размещение: смена serving node не должна незаметно создавать другую комнату. Достаточен документированный адаптер, если он решает задачу существующим API. Универсальная система плагинов не требуется.

Подробное задание и матрица проверки: [service-session-facets-v1.md](../library-tasks/service-session-facets-v1.md). Исходный обзор публичной поверхности: [service-session-facets.md](../library-tasks/service-session-facets.md).

### H1. Общий исполнитель повторной сверки состояния

**Закрыто в 2.21.0, подключено к обоим агентам.** [Отчёт](../changes/common2-2.21.0.md). Далее исходное обоснование.

Docker- и LXD-агенты вручную поддерживают `busy/dirty/running`, подписки, отложенные повторы и остановку. Пока идёт IO, новые уведомления должны требовать один следующий проход со свежим снимком. Обычная `createAsyncQueue(1)` правильно выполняет все поставленные задачи; очередь не объявляется дефектной.

Приёмка композиции: нет неограниченного накопления проходов, один проход не запускается параллельно сам с собой, уведомление во время завершения не теряется; повтор задаётся политикой потребителя; close отменяет ожидания, снимает подписки/таймеры и имеет явную гарантию завершения. После внедрения дублирование действительно удаляется из обоих агентов. Идентификаторы внешних операций и решения при неизвестном результате остаются приложению. Распределённые lease/fencing/exactly-once этим примитивом не обещаются.

### H2. Публичное владение ресурсами

**Закрыто в 2.21.0, подключено к обоим агентам.** [Отчёт](../changes/common2-2.21.0.md). Далее исходное обоснование.

При создании агента приобретаются lock, клиент, подписки и другие ресурсы. Нужна общая композиция частичного старта, поздно завершившегося приобретения и остановки. `installServiceSignals` уже опубликован и применён — его повторно создавать не надо. Внутренний `createHostLifecycle` не является публичным экспортом; его параллельное освобождение нельзя молча принять за последовательное завершение зависимых ресурсов.

Приёмка: исходная ошибка старта сохранена; уже приобретённое освобождено; поздний ресурс после отмены также освобождён; повторные close разделяют завершение. Последовательные зависимости и независимые disposers различаются явно. Ошибка одного не пропускает остальные; предел ожидания не выдаётся за гарантированную остановку внешнего IO. H1/H2 могут стать одной небольшой композицией. Прежняя C4 о lifecycle хоста закрыта и не открывается заново.

### H0. Документация Store через await

**Закрыто в 2.18.2.** В опубликованном `doc/STORE-CONSUMER-GUIDE.md` есть пример со вложенным массивом, активной операцией и проверкой актуального состояния перед внешним действием. Далее — исходная постановка.

Добавить пример живого `store.state` и отдельного `store.snapshot()` при асинхронном проходе. Снимок фиксирует данные для вычисления, но перед внешним опасным действием может потребоваться проверка актуального состояния. Он не заменяет транзакцию или fencing. Ошибка использования уже исправлена в агентах; нового дефекта Store нет.

Подробности H1/H2/H0 и исходные потребители: [hosting-runtime.md](../library-tasks/hosting-runtime.md). Из `apps/hosting`: `npm run test:library-audit` проверяет текущие snapshot/queue/signals, отдельно от новых контрактов H1/H2. H1/H2 приняты: `npm run test:orchestration`, агентские проверки и живой Docker прошли на 2.21.0.

## Граница ответственности

Библиотекам передаются lifecycle, публичная композиция фасадов, повторяющаяся оркестрация ресурсов и документация примитивов. Приложению остаются комнаты и видимость конкретных задач, цвета/имена, курсоры и фокус доски, конфликты карточек, рецептуры/склад, Docker/LXD-политики и схема хостинга, предметные формы, прикладные ИИ-команды.

Мессенджер, экран и голос реализованы на существующих conversation/media/ai и React hooks. Они обосновали только H3/M1/A1, перечисленные выше; новый общий чат, экран или ИИ-оркестратор не требуется. SFU, CRDT, универсальные workflow/form builders, HA-writer и распределённые leases не входят в текущий пакет без отдельного доказанного сценария.
