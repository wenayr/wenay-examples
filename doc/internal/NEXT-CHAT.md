## Главная цель

Мы создаём законченные, небольшие, практически полезные примеры на wenay-common2 и wenay-react2 и через их использование выявляем реальные потребности библиотек. Пользователь хочет, чтобы библиотеки покрывали большинство типичных задач без лишней обвязки. Бизнес-правила остаются в приложении; в библиотеку отправляем только повторяемые общие механизмы или доказанные дефекты. Не составлять список абстрактных улучшений ради количества.

Цикл работы: реальный сценарий → существующий публичный API → минимальная композиция → работающие проверки → при нехватке воспроизводимое задание в doc/library-tasks → после публикации точное npm-обновление → удалить заменённую обвязку и повторить сценарий. Пользователь просил работать крупными законченными этапами, сначала составлять подробный план, продолжать автономно и не запрашивать повторное разрешение на уже порученную работу.

## Правила и ограничения

- Прочитать AGENTS.md и doc/CODE-RULES.md. Фабрики/замыкания, явные deps, ролевые фасады, вывод типов из реализации, минимум слоёв. Без Zod и дублирования транспорта, replay, reconnect или типизационной системы. Публичные экспорты опубликованных пакетов, точные версии и lock, без npm link/соседних исходников.
- Общаемся по-русски, короткие понятные обновления о результате; не завершать работу после каждого микрошажка.
- Целевой дополнительный расход RAM 1–2 ГиБ, максимум 3. Последовательные лёгкие проверки. Docker установлен и работает, но не запускать тяжёлый кластер, реальные VM или локальные ИИ-модели.
- Пользователь явно выбрал «пока без платных запросов». ИИ-провайдер заменяемый; без оплаты проверять fixtures, отмену, доступ, persistence. Не отправлять сообщения третьим лицам без отдельного поручения.
- Не создавать коммиты, не публиковать и не удалять пользовательские данные просто ради передачи контекста. Большая часть apps/ и doc/ пока untracked; это сделанная работа, не мусор. Новая задача должна использовать текущий каталог.
- Для нового существенного этапа создать doc/progress/<task>.md, поддерживать контрольные точки, при завершении переносить выводы и удалять временный файл.

## Что реализовано

apps/pizzeria: пиццерия по ролям customer/cook/courier/manager/owner. Блюда/рецептуры/описания/фотографии, склад партий, количества, FEFO, срок годности, ручная порча, резервы, заказы. Сеть независимых точек, масштабирование и восстановление через библиотечный runtime.

apps/pizzeria/organizer: самостоятельный и встраиваемый органайзер. Сотрудники и права, произвольные задачи, дедлайны, checklist, проверка результата, загрузка исполнителей. Автоматические задачи из заказов и проблем склада. Обычная доска, свободные заметки/связи/ревизии, курсоры, присутствие, слежение, чужой временный drag через SC1. useReorderBoard и useDraggableApi обеспечивают механику ввода; координаты/конфликты/RPC остаются приложению.

Общение: защищённый ресурс чата, durable сообщения/receipts, вложения, ответы, поиск/страницы/прочтение/typing. Экран через явное getDisplayMedia, ограниченная JPEG-передача, один ведущий, поколения/TTL. Голос PCM16/WAV с preview/send; ИИ-run через библиотеку, отмена/revoke, предложение обычных задач с подтверждением. AI checkpoint fsync сохраняется, после неизвестного исхода нет автоматического повтора внешнего эффекта. Серверный recovery требует сверки.

apps/hosting: панель/контроль/агенты через common2, immutable OCI-релизы, deploy/update/rollback, стабильный HTTP/WS gateway, readiness, состояние на volume, runtime-секреты отдельно. Docker не ограничен Node: проверен Python. LXD-контейнеры/VM представлены адаптером и protocol fixture; реальная VM не проверена. Kubernetes — дальнейший большой сценарий, не готовый настоящий кластер.
