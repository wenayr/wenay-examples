# Daylight: приёмка интерфейса R04 / R07

Дата: 10 сентября 2026. Приложение: `apps/booking`, локальный сервер `http://127.0.0.1:3814/`. Проверка выполнена в настоящем Chrome через доступный CUA API, без подмены ответа сервера, состояния React или команд приложения.

## Что реализовано

- Самостоятельный календарь Daylight с отдельным оформлением: выбор услуги, день/неделя, UTC-сдвиг и часовой пояс места встречи, проверка доступности, удержание, подтверждение, перенос и отмена.
- Личный список встреч, история, обратный отсчёт удержания, настройки локального напоминания, лист ожидания и явно обозначенная тестовая предоплата без движения денег.
- Формы услуг и расписаний для сотрудников: длительность, подготовка/перерыв, вместимость, рабочие интервалы и исключения по датам. Сервер проверяет роль, область доступа и исходную ревизию.
- Подбор по пожеланиям через AI run host. Демонстрационный разбор текста явно обозначен; платная модель не используется. Предложение только заполняет календарь, создание удержания остаётся отдельным действием человека.

## Проверено в браузере

1. Клиент Илья выбрал консультацию 11 сентября в 10:00 Europe/Berlin, ввёл комментарий, удержал время и подтвердил встречу. Список показал удержание с обратным отсчётом, затем подтверждённую запись.
2. Перенос на 11:00 изменил ту же встречу. Прежнее локальное напоминание отменилось, новое появилось. После явного подтверждения отмены активный список стал пустым, оба напоминания отменены.
3. После обновления сервера помощник разобрал «Завтра в 12:00, 1 человек». Публичное состояние run завершилось; отдельное чтение результата вернуло 11 сентября, 12:00 GMT+2, Europe/Berlin. «Применить выбор к календарю» не создало встречу: личный список остался пустым. Только последующие выбор слота, удержание и подтверждение создали запись на 12:00.
4. Новое локальное напоминание содержит человекочитаемое время встречи «11 сентября в 12:00 GMT+2 · Europe/Berlin». Время отправки показано отдельно. Старые сохранённые напоминания до исправления форматирования остаются историческими данными.
5. После выхода и входа клиентом Дарьей список встреч, ожиданий и локальная почта пусты. Запись Ильи, его комментарий и результаты предыдущего помощника не отобразились.
6. Аккаунт другой команды получил только Harbor Labs, собственное расписание и Europe/Moscow/GMT+3. Northstar в выборе организаций отсутствует. Через роль владельца Harbor сохранены новое описание услуги и название расписания; обычные рабочие интервалы сохранились.
7. Мобильная проверка 390×844: реальная ширина содержимого 375px, `documentElement.scrollWidth == clientWidth == 375` на календаре и странице настроек. Скриншоты проверены визуально: карточки, подписи и формы читаемы. Недельный календарь и меню прокручиваются внутри своих областей. Размер браузера после проверки восстановлен.
8. При завершении браузерный журнал ошибок и предупреждений пуст. Вкладка Daylight оставлена доступной, сервер не остановлен.

`npm run typecheck` и `npm run build` прошли после подключения помощника. Предметные, сетевые и assistant проверки отдельно принадлежат backend-набору приложения; этот отчёт не выдаёт их за браузерные сценарии.

## Использование библиотек и границы примера

Фронтенд использует публичные service session/resources, `ServiceView`, `useOwnedClient`, `useClientStore`, библиотечный `useStoreReplayMirror` через общий тонкий React hook и типизированные команды. Собственного транспорта, reconnect или реализации replay нет. Авторитетную доступность возвращает ресурс `calendar`; локальная сетка лишь отображает снимок. При записи сервер заново проверяет вместимость. Скрытые чужие встречи не передаются клиенту ради обновления сетки; доступен явный повторный запрос свободного времени.

Частный результат помощника читается отдельным методом с текущими ACL и версиями каталога. Публичное состояние run не является хранилищем частного текста. После смены организации, набора ревизий или поколения ресурса ранее показанный результат скрывается; применение снова запрашивает проверенный результат и перечитывает календарь.

Браузерная приёмка не проверяла достижение TTL ожидания реальным пятиминутным ожиданием, конфликт двух одновременных посетителей, осенний DST или живой платёжный шлюз. Эти ограничения нельзя заменять заявлением о браузерном покрытии; соответствующие предметные/сетевые проверки и тестовый характер платежей описаны в README приложения.
