# Проверенная композиция библиотек для SaaS-примеров

Инвентаризация 2026-09-10. Проверены установленные публичные экспорты `wenay-common2@2.21.1` и `wenay-react2@3.5.1` (во время чтения react2 обновлён с 3.5.0). Это карта доступных механизмов и ограничений контрактов, а не отчёт о выполнении нового нагрузочного теста.

## Минимальная архитектура

Первый helpdesk: отдельное приложение с собственной точной npm-зависимостью, конфигурацией и каталогом данных. Предметное состояние организаций, членства, обращений и статей принадлежит `tServiceDefinition`. Состояние меняют `schemaCommand`, клиент получает разрешённые `views`. Общение и задания ИИ подключаются через `resources` с размещением `authority`. Публичный `createServiceClient` обслуживает транспорт и переподключение.

Второй потребитель — обработка документов. Общие адаптеры выделяются после появления этого потребителя. Не нужно переносить всю пиццерию в новый пакет или создавать платформу аккаунтов до первого законченного сценария.

## Изоляция организаций: существенные границы

1. `tServicePrincipal` содержит `account` и `roles`; отдельного поля tenant в проверенном контракте нет. Членство и текущая организация — предметное состояние приложения. Не объявлять это дефектом библиотеки.
2. Строки ролей являются грубым допуском к команде/ресурсу. `apply` повторно проверяет членство в нужной организации по текущему состоянию, включая объект обращения/статьи; недостаточно доверять `tenantId` из браузера.
3. `view.project` фильтрует организации, обращения, статьи и пользователей до отправки. Общая роль `agent` не должна давать данные всех организаций. `shared: true` нельзя использовать для проекции, зависящей от principal.
4. Имя аккаунта глобально внутри сервиса. Пользователь с членством в двух организациях не должен получать вторую организацию в первой выборке. Не объединять account и tenant неоднозначной конкатенацией.
5. Ресурс может пережить изменение прав. Перед чтением, скачиванием, отправкой, запуском ИИ и фиксацией результата проверять текущее членство. `ctx.signal` сообщает закрытие ресурса, но не заменяет предметную проверку доступа к конкретному обращению.
6. `ConversationHost` policy должна разрешать конкретное обращение и его аудиторию; внутренние заметки операторов не должны попадать в клиентский канал. Ссылки на статьи и артефакты в ИИ-ответе проходят тот же контроль доступа, что и исходные данные.
7. Чувствительные AI checkpoint, server-only recovery и полное состояние журнала не ретранслируются в RPC-фасад. В публичном дескрипторе также не должно быть ключей провайдера.

Практические проверки: два tenant с одинаковыми локальными названиями; клиент видит только свои обращения; агент не видит чужую организацию; отзыв членства при открытом ресурсе; отложенный результат ИИ после отзыва; повторный requestId; изменение revision двумя операторами. Проверять и команды, и подписки, и загрузку по известному чужому id.

Не импортировать backend пиццерии из браузерного SaaS entry point.

## Долговечность и масштабирование: чего проверенные контракты не обещают

- `runNodeProcess` даёт обслуживающий узел, а authority-ресурс продолжает жить на владельце. Добавление двух узлов не означает два конкурентных исполнителя одного AI/file задания.
- В `FileJobHostDeps` проверенной версии есть storage/runner/policy/id/now/history/drain, но нет публичных `initial`/`persistence`, аналогичных AI checkpoint. Для обработки документов необходимо отдельно проверить восстановление задания и входа после рестарта. Это подтверждённое различие поверхности API, но ещё не воспроизведённый дефект и не готовая заявка на разработку.
- `AiRunUsage` содержит необязательные счётчики токенов, не тариф или финансовую транзакцию. Отсутствующая информация о цене не равна нулевой цене.
- Локальные chat/AI адаптеры записывают файлы одним владельцем; они не являются многопроцессной БД и не должны открываться конкурентными владельцами как способ масштабирования записи.
- Conversation/AI/Artifact/FileJob имеют account-проекции с replay V2; это полезная основа доставки изменений. Их политика всё равно должна выражать продуктовую tenant-изоляцию.
- Вызов внешнего провайдера может завершиться при потерянном ответе. Ни UI retry, ни receipt команды сами по себе не доказывают однократную оплату или внешний side effect.

## Что переносить, а что оставить предметным

**Готово к использованию:** публичные механизмы выше, маленькие проверенные React-адаптеры и форма composition через factories/deps. Identity hash/verify из существующего backend — пример ресурса; при реальном повторении перенести минимальные функции вместе с их тестом, без импорта бизнес-сервиса.

**Кандидаты после двух потребителей:** fsync checkpoint adapter; UI сообщения команд; отображение lifecycle задания и human approval; ограниченное скачивание артефакта с отменой. Сначала проверить, не появился ли подходящий публичный API в новом релизе.

**Приложение:** членство организаций, SLA, очередь операторов, видимость внутренней заметки, источники RAG, критерии публикации статьи, правила удержания файлов, тарификация и право подтвердить результат. Эти правила не отправлять в библиотеку.

**Проверить и только затем оформить библиотечную задачу:** восстановление file job, позднее завершение результата после закрытия ресурса, удобство typed approval input при двух разных продуктах. Для каждого нужны точная версия, минимальный воспроизводимый сценарий через публичный API и ожидаемое общее поведение.

## Подтверждённая потребность: внешняя смена AI policy

После инвентаризации проверен [ai-policy-repro.ts](../../apps/support/backend/ai-policy-repro.ts) через публичные `createAiRunHost` и `createAiRunClient` на common2 2.21.1. Runner — локальный fixture, без сети и оплаты. `policy.canRead` читает внешнее членство. После завершения задания доступ отзывается без изменения собственного AI store.

Фактический результат: старый клиент сохраняет запись; **новый клиент на прежнем fragment заново получает запрещённый результат**, и свежий вызов `state.keyframe()` прежнего fragment также содержит результат. Новое `host.connection()` применяет актуальную policy и исключает запись. `cancelRun` проверяет актуальную policy и запрещает операцию. Следовательно, проблема шире уже сохранённой копии браузера: сервер повторно выдаёт кэшированную разрешённую ранее проекцию после отзыва доступа.

В проверенном публичном контракте нет уведомления о внешнем изменении policy. Минимальное общее дополнение — серверный метод инвалидации/пересчёта доступа, который приложение вызывает при изменении членства; API не должен знать организации или статьи. Критерии: текущие подписчики теряют скрытые runs/inputs/approvals; новые keyframe/chunks/replay после инвалидации не выдают данные старой политики; command policy остаётся актуальной; изменения доступа одного account не смешивают данные другого. Историю replay нужно проверить отдельно: одного удаления из текущей проекции может быть недостаточно.

Запуск из `apps/support`: `node --import tsx backend/ai-policy-repro.ts` подтверждает наблюдение; `--expect-fixed` проверяет желаемый инвариант и на 2.21.1 завершается ошибкой. После появления API инвалидации repro должен явно вызывать его в точке изменения policy. Произвольное изменение внутреннего store ради запуска обновления не является допустимым решением.
