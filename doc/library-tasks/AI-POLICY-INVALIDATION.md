# AI-POLICY-INVALIDATION: обновление доступа к существующей AI-проекции

Статус: **открыто, воспроизведено** 10 сентября 2026 на опубликованной npm-версии **wenay-common2 2.21.1**. React2 3.5.1 установлен в примере, но воспроизведение не использует React и не предъявляет задачу frontend-библиотеке.

Связанные материалы: [инвентаризация публичных механизмов](../saas-library-inventory.md), [воспроизведение](../../apps/support/backend/ai-policy-repro.ts), [потребитель поддержки](../../apps/support/backend/assistant-resource.ts), [потребитель органайзера](../../apps/pizzeria/organizer/assistant-resource.ts).

## Пользовательский сценарий

Оператор получил AI-черновик по обращению организации. Затем его членство или доступ к источнику отозваны в предметном состоянии приложения. `AiRunPolicy.canRead` читает актуальное внешнее состояние и теперь возвращает `false`. Само завершённое AI-задание не изменилось. Существующая серверная AI-проекция продолжает выдавать разрешённый ранее результат.

Проверка касается нового чтения после отзыва. Невозможно забрать данные, которые пользователь уже сохранил до отзыва; этого задача не требует.

## Минимальное воспроизведение

Из каталога `apps/support`:

```sh
node --import tsx backend/ai-policy-repro.ts
```

Тест использует только публичные `createAiRunHost` и `createAiRunClient` из `wenay-common2/ai`. Нет сетевого сервера, внешнего провайдера, платных запросов или доступа к private API.

1. Создать host с локальным runner, возвращающим маркированный результат, и policy, читающей внешнее `allowed = true`.
2. Открыть `host.connection('agent')`, создать клиент из его `fragment`, выполнить задание и дождаться доставки результата.
3. Установить `allowed = false`, не изменяя AI store.
4. Создать **новый** клиент из прежнего `fragment` и отдельно вызвать прежний `fragment.state.keyframe()`.
5. Для сравнения открыть новую серверную `host.connection('agent')` и создать клиент из неё.

Наблюдение 2.21.1:

```json
{
  "originalClientRetainsResult": true,
  "newClientFromOldFragmentReceivesResult": true,
  "oldFragmentKeyframeContainsResult": true,
  "newConnectionReceivesResult": false
}
```

`cancelRun` на прежнем соединении при этом корректно отклоняется как forbidden/missing: актуальная policy учитывается в команде. Проблема подтверждена в выдаче сохранённой серверной проекции.

Обычный режим воспроизведения проверяет именно наблюдаемое ограничение и завершается успешно. Вариант `--expect-fixed` проверяет желаемый инвариант и на 2.21.1 завершается ошибкой `Revoked policy must prevent a new read through an existing fragment`. После появления публичного API уведомления о смене policy вызов этого API необходимо добавить непосредственно после изменения `allowed`.

## Проверенная публичная поверхность

В `AiRunHostDeps` есть `policy`, `runner`, `initial`, `persistence`, `capabilities`, `history`, `drain`, `id`, `now`. Host возвращает `connection`, `store`, `persistence`, `recovery`, `close`. В проверенной версии нет публичного способа сообщить существующим проекциям о внешнем изменении доступа.

Новое `host.connection()` создаёт правильную проекцию и является подтверждённым обходным направлением. Однако принудительная замена соединения требует от приложения также защитить сохранённые ранее фасады и остановить соответствующие подписки. Просто скрыть данные в UI или закрыть один клиентский mirror недостаточно.

## Что требуется от библиотеки

Предоставить поддерживаемый публичный способ уведомить AI runtime об изменении внешней политики и обеспечить актуальный доступ существующих соединений. Библиотеке не нужно знать понятия организации, обращения, статьи или членства. Решение может задавать явную точку инвалидации; автоматическое наблюдение произвольного замыкания не требуется.

Имя метода, способ пересоздания проекции и внутренняя организация остаются на стороне библиотеки. Не требуется переносить tenant-правила в common2 или вводить новый транспорт. Изменение внутреннего `store` ради искусственного запуска подписки не является допустимым API-решением.

## Критерии готовности

1. После внешнего отзыва и предусмотренного публичного уведомления новый клиент на ранее открытом fragment не получает запрещённый run/result. Уже подключённый mirror получает удаление или понятный сигнал потери разрешённой проекции.
2. Связанные `approvals` и `inputs`, включая их данные, фильтруются вместе с run. Восстановление разрешения возвращает только актуально доступные записи.
3. Новые `keyframe`, `since`, `frame` и chunk-операции после инвалидации не выдают данные прежней политики. Проверить также `pull` snapshot, начатого до отзыва. Допустимо инвалидировать координаты и требовать новый разрешённый keyframe; нельзя повторно отправлять закрытые данные в старых патчах до последующего удаления.
4. Проверить семантический `events` replay, включая sync и историю событий с result/tool/input/approval данными. Если доступ к старым данным уже закрыт, новый запрос истории их не раскрывает.
5. Проверить две сессии одного account, два account и независимый run другого account: отзыв не смешивает проекции и не закрывает чужую разрешённую работу.
6. Проверить изменение доступа при выполнении задания и запоздавшие progress/result/events. Инвалидация чтения не обязана означать отмену бизнес-операции; семантику явно описать и не доставлять закрытые данные.
7. Проверить close, повторную инвалидацию, восстановленный из checkpoint host и отсутствие изменений AI store при внешней смене policy.
8. Опубликовать npm-версию и документацию. В примерах обновить точную зависимость, применить публичное уведомление при изменении доступа и повторить воспроизведение с `--expect-fixed`.

Пункты про старую историю, chunks, approvals/inputs и поздние события — критерии проверки исправления; отдельное воспроизведение их текущего поведения пока не выполнялось. Подтверждённый дефект ограничен старой проекцией, новым клиентом на прежнем fragment и `keyframe()`.

## Текущая защита нового примера поддержки

`apps/support/backend/assistant-resource.ts` намеренно не помещает текст черновика и источники в `AiRun.result`: туда попадает только `{available, demo}`. Закрытый результат хранится сервером и читается через `control.result(runId)`, который заново проверяет владельца, текущий доступ к обращению, принадлежность и публикацию статей, их revision. Поиск источников тоже проверяет текущую организацию. Отправка ответа остаётся отдельной предметной командой с проверкой её условий.

Эта композиция сокращает раскрываемые данные и позволяет продолжать продукт, но не объявляется исправлением AI runtime. Метаданные задания остаются в owner-проекции; для строгого отзыва всей проекции нужен описанный механизм библиотеки. Органайзер также использует policy, зависящую от внешнего доступа к разговору, поэтому после публикации исправления его следует проверить отдельно.
