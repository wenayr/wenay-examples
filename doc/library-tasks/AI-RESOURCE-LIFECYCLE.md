# AI-RESOURCE-LIFECYCLE: управляемое завершение AI-клиента при отзыве SC1

Статус: **открыто, повторно воспроизведено** 26 сентября 2026 на опубликованной **wenay-common2 3.1.1**. Исходное воспроизведение — 10 сентября на 2.21.1. Текущий переход frontend — react2 5.0.0; минимальное воспроизведение работает без React. Это отдельная задача от [инвалидации внешней policy](AI-POLICY-INVALIDATION.md).

На npm 3.1.1 обычный режим после выполненного `ready` и внешнего revoke снова завершился с кодом 1: `replaySubscribe: live line from seq 2 failed: logical RPC line ended`. Декларация `AiRunClientDeps` по-прежнему содержит только `remote`, `initial`, `drain`; публичного error/lifecycle port нет. Остальные варианты таблицы ниже — историческая проверка 2.21.1, в этом коротком аудите они не повторялись. [Аудит обновления](../reports/LIBRARY-API-AUDIT-2026-09-26.md).

Воспроизведение: [apps/support/backend/ai-resource-lifecycle-repro.ts](../../apps/support/backend/ai-resource-lifecycle-repro.ts).

## Сценарий и ожидаемый жизненный цикл

Клиент поддержки открыл SC1-ресурс с AI-фасадом и подписался через `createAiRunClient`. Другой пользователь отозвал его роль. SC1 правильно закрывает разрешённый ранее ресурс, запрещает старые RPC-адреса и переводит controller в `denied`. Завершение вложенных подписок должно попадать в управляемую ошибку/статус клиента. Оно не должно порождать исключение из отложенного callback вне области уже выполненного `client.ready`.

Документация опубликованного пакета `doc/SERVICE-RESOURCES.md` определяет generation-bound remote: смена ролей закрывает прежний scope даже при сохранении допуска; восстановление доступа создаёт новый generation. Приложение должно освободить прежнего потребителя и построить нового из `current()`. Заранее знать об отзыве другим пользователем приложение не может.

## Проверенные результаты

Из `apps/support`:

```sh
node --import tsx backend/ai-resource-lifecycle-repro.ts
node --import tsx backend/ai-resource-lifecycle-repro.ts --dispose-on-status
node --import tsx backend/ai-resource-lifecycle-repro.ts --dispose-before-revoke
node --import tsx backend/ai-resource-lifecycle-repro.ts --safe-state
```

| Вариант | Результат на 2.21.1 |
| --- | --- |
| Обычный AI-клиент при внешнем отзыве | Необработанная ошибка `replaySubscribe: live line from seq 2 failed: logical RPC line ended`, код выхода 1 |
| Синхронно закрывать AI-клиент по изменению `resource.status` | Та же ошибка, код выхода 1; реакция на status запаздывает относительно завершения RPC line |
| Закрыть клиент до изменения серверной роли | Проходит; полезно для контролируемого shutdown, не решает внешний отзыв |
| State-only публичный replay с `onError` | Проходит: ошибка доставлена обработчику, зеркало очищено, новый generation восстановил состояние, отмена нового задания сохранилась после позднего результата |

Каждая проверка использует реальный локальный RPC с host и клиентом в одном процессе, без дочерних процессов, Docker и внешнего ИИ. `client.ready` дожидается завершения до отзыва. Никакого глобального `uncaughtException`/`unhandledRejection` подавления нет. Воспроизведение обычного режима намеренно завершается ошибкой процесса.

## Проверенная поверхность API

`createAiRunClient` из `wenay-common2/ai` принимает `remote`, `initial`, `drain`. Его клиент даёт `store`, `events`, `ready`, координаты replay, команды и `close`. Публичного обработчика поздней ошибки подписки либо наблюдаемого состояния завершения нет.

Нижележащий публичный `syncStoreReplay` из `wenay-common2/observe` поддерживает `onError`. `createAiRunClient` создаёт свои подписки состояния и событий без пользовательского error port. Ошибка после готовности не может быть доставлена повторным отклонением уже выполненного Promise `ready`.

`useOwnedClient({key: remote})` и привязка React-компонента к generation — правильное владение, но не исправление этой ошибки: React cleanup не обязан успеть до завершения RPC line. Более ранний синхронный status subscriber тоже проверен и не предотвращает её.

## Требуемое общее улучшение

Дать потребителю поддерживаемый канал поздней ошибки/завершения подписок AI-клиента и использовать его для всех внутренних replay-подписок. Явно описать, как клиент сообщает окончание текущего remote и кто создаёт клиента следующего SC1 generation. Не требуется, чтобы AI-клиент сам выбирал ресурс, изменял разрешения, пересоздавал транспорт или повторял команды.

Конкретный API остаётся на стороне библиотеки. Не нужно глобально подавлять ошибки `replaySubscribe`: неизвестные ошибки должны оставаться наблюдаемыми и различимыми от ожидаемого завершения.

## Критерии готовности

1. Внешний отзыв после выполненного `ready` не выбрасывает необработанного исключения; потребитель получает объяснимое терминальное состояние или ошибку.
2. Завершение обрабатывается и для state replay, и для semantic events replay. Проверить первоначальную ошибку, позднее завершение, прерванный catch-up и закрытие до готовности.
3. `close()` идемпотентен. После close не приходят новые пользовательские callbacks; нет позднего глобального throw.
4. Смена generation не использует прежний remote для нового ресурса и не повторяет createRun/подтверждение автоматически. Новый клиент восстанавливает разрешённое состояние через библиотечный replay.
5. Отзыв одной сессии не завершает остальные независимые AI-клиенты и общий host. Проверить две сессии и две роли.
6. Потеря транспорта и отключение сервера имеют документированное поведение; не заявлять автоматическое продолжение через уже терминальный SC1 remote.
7. Проверить React-композицию `useOwnedClient`/`useClientStore` и очистку прежнего generation. Ошибка не должна оставаться только в уже выполненном `ready`.
8. Опубликовать точную npm-версию, адаптировать пример через новый публичный API и прогнать самостоятельный repro вместе с проверкой внешнего отзыва в приложении.

Описанные дополнительные варианты — критерии исправления. Непосредственно воспроизведён внешний отзыв одной SC1-сессии после завершённого AI-задания и три варианта управления клиентом из таблицы.

## Проверенная временная композиция приложения

Для экрана, которому достаточно lifecycle state, можно использовать `createStore<AiRunStore>` и `syncStoreReplay(store, remote.ai.state, {onError})`. Обработчик передаёт ошибку в наблюдаемое состояние UI и очищает устаревшие runs/approvals/inputs. Команды вызываются на том же `remote.ai`; AI host, checkpoint, типизация, RPC и replay сохраняются библиотечными. Семантические delta/tool events в этой композиции не подписываются и не изображаются в интерфейсе.

В React: владеть таким небольшим зеркалом через `useOwnedClient` с ключом remote; читать его store через `useClientStore`. Поздняя ошибка хранится отдельно от Promise `ready`, например в маленьком lifecycle Store. При новом SC1 generation создаётся новое зеркало. Вариант `--safe-state` проверяет этот путь без нового транспорта и без обращения к private API.

Это временная ограниченная композиция для state-only UI, не копия общего AI-клиента и не основание откладывать библиотечную задачу. Примеру, которому нужны semantic events, потребуется аналогичный публичный error-aware consumer этих событий или исправленный AI-клиент.
