# GRAPHICAL-DROP-NAVIGATION: политика целей и клавиатуры для двумерной доски

Дата: 26 сентября 2026. Проверена установленная опубликованная пара **wenay-react2 5.0.0 / wenay-common2 3.1.1**.

**Статус: запрос развития публичного API, не подтверждённый дефект.**
Документ не меняет статус дефектов в CURRENT-HANDOFF и не требует немедленной замены работающих интерфейсов.
Проверка выполнена по опубликованным export declarations и документации; отдельный browser repro библиотеке не запускался.

## Реальный сценарий

В [недельном графике organizer](../../apps/pizzeria/organizer/schedule-week.tsx) строки — сотрудники,
столбцы — даты, внутри клетки находится список задач. Приложение представляет каждую клетку как колонку `useReorderBoard`:
`backlog`, `[сотрудник A, понедельник]`, `[A, вторник]`, …, `[B, понедельник]`.

Стандартная клавиатура корректно выполняет документированную навигацию по этому плоскому списку:
Left/Right меняют колонку, Up/Down меняют позицию карточки внутри колонки.
Для графического календаря желательно выбирать дату горизонтально и сотрудника вертикально,
сохраняя отдельную возможность выбрать позицию внутри клетки. Переход с последней даты A на первую дату B
по Right не соответствует расположению клеток на экране.

Сотруднику разрешена только своя строка, менеджеру — все доступные строки.
Сейчас organizer ограничивает список колонок для сотрудника и проверяет цель перед серверной командой;
назначение в чужой строке можно изменить через точный инспектор при наличии прав.
Это рабочая композиция, но у неё нет общей политики допуска цели и двумерной навигации при сохранении всех отображаемых колонок.

Второй связанный потребитель — [график booking](../../apps/booking/frontend/schedule-card.tsx):
даты и ресурсы задают клетки, внутри них — реальные интервалы времени. Он использует `useDraggableApi`,
а доступность, совместимость услуг и ближайшие интервалы вычисляет приложение по серверному ответу.
Ему тоже нужны разрешённые цели и согласованная клавиатура, однако это **не готовый адаптер `useReorderBoard`**:
временная координата не является индексом карточки. Календарную модель в библиотеку переносить не предлагается.

## Какие публичные API проверены

| Публичный API | Что предоставляет | Почему текущую задачу не закрывает |
| --- | --- | --- |
| `wenay-react2/react`: `useReorderBoard`, `BoardPosition`, `ReorderBoardOptions` | Колонки `{key, items}`, `canDrag`, preview/overlay, callbacks, `over`, отмена, edge scrolling | В типах нет `canDrop`, resolver клавиатурной цели или публичного setter `over`. `canDrag` разрешает начало жеста, а не отдельную цель |
| `wenay-react2/react`: `useReorder` | Reorder внутри одного списка, настраиваемый `move`, CSS wrapped grid | Нет перемещения между контейнерами; `move` задаёт результат порядка, а не соседнюю пространственную клетку |
| `wenay-react2/react`: `useDraggableApi` | Общий владелец mouse/touch/keyboard, `Position`, `setPosition`, callbacks и отмена | Нет реестра дискретных целей или выбора разрешённого соседа; координаты и ограничения принадлежат приложению |
| `wenay-react2/grid` | AG Grid, ColumnGrid, конфигурация колонок, chrome таблицы | Это табличный API, не навигация карточки по пользовательским drop-клеткам |
| `wenay-react2/core`, `/native`, `/ui`, `/windows` | Headless utilities, column state, UI и окна | Публичного подходящего spatial drop API в этих export declarations не найдено |

При аудите прочитаны файлы установленного пакета в `apps/pizzeria/node_modules/wenay-react2/`:
публичный barrel `lib/react/index.d.ts`, типы `lib/internal/hooks/useReorderBoard.d.ts`
и `lib/internal/hooks/useDraggable.d.ts`, руководство `doc/wenay-react2.md` (Drag / Floating Windows).
Эти файлы появляются после установки зависимостей и не входят в чистый clone.
Точная зависимость указана в [package.json](../../apps/pizzeria/package.json),
использование API — в [доске](../../apps/pizzeria/organizer/board.tsx)
и [календаре](../../apps/pizzeria/organizer/schedule.tsx).
Физические пути `internal` относятся к declarations, реэкспортированным публичным barrel; приложение их не импортирует.
Руководство явно обещает board Left/Right по колонкам и оставляет координаты, ограничения и сохранение free drag приложению.

## Минимальное предложение для обсуждения

Сохранить существующее поведение `useReorderBoard` по умолчанию. Рассмотреть два необязательных расширения:

1. Предикат допустимой цели, получающий ключ карточки, исходную и предложенную `BoardPosition`.
   Одинаковая проверка применяется к pointer, touch, клавиатуре, preview и финальному drop.
2. Resolver клавиатурного соседства, получающий текущее положение, направление и доступные колонки,
   возвращающий следующую `BoardPosition` либо отсутствие перехода.
   Приложение сопоставляет ключи клеткам и решает, означает ли направление смену строки, даты или индекса.

Имена и окончательные типы должен выбрать автор библиотеки. Отдельный spatial framework, новый renderer,
imperative изменение серверных данных и предметные правила календаря не требуются.
Если расширение противоречит намеренно узкому контракту board, достаточно зафиксировать эту границу в документации;
текущие формы и композиция с `useDraggableApi` остаются допустимым решением.

## Критерии приёмки расширения

- Без новых опций существующие list/board примеры сохраняют прежнюю клавиатуру и порядок callbacks.
- На нейтральной сетке 2 строки × 3 колонки resolver даёт ожидаемые соседние клетки, включая пустые;
  граница сетки сохраняет текущую цель, а явно исключённая клетка не становится preview или drop-целью.
- Все отображаемые колонки могут оставаться в DOM; запрет отдельных целей не запрещает просмотр или начало допустимого жеста.
- Pointer/touch и клавиатура используют один предикат цели. Изменение разрешений или состава клеток отменяет устаревший жест.
- Preview и итоговый callback описывают одну цель; подтверждение вызывает не более одного commit, Escape/blur/unmount — ни одного.
- Изменение клавиатурной цели доступно потребителю для объявления и прокрутки в видимую область без приватных методов.
- Тесты библиотеки проверяют навигацию и lifecycle без зависимостей от дат, сотрудников, услуг, депозитов или вместимости.

Приложения сохраняют ревизии, ACL и финальную серверную проверку независимо от любого UI-предиката.
