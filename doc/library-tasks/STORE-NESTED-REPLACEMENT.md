# Observe: замена родителя с сохранением элементов вложенного массива

Статус: **воспроизведённый дефект**, `wenay-common2@2.21.1` из npm. Библиотека внутри примера не изменялась. Связанный пример — история версий статей в `apps/support`.

## Сценарий

При сохранении новой редакции статьи приложение создаёт новый объект статьи и дополняет массив её прошлых редакций. Старые элементы массива берутся из реактивного состояния. Это обычное обновление вложенных объектов; публичная документация Observe описывает `store.state` как reactive data object с обычной записью и не оговаривает запрета такого обновления.

## Минимальное воспроизведение

Только опубликованный публичный экспорт:

```ts
import {createStore} from 'wenay-common2/observe'

const store = createStore({article: {title: 'first', history: [{title: 'previous'}]}})
store.state.article = {
    title: 'second',
    history: [...store.state.article.history, {title: 'first'}]
}
store.snapshot()
```

Фактически `snapshot()` выбрасывает `RangeError: Maximum call stack size exceeded`. В стеке повторяется `Object.ownKeys` в `lib/Common/Observe/reactive.js:241` и `Reflect.ownKeys`. Воспроизведено отдельно от сервиса, без сети, ИИ, Docker и пользовательского интерфейса.

Ожидается конечный снимок:

```json
{"article":{"title":"second","history":[{"title":"previous"},{"title":"first"}]}}
```

Рабочий воспроизводитель: [store-nested-replacement-repro.ts](../../apps/support/backend/store-nested-replacement-repro.ts).

Из каталога `apps/support`:

```text
node --import tsx backend/store-nested-replacement-repro.ts
```

Этот режим подтверждает именно известный дефект и отдельно проверяет безопасный вариант. После публикации исправления критерий приёмки запускается так:

```text
node --import tsx backend/store-nested-replacement-repro.ts --expect-fixed
```

На 2.21.1 первый режим завершается успешно; второй падает с указанным RangeError.

## Безопасная адаптация примера

Перед заменой родителя отделяем простые снимки элементов массива:

```ts
const history = store.state.article.history.map(version => ({...version}))
store.state.article = {title: 'second', history: [...history, {title: 'first'}]}
```

В нашем формате элемент версии содержит только строки и числа, поэтому поверхностной копии достаточно. Это не общая рекомендация неглубоко копировать произвольные вложенные структуры. Реализация находится в `articleHistory()` в [domain.ts](../../apps/support/backend/domain.ts).

В документации также проверены `Observe.toRaw`, `store.snapshot`, `store.node.*.snapshot` и контракт реактивности. Это полезные явные средства отделить данные, но ожидаемое исправление не должно требовать переписывания обычного массивного обновления в каждом потребителе.

## Минимальное задание библиотеке

Исследовать хранение/нормализацию proxy-значений при записи нового объекта с элементами из старого реактивного поддерева. Гипотеза о причине: сохранённый proxy элемента при смене родителя начинает разрешаться через себя. Это гипотеза, а не подтверждённый разбор внутреннего алгоритма.

Критерии готовности:

1. Воспроизводитель с `--expect-fixed` возвращает ожидаемый снимок.
2. После замены родителя изменение сохранённого элемента продолжает отражаться в снимках и уведомлениях подписчика.
3. Повторение замены/добавления и ограничение истории через `slice(-20)` не вызывает рекурсию.
4. Репликация/patch/snapshot round-trip даёт те же значения без proxy-артефактов.
5. Проверены соседние варианты: замена самого массива, родителя массива и перенос элемента между ветками. Если какие-то формы алиасов намеренно запрещены, это явно документировано и отказ понятен; без бесконечной рекурсии.

Задача относится к Observe библиотеки, а хранение редакций, лимит истории, публикация и права остаются в приложении.
