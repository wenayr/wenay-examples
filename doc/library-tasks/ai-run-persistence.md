# A1 — восстановление AiRunHost и receipts после рестарта

**Закрыто в 2.20.0.** Публичные initial/persistence/recovery подключены через `openAiCheckpoint`. `npm run test:ai-persistence` проверяет диск, обрыв append, input/approval, права, отказ записи и принудительно завершённый процесс. [Принятие релиза](../changes/common2-2.20.0.md). Ниже — исходная постановка; старый `ai-restart-repro` демонстрирует in-memory режим без persistence и больше не доказывает пробел API.

Проверено на npm `wenay-common2@2.19.0`, потребитель `wenay-react2@3.3.0`. Это недостающий публичный контракт для устойчивого сервера, а не дефект заявленной in-memory реализации.

## Сценарий и воспроизведение

Голосовое принято, внешний провайдер начал обработку. Сервер перезапустился до подтверждения клиенту. Повтор того же owner/requestId не должен незаметно запускать оплачиваемую работу заново. Аналогично должны восстанавливаться завершённые результаты и ожидающие подтверждения/ввода операции.

В `apps/pizzeria`: `npx tsx organizer/ai-restart-repro.ts`. Реальный публичный AiRunHost с локальным runner: внутри одного host два одинаковых запроса дают один вызов; после пересоздания host тот же запрос даёт второй вызов. Проверка не обращается к ИИ и не расходует деньги.

Проверены `AiRunHostDeps`, `createAiRunHost`, `connection`, `createAiRunClient`: у host есть runner/capabilities/policy/id/now/history, нет initial/persistence. Публичный Store не заменяет восстановление закрытого индекса requestIds, входов runner и ожидающих promises. Вручную менять Store ради имитации восстановления нельзя считать поддерживаемым решением.

## Минимальная задача

Дать поддерживаемые initial + persistence port для состояния запусков и receipts, либо поддерживаемый адаптер композиции с существующим архивом. До внешнего эффекта запрос и его идентификатор должны иметь подтверждённую долговечную запись. Ошибка записи должна блокировать запуск. Ключ включает владельца; повтор с изменённым входом должен явно отклоняться.

Отдельно определить политику восстановления running: состояние неопределённого исхода или требование сверки с провайдером. Не запускать автоматически повторный внешний запрос. Queued/waiting_input/waiting_approval восстанавливать только по описанному контракту; вход, ресурсы, отмена и результат должны быть согласованы. Библиотека не выбирает провайдера, тариф, комнату, аудиоформат или правила создания задач.

Не обещать exactly-once внешний эффект без идемпотентности/сверки самого провайдера. Восстановление состояния не устраняет окно между внешним эффектом и его локальным подтверждением.

## Приёмка

- Перезапуск до runner, во время IO, после результата и при ожидании подтверждения; одинаковые запросы не запускают скрытые повторы.
- Ошибка/частичная запись persistence; корректная последовательность write-before-effect и явный неопределённый исход.
- Отзыв прав во время восстановления, доступ только владельцу и доступным ресурсам, отмена и поздний результат.
- Существующие in-memory потребители работают без обязательного диска; точные публичные импорты и пример восстановления.

В примере сейчас сохраняются готовые предложения в conversation facts; подтверждённые задачи и их receipts — в обычном service archive. Незавершённые ИИ-запуски не восстанавливаются и автоматически не повторяются. Это ограничение явно показано в интерфейсе. Пользователь выбрал работу без платных запросов.
