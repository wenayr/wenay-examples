# C6 — бинарный HTTP/storage адаптер (дополнительный кандидат)

common2 2.17.0, пример 0.8.0. Это запрос небольшого storage adapter, а не утверждение, что библиотека вообще не умеет файлы.

**Факт.** `backend/dish-media.ts:7-55` повторяет общую часть upload/immutable read: лимит тела, hash ID, временный файл, повторная авторизация перед commit, rename, очистка временного файла, проверка имени и nosniff/cache headers. В доменное состояние попадает только ID. Эту же механику потребуют аватар или вложение в другом продукте.

**Проверено.** `Resource.createFileJobHost` имеет `FileStoragePort` beginUpload/confirmUpload/download; Artifact предоставляет storage.open/remove и retention; server/fs экспортирует key volume/replay storage. Значительная часть lifecycle уже существует, а приём/атомарное хранение сырых bytes остаётся storage port потребителя. Media entrypoint про источники/маршруты медиа, а не конкретный HTTP blob store.

**Работа.** Сперва показать минимальный адаптер существующего Resource/Artifact storage port для локального HTTP binary IO. Если самостоятельный immutable blob проще без job lifecycle, выделить только общий storage/HTTP примитив и показать интеграцию с существующими портами. Настраиваемые byte limit, validator, authorize, ID strategy и путь; не жёстко зашивать фотографии или роли пиццерии.

**Приёмка.** Oversize/traversal отвергаются; отказ IO или прав не оставляет временный файл/опубликованный объект; одинаковые bytes дают один объект при выбранной hash strategy; авторизация выполняется перед чтением тела и перед commit. Правила изображения/декодирования передаются валидатором: проверку сигнатуры нельзя объявлять полной проверкой безопасности содержимого. Метаданные можно вести через уже существующий runtime. Сырой файл не идёт в replay. Удаление/retention задаются явно; снятие фото с карточки не удаляет байты старого заказа автоматически.
