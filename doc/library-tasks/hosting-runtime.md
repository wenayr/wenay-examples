## Задание для разработчика библиотеки

Проверьте существующие публичные примитивы common2 и сократите повторяющуюся оркестрацию двух реальных исполнителей: [Docker](../../apps/hosting/backend/agent.ts) и [LXD](../../apps/hosting/backend/lxd-agent.ts). Сначала покажите композицию уже доступных API. Если она устраняет повторение и сохраняет поведение, нового API не требуется. Иначе предложите минимальное расширение с выводом типов из реализации и фасадом фабрики. Не переносите Docker/LXD, правила развёртывания, HTTP gateway или схему хостинга в библиотеку.

### H1. Исполнитель повторной сверки состояния — основной кандидат

Сценарий: агент подписан на представление назначенных работ. Пока он ждёт внешний IO, приходят новые изменения. Нужно закончить текущий проход, затем прочитать свежий снимок и выполнить ещё один проход. При временной ошибке нужен отложенный повтор, при остановке — отмена и освобождение ресурсов.

В обоих агентах вручную поддерживаются `busy`, `dirty`, `running`, отписка, таймеры повторов и `AbortController`. Политики повторов различаются: Docker хранит их по операциям, LXD использует общий таймер. Это повторение механизма, а не основание сделать все политики одинаковыми.

Проверено: публичный `createAsyncQueue(1)` выполняет каждую поставленную задачу; десять уведомлений дают десять запусков. Это правильное поведение очереди. Публичные throttle/debounce также существуют. Предлагаемая композиция должна дополнительно объединять уведомления во время IO, управлять остановкой и сообщать об ошибках. Не добавляйте ещё одну обычную очередь.

Критерии готовности:

1. Во время одного прохода поток уведомлений требует не более одного ожидающего прохода, без неограниченной очереди. Новый проход получает свежий снимок; уведомление в момент завершения не теряется.
2. Один исполнитель не запускает проходы одновременно. Если вводятся ключи, явно определены общий предел параллельности и очистка завершённых ключей.
3. Задержка и решение о повторе задаются потребителем. Успешное новое выполнение не оставляет ненужных повторов; сбой не вызывает горячий цикл.
4. `close()` идемпотентен: запрещает новые запуски, отменяет ожидания, снимает принадлежащие ему подписки и таймеры, ждёт завершения прохода в рамках явно заданного контракта отмены. Ошибка не превращается в необработанное отклонение Promise.
5. Проверки покрывают уведомления до/во время/после IO, ошибку, остановку во время повтора и несколько вызовов `close()`.
6. В обоих агентах действительно удаляется дублирующаяся оркестрация, а существующие сценарии развёртывания, восстановления и принадлежности ресурсов продолжают проходить.

Граница: это локальный исполнитель. Он не даёт распределённую блокировку, fencing или exactly-once внешнего IO. Потерянный ответ провайдера нельзя автоматически считать неуспехом и создавать новую операцию. Идентификаторы заявок и проверки текущего состояния перед удалением ресурса остаются обязанностью приложения.

### H2. Публичная область владения ресурсами — дополнительный кандидат

Сценарий: создание агента последовательно приобретает lock-файл, клиент, подписки и сетевые ресурсы. Ошибка посередине должна освободить уже созданное; остановка должна корректно завершить работающий проход. Сегодня эти связи вручную описаны в двух фабриках агентов.

Проверено: `installServiceSignals` уже публичен в `wenay-common2/service/host` и применён в обеих точках запуска. Его повторно реализовывать не нужно. В установленном пакете есть внутренний `createHostLifecycle`, но он не экспортирован публичной точкой `service/host`. Пример не должен импортировать его по приватному пути. Кроме того, внутреннее освобождение независимых ресурсов выполняется параллельно: это нельзя молча принять за последовательное завершение зависимых ресурсов.

Сначала оцените возможность публичной композиции или аккуратного расширения существующего lifecycle. Не экспортируйте внутреннюю реализацию без определения контракта.

Критерии готовности:

1. Частичный сбой запуска освобождает приобретённые ресурсы и сохраняет исходную причину ошибки.
2. Одновременные остановки разделяют один результат. Ресурс, завершивший создание после отмены, также освобождается.
3. Явно различаются зависимые последовательные шаги завершения и независимые disposers; ошибки одного не пропускают остальные.
4. Описаны предел ожидания и поведение IO, который не поддерживает отмену. Таймаут не выдаётся за гарантированное завершение внешнего действия.
5. Есть проверки частичного старта, позднего приобретения, повторного закрытия и ошибки освобождения. После внедрения общий API заменяет ручное владение в обоих агентах.

H1 и H2 можно решить одной небольшой композицией; количество новых экспортов не является целью. Прежняя задача C4 о lifecycle хоста уже закрыта и здесь не переоткрывается.

### H0. Документация Store через await — без изменения API

При разработке Docker-очистки обнаружена ошибка приложения: ссылка на `store.state` переживала `await` и изменялась вместе с Store. Это живое состояние по контракту. Уже существующий `store.snapshot()` даёт отдельный снимок; он применён в Docker- и LXD-проходах.

Полезно добавить в документацию короткий пример сверки с внешним IO: снимок для одного прохода, а перед опасным действием — повторная проверка актуального состояния. Снимок не замораживает внешний мир и не заменяет транзакцию или fencing.

Критерий: пример показывает изменение вложенного массива и поля активной операции через `await`, разницу `state`/`snapshot()`, пределы гарантии снимка. Минимальное доказательство уже есть в [library-audit-check.ts](../../apps/hosting/backend/library-audit-check.ts).

## Проверка и внедрение

Из `apps/hosting`: `npm run test:library-audit` проверяет снимок, существующую очередь и идемпотентное закрытие обработчиков сигналов. Это проверка текущих публичных возможностей, а не тест ещё не реализованных H1/H2. `npm run typecheck` и `npx tsx backend/lxd-check.ts` прошли после их применения в этом аудите.

Для H1/H2 потребуются отдельные проверки нового контракта и существующие `agent-check.ts`/`lxd-check.ts`. Настоящие Docker-сценарии уже проверены в 0.4.0; настоящий LXD здесь не запускался. При внедрении использовать опубликованную точную npm-версию, затем проверить оба агента последовательно. На этой машине максимум 3 ГиБ RAM, целевой расход 1–2 ГиБ; VM и Kubernetes для этих проверок не нужны.

## За пределами текущего пакета

Распределённое владение операциями с lease/attempt/fencing понадобится для нескольких агентов одного пула. Наличие receipts и лидерства сервиса само по себе не ограждает внешние Docker/LXD-запросы. Это отдельный будущий сценарий с воспроизведением потери владения и запоздалого результата, пока не доказанный дефект или готовое задание на универсальный планировщик.

В проверенной части react2 нового пробела не найдено: `useOwnedClient`, `useClientStore`, `useAsyncAction` и `useServiceCommands` покрывают текущие потребности интерфейса. Предметные формы и подписи не требуют нового библиотечного конструктора.
