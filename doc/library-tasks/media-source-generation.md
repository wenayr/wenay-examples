# M1 — поздний MediaRecorder chunk попадает в новую запись

**Закрыто в 2.20.0.** `npm run repro:media-generation -- --expect-fixed` проходит; проверка включена в общий test. [Принятие релиза](../changes/common2-2.20.0.md). Ниже — историческая постановка 2.19.0; режим без флага ожидает старый дефект и не предназначен для нового релиза.

Подтверждено на npm `wenay-common2@2.19.0`. Потребитель `wenay-react2@3.3.0` использует тот же источник через `useMediaSource`.

## Воспроизведение

В `apps/pizzeria`: `npx tsx organizer/media-generation-repro.ts`. Контролируемый fixture заменяет только браузерный MediaRecorder/MediaStream; фабрика `createAudioSource` и кодек импортированы из опубликованного `wenay-common2/media`.

1. Начать источник в `mode: 'record'`.
2. Его `ondataavailable` ждёт `Blob.arrayBuffer()`.
3. Вызвать stop, затем start того же источника.
4. Завершить старый arrayBuffer.
5. Слушатель новой записи получает старый payload `[17]`.

Проверка подтверждает наблюдаемое поведение через публичный listen; это не запись реального микрофона. `--expect-fixed` сейчас падает, после публикации должен проходить.

## Минимальная задача

Привязать асинхронные callbacks источника к поколению записи и проверять актуальность после await. Определить, допускается ли финальный chunk после stop, и как он адресуется завершённой записи. Он не должен смешиваться с новой записью или передаваться новому потребителю. Отсоединять старые callbacks и обрабатывать их ошибки без unhandled rejection.

Проверить также поздние media callbacks и ошибки start после stop/new start, чтобы прошлый запуск не останавливал и не переводил новый в error. Последнее — критерий проверки, не отдельный доказанный данным repro дефект.

## Приёмка

- Старый отложенный chunk, stop/start и смена источника; новая запись получает только своё поколение.
- Ошибка старого arrayBuffer, завершение tracks, закрытие подписки и React unmount.
- Если финальные данные поддерживаются, их завершение имеет явный контракт; документация и regression тест.

Текущий пример голосовых сообщений использует bounded PCM→WAV и не зависит от MediaRecorder. Не нужно переносить в библиотеку лимит 12 секунд, WAV-политику приложения или формат сообщения.
