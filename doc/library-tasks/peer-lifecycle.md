# PC1 / PC2: завершение peer-подключения и RPC-клиента

**Закрыто 10 сентября 2026 года:** опубликованный common2 2.18.2 установлен в обоих приложениях. Локальное и оба сетевых воспроизведения в режиме `--expect-fixed` проходят. `npm run test:peer` проверяет исправление и включён в обычный `npm test`. Ниже — исходная постановка для 2.18.1; без `--expect-fixed` скрипты предназначены только для воспроизведения прежних дефектов.

Статус: два воспроизведённых дефекта common2, 9 сентября 2026 года. Установлен и проверен npm `wenay-common2@2.18.1`; окружение `wenay-react2@3.3.0`, Node.js 24.18.0, Windows. React не участвует в воспроизведении и не объявляется причиной. Зависимости только опубликованные, изменений в node_modules нет.

Потребитель — совместная доска органайзера. При уходе из комнаты старое подключение освобождается, но соединение с приложением может оставаться открытым для других функций. Дефекты относятся к общему lifecycle peer/RPC; карточки, координаты курсоров и роли сотрудников библиотеке передавать не нужно.

## PC1. Закрытое подключение продолжает публикацию и signaling

### Запуск

Из `apps/pizzeria`:

```sh
npm ci
npm run repro:peer-close
npm run repro:peer-network
```

Файлы: [локальное минимальное воспроизведение](../../apps/pizzeria/organizer/peer-close-repro.ts), [сетевое воспроизведение](../../apps/pizzeria/organizer/peer-network-check.ts). Второе использует реальные Socket.IO/RPC, service-issued tokens и серверные ID сессий; это тестовый стенд, а не новый runtime продукта.

Локальные шаги:

1. Создать `createPeerHost`, подключения sender/receiver и подписку на сигнал receiver.
2. Опубликовать начальный patch и доставить контрольный сигнал.
3. Вызвать `sender.close()` дважды; sender исчезает из presence.
4. Через сохранённый `sender.fragment` вызвать `publish`, `publishBatch` и `signal.send`.
5. Отдельно начать отправку с ожидающим Promise в `authorize`, закрыть sender и разрешить ожидающую авторизацию.

На 2.18.1 одиночная и пакетная публикации возвращают `true`, меняют состояние relay; сигнал доставляется после закрытия. Отправка, начатая до закрытия, также доставляется после завершения `authorize`. Фактический вывод:

```json
{"published":true,"singleChanged":true,"batchPublished":true,"batchChanged":true,"sent":true,"deliveredAfterClose":1}
{"pendingAfterClose":true,"delivered":1}
```

Сетевой вариант закрывает именно комнатное подключение, оставляя родительский RPC живым. Сохранённый удалённый `peer.publish` меняет курсор наблюдателя на `777`. В момент вызова sender уже отсутствует в списке присутствия.

### Ожидание и границы

`connection.close()` должен быть терминальным для принадлежащих этому подключению исходящих действий: последующие публикации и сигналы отклоняются или возвращают предусмотренный контрактом отказ, состояние и получатели не меняются. Проверка жизни нужна также после асинхронной авторизации. Простого удаления sender из presence недостаточно.

Это **не** доказательство обхода полностью отозванного RPC principal и не проверка остановки настоящего WebRTC-медиапотока. В сетевом стенде закрыто комнатное подключение, а RPC намеренно продолжает существовать. Исправление локального close также не заменяет серверную авторизацию и изменение доступного пользователю RPC-фасада.

### Приёмка

- Сохранённые `publish`, `publishBatch`, `signal.send` после close не дают эффекта; в том числе повторный close.
- Отправка, ожидающая `authorize`, не доставляется после закрытия её подключения.
- Другое живое подключение, в том числе того же аккаунта, продолжает работать. Закрытие одного не закрывает общий relay для всех.
- Штатное завершение всего host остаётся корректным.
- Локальный `npm run repro:peer-close -- --expect-fixed` проходит. Сетевая проверка в режиме исправления проходит после устранения также PC2.
- Уточнить документацию: что освобождается при close, какие сохранённые методы становятся недействительными, что остаётся обязанностью внешнего RPC-владельца.

Не требуется менять порядок сообщений, придумывать новые комнаты или вводить новую систему прав. Исправить terminal state существующей композиции peer/signal.

## PC2. Закрытие peer-клиента и hub даёт unhandled RPC_ABORT

### Независимое воспроизведение

```sh
npm run repro:peer-network -- --shutdown-only
```

Этот режим **не вызывает** публикацию после закрытия из PC1. Он создаёт три настоящих RPC-соединения, два независимых курсора и два наблюдения у третьего клиента. После готовности представлений и получения обновлений вызывает:

```ts
manager.client.close()
manager.hub.close()
```

Оба метода публичные; `createPeerClient.close()` имеет синхронный контракт. Потребитель не получает Promise завершения его внутренних отписок, который мог бы ожидать.

Результат на 2.18.1: две необработанные ошибки с содержимым:

```json
{"error":{"name":"RPC_ABORT","message":"RPC hub closed"}}
```

Первый запуск без диагностического обработчика завершился с `ERR_UNHANDLED_REJECTION`. В сохранённом воспроизведении временный обработчик собирает эти ошибки, проверяет точное содержимое и печатает `REPRODUCED`. Это фиксация дефекта, не production-обход и не положительная проверка безопасного завершения. Неизвестные ошибки приводят к провалу воспроизведения.

### Приёмка

- `npm run repro:peer-network -- --shutdown-only --expect-fixed` проходит с нулём необработанных Promise-ошибок.
- Последовательность «закрыть peer, сразу закрыть hub» корректна. Не требовать от приложения случайной задержки между ними.
- Проверить закрытие при открытии подписки, после её готовности, при активном обновлении и при потере транспорта; освобождение повторяемо.
- Если требуются изменения низкоуровневого RPC unsubscribe/lifecycle, исправлять владельца Promise; не добавлять глобальный `unhandledRejection` или подавление всех ошибок в React/примере.
- После исправления обоих дефектов проходит `npm run repro:peer-network -- --expect-fixed`, а положительный `npm run test:peer-contract` остаётся зелёным.

Точная внутренняя причина PC2 не утверждается: воспроизведена проблема **композиции peer/RPC при завершении**, а не отдельно доказан дефект конкретной внутренней функции.

## Что уже работает и не требует задачи

`npm run test:peer-contract` подтверждает отдельные room-host, независимые peer ID для вкладок, актуальное состояние за пределами короткой истории, account-level подсчёт присутствия и сохранение второй сессии после закрытия первой. Сетевой стенд подтверждает два курсора через реальный RPC и очистку presence после штатного отключения socket.

Это не тест аварийного истечения присутствия, полного отзыва прав или межузлового восстановления. Такие проверки остаются этапом S1/S5. Срок актуальности курсоров, сопоставление сессии аккаунту и предметная видимость задач пока не объявлены недостатками библиотеки.
