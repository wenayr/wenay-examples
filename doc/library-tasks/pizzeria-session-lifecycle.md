# Задание common2: жизненный цикл ролевого клиента

**Статус: применено в примере 0.8.0 (common2 2.17.0).** Проверены реальные клиенты, отзыв/возврат роли и сетевые сценарии. Ниже сохранена исходная постановка, а не список отсутствующих API. См. [результат внедрения](../changes/0.8.0.md).

Работать в исходном scaffold/генераторе `wenay-common2`, затем выпустить npm-версию. Потребитель: `wenay-examples/apps/pizzeria@0.4.0`, common2 2.16.0, react2 3.1.0. Это улучшение интеграции высокоуровневого клиента; отсутствие нужных низкоуровневых примитивов не утверждается.

## Сценарии и фактическое поведение исходного адаптера

Менеджер держит открытый склад на serving node. Владелец снимает роль. Набор выданных команд и закрытых линий был построен при подключении, а ранее созданная проекция продолжала использовать прежний доступ. Повторная серверная проверка команды защищает запись, но сама по себе не прекращает чтение из выданной линии.

Отдельно: клиент создаётся с `{auth:{token}}`. В адаптере продление возвращало тот же токен; истечение срока нарушало длительную работу и последующее переключение заведений.

## Проверенные поверхности и текущее решение потребителя

Публичные `deriveStore` и `exposeStoreReplay` позволяют проверять доступ в проекции по текущему локальному состоянию. `StoreNodeSession.onGone` освобождает её. Низкоуровневый `RpcServerControl.grant` существует, но используемый callback `StoreNodeSession` не предоставляет пересборку разрешений как готовую операцию сервиса. Поэтому нельзя объявлять это отсутствием regrant во всей библиотеке.

В приложении закрытые линии теперь отдельные для сессии, даже если данные общие для роли. После отзыва они очищаются; public-линии остаются общими. `identity.me()` возвращает свежие роли/команды/представления, браузер сверяет их раз в секунду и пересоздаёт клиент. Продление использует имеющийся identity facade и callback нового токена.

## Доработка

Обновить общий клиент и access scaffold. По возможности дать высокоуровневую реактивную смену разрешений без ручного опроса в каждом UI, используя существующие механизмы библиотеки. Сохранить проверку команды на authority. При совместном использовании проекций отдельно решить прекращение чтения отозванной сессией, не возвращая прежнюю утечку обновлений.

## Воспроизведение и приёмка

1. Authority + serving node, менеджер открывает inventory через RPC. Владелец снимает роль и изменяет склад. Старая подписка после применения роли локальной репликой не должна получать новые закрытые значения; это проверяется без сотрудничества UI.
2. Вернуть роль: открытый клиент получает нужный фасад без ручного выхода/входа. Запрещённые команды нельзя выполнить через сохранённую ссылку.
3. Повторить с общей по содержимому проекцией, несколькими сессиями и переходом на другой serving node. Права одного клиента не должны влиять на остальных.
4. Создать клиента с коротким готовым токеном. Убедиться, что до истечения происходит продление, новый токен доступен потребителю и работает после переподключения.
5. Закрыть клиент во время ожидания: соединения, линии и таймеры освобождаются. Явно описать задержку отзыва на репликах и последствия потери связи с authority.

Базовые исполняемые проверки уже есть: `npm test` в приложении (отзыв линии в `backend/check.ts`, продление в `backend/network-check.ts`). После публикации сообщить точную версию, затем заменить адаптер только через публичные npm-экспорты и повторить весь сценарий.
