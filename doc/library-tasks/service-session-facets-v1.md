# SC1 v1: статические ресурсные фасады авторизованной сессии

**Закрыто после публикации common2 2.19.0.** [Внедрение в потребитель и проверки](../changes/common2-2.19.0.md). Актуальный API описан в опубликованном `doc/SERVICE-RESOURCES.md`: `definition.resources`, `client.resources.open(name)`, `resourceId` для независимого владельца. Ниже сохранена исходная постановка от 10 сентября на базе 2.18.2; предложенные в ней названия не заменяют документацию реализованного API.

## 1. Цель и отличие от загрузки кода

Дать service runtime возможность создавать заранее зарегистрированный ресурсный фасад для авторизованной сессии. Первый потребитель — peer-подключение к доске. Второй проверочный ресурс — защищённый счётчик с подпиской. Библиотека управляет доступом и временем жизни ресурса; приложение определяет его содержание.

Код фабрик уже установлен на сервере при запуске. Во время работы создаётся **экземпляр подключения**, а не загружается новый код. Аналогия: программа работы с БД установлена заранее, а соединение открывается по потребности.

Hot reload, dynamic import, плагины, установка пакетов, замена функций, деплой, миграция исполняемого кода и перенос живого экземпляра между серверами не входят в SC1. Механизм не зависит от Docker или модели данных доски.

## 2. Пользовательский путь

1. Пользователь входит в органайзер и получает обычные команды и разрешённые представления.
2. При открытии доски клиент запрашивает зарегистрированный ресурс `boardPresence`.
3. Сервер проверяет текущий principal, создаёт peer connection с серверным ID и выдаёт фасад через существующий RPC.
4. Клиент использует обычный `createPeerClient` и hooks react2.
5. Закрытие доски освобождает только этот ресурс; остальные функции приложения продолжают работать.
6. Отзыв права прекращает вызовы и доставку через существующие подписки. Сохранённая старая ссылка на фасад также перестаёт действовать.
7. После обрыва соединения прежнее поколение недоступно. Reconnect создаёт новый экземпляр и новую удалённую поверхность.

Пункты 5–7 проверяются через сохранённые ссылки и действующие подписки, а не только визуальным исчезновением курсора.

## 3. Проверенная основа

| API common2 2.18.2 | Используем | Чего сам по себе не обеспечивает |
| --- | --- | --- |
| Definition/descriptor | Контракт, вывод типов, безопасный JSON | Фабрику дополнительного ресурса с владельцем сессии |
| Service host mount | HTTP и lifecycle всего хоста | Фабрику на конкретный аутентифицированный principal |
| Service client | Токен, права, health, выбор узла | Дополнительную типизированную сессионную поверхность |
| Service access/RPC auth | Principal, admission, deadline, инфраструктуру подписок | Отзыв любого динамического поддерева по обычному pruning |
| Peer connection.close | Остановку исходящих publish/batch/signal | Прекращение чтения общего host-owned журнала |

Опубликованный `doc/RPC-AUTH.md` отмечает: подписки под `noStrict` не обнаруживаются обычным pruning principal. В 2.18.2 их корректно освобождает владелец, но они не восстанавливаются автоматически при смене поколения транспорта. `doc/PEER-LIFECYCLE.md` отдельно указывает, что закрытие peer connection не отзывает чтение общего журнала.

[Сетевой стенд примера](../../apps/pizzeria/organizer/peer-network-check.ts) подтверждает низкоуровневую композицию. Он не реализует service-интеграцию с изменением прав и сменой узла. Скопировать её в приложение целиком — не результат SC1.

## 4. Ограничения первой версии

- Реестр имён/фабрик фиксирован при запуске host. Новый тип ресурса добавляется обычным выпуском приложения.
- Ресурс принадлежит одной сессии и одному поколению доступа; вкладки одного аккаунта независимы.
- Размещение только на authority. Serving node обслуживает обычные views, но не создаёт копию комнаты.
- Первый пример — одна доска на экземпляр сервиса. Фабрика уже знает комнату; произвольные клиентские параметры фабрики не нужны.
- Ресурс открывается по запросу. Один UI-владелец, дочерние компоненты заимствуют его; общий refcount UI-владельцев не требуется.
- Фабрика и disposer могут быть асинхронными. Отмена и позднее завершение обязательно обработаны.
- Экземпляр подключения не попадает в durable-команды/архив. Собственное долговечное хранилище ресурса имеет отдельного владельца.
- Команды ресурса автоматически не повторяются. Reconnect восстанавливает доступ, а не переисполняет неизвестный внешний эффект.
- Приёмка v1 использует relay/RPC; отзыв доступа к прямому WebRTC-медиасоединению проверяется следующим отдельным срезом.

## 5. Предлагаемая поверхность

### Сервер

Необязательный статический реестр `resources` в definition. Запись задаёт разрешения, placement `authority` и фабрику. Контекст фабрики: проверенный principal, серверный session ID и AbortSignal. Предметные зависимости передаются обычным замыканием. Результат — `{facade, close}`.

Схематический вклад приложения, **не готовый код опубликованного API**:

```ts
resources: {
    boardPresence: {
        allow: ['owner', 'manager', 'member'],
        placement: 'authority',
        open({sessionId, signal}) {
            signal.throwIfAborted()
            const connection = room.connection(sessionId)
            return {facade: connection.fragment, close: connection.close}
        },
    },
}
```

Библиотека добавляет вокруг результата защиту вызовов/подписок и владение. Сам этот объект не обеспечивает отзыв чтения журнала. ID нельзя подменить клиентским account из handshake. Общий room-host принадлежит приложению, его connection — сессии; закрытие connection не удаляет комнату.

### Descriptor и типы

Descriptor содержит только безопасные метаданные: имя ресурса, placement и необходимые декларативные возможности. Без фабрик, секретов, seed state и объектов подключения. Тип удалённого фасада выводится из definition. Вызов неизвестного ресурса/метода и неверные аргументы запрещены типами. Второй вручную поддерживаемый интерфейс и Zod не нужны.

### Клиент

Предложение вызова: `client.resources.open('boardPresence')` возвращает отдельный контроллер. Точные имена обсудить, но семантику определить до реализации:

- Наблюдаемый статус: `opening / ready / offline / denied / failed / closed`, номер поколения и безопасная ошибка.
- `current()` возвращает `{generation, remote}` только в ready; remote типизирован по имени ресурса.
- Контроллер сохраняет тождество при reconnect того же аккаунта; новый экземпляр получает **новый remote**. Старая ссылка никогда не переключается незаметно на новое поколение.
- `close()` терминален и идемпотентен. Повторный вход на доску создаёт новый контроллер.
- Каждый самостоятельный open создаёт собственного владельца/экземпляр. Приложение вызывает его один раз на владельца UI.
- Смена аккаунта терминальна для прежнего контроллера; новый вход создаёт нового владельца.

Клиентская проверка поколения нужна для понятной ошибки, но сервер остаётся источником разрешения. Статус можно читать существующим Store hook. Peer-клиент привязан к ready-поколению: закрывается вместе с ним, а новый создаётся с новым remote и синхронизируется средствами peer API. Стабильность контроллера не означает автоматического переноса его динамических подписок.

## 6. Жизненный цикл

| Событие | Сервер | Клиент |
| --- | --- | --- |
| Нет допуска | Не вызывает фабрику | denied, remote отсутствует |
| Допущенный open | Создаёт поколение, запускает фабрику | opening |
| Фабрика вернула живой результат | Публикует защищённый фасад | ready и remote поколения |
| Фабрика выбросила ошибку | Не публикует частичный фасад | failed; повтор по явному действию |
| Close во время фабрики | Запрещает поколение, abort; поздний результат закрывает один раз | closed, поздний remote не появляется |
| Close готового ресурса | Запрещает admission, отключает подписки, abort, disposer | closed, старая ссылка недействительна |
| Потеря права | Завершает scope при применении обновления на authority | denied без необходимости закрыть UI |
| Роли изменились, доступ сохранился | В v1 пересоздаёт ресурс, исключая захват старых ролей фабрикой | Новое поколение |
| Продление токена, тот же principal/роли | Обновляет deadline, сохраняет экземпляр | ready без пересоздания |
| Смена аккаунта | Завершает прежние scopes | Старый контроллер терминален |
| Истечение/отзыв токена | Завершает прежние поколения | denied; восстановление требует действительного допуска |
| Обрыв транспорта | При обнаружении завершает scopes | offline; старый remote недоступен |
| Reconnect того же аккаунта | Новая серверная сессия/поколение | Восстанавливает только не закрытые контроллеры; без повтора команд |
| Возврат права тому же аккаунту | Новый экземпляр для ещё открытого контроллера | Новое ready-поколение |
| Смена serving node | Не переносит authority-ресурс | Views могут сменить узел без второй комнаты |
| Остановка host | Запрещает scopes, освобождает ресурсы | Потеря доступности; старый host не создаёт новых поколений |

Одновременные revoke/close/disconnect сводятся к одному завершению. Нельзя полагаться только на AbortSignal: фабрика может его проигнорировать. Результат после отмены закрывается, но никогда не публикуется.

Частичные выделения внутри фабрики, бросившей ошибку до возврата результата, освобождает автор фабрики. Runtime принимает ответственность после получения `{facade, close}`.

## 7. Точная гарантия отзыва доступа

Точка линеаризации — **authority применил отзыв к scope**. После неё:

1. Новые вызовы/чтения поколения не достигают реализации, в том числе по сохранённому raw RPC-пути.
2. Новые подписки не прикрепляются.
3. Все существующие подписки этого scope, включая `noStrict`, перестают выдавать новые данные. Чужие подписки продолжают работать.
4. Ожидающая проверка допуска/создание подписки после await перепроверяет поколение; поздний handle освобождается.
5. Результат чтения, завершившегося после отзыва, не выдаётся как успешный ответ прежнего scope. Уже отправленные в сеть или ранее сохранённые клиентом данные отозвать невозможно.

Допущенный до отзыва вызов уже мог изменить внешний мир. SC1 передаёт отмену и блокирует последующую выдачу данных, но не обещает откат внешнего эффекта, exactly-once или принудительное прекращение произвольного JS. Ресурс сам определяет семантику отмены/идемпотентности.

Использовать существующие RPC admission, registry подписок, auth lifecycle и владельцев handles. Нужна доказуемая принадлежность вызовов/подписок scope либо эквивалентная композиция. Удаление имени из descriptor, peer connection.close или AbortSignal по отдельности не доказывают отзыв чтения.

Не писать рекурсивный защитный Proxy в приложении. Если нужен небольшой внутренний контракт RPC ownership, реализовать его как SC1-A и проверить до слоя service. Отзыв одного читателя не должен закрывать общий peer-host.

При сетевом разделении время обнаружения сервером ограничено heartbeat/deadline. Не обещать мгновенного исчезновения ресурса до обнаружения разрыва.

## 8. Ошибки освобождения

Логическое закрытие немедленно запрещает доступ; физический disposer может завершаться позже. Он вызывается один раз. Его сбой не возвращает ready и не пропускает освобождение других scopes. Ошибка наблюдаема владельцем, не становится unhandled Promise.

Ожидание ограничивается документированным бюджетом host/client. Таймаут означает ошибку/неподтверждённое освобождение, а не гарантированную остановку внешнего ресурса. Первичная ошибка старта сохраняется вместе с диагностикой cleanup.

SC1 владеет результатом одной фабрики; внутренний порядок её ресурсов определяет автор. Общий менеджер зависимостей, H1/H2 и библиотечный workflow не являются предпосылками.

## 9. Реализовывать небольшими этапами

**SC1-A: scope RPC и отзыв.** Без React и peer: обычный метод, подписка и динамический `noStrict` источник. Сначала доказать отзыв уже открытого потока и независимость второго scope.

**SC1-B: service-композиция.** Статический реестр, descriptor, authority-фабрика, поколения, principal/deadline/роли. Контролируемая асинхронная фабрика и счётчик, затем peer.

**SC1-C: настоящий RPC.** Socket.IO, authority, затем один serving node. Смена узла, reconnect, вкладки, два ресурса на одной сессии.

**SC1-D: органайзер.** После публикации точная npm-версия, существующие React hooks, два браузера, открытие/закрытие доски, курсоры и отзыв прав. Фильтры и видимость карточек проверяются здесь.

A/B/C относятся к библиотеке, D — к wenay-examples. Это один проверяемый результат, но не одно огромное изменение. До кода обсудить новые публичные имена и семантику; этот документ не выдаёт предложение за утверждённый API.

## 10. Обязательная матрица проверки

| ID | Сценарий | Проверяемый факт |
| --- | --- | --- |
| A1 | Close одного из двух scopes, сохранённая ссылка на метод | Старая ссылка не достигает реализации; второй scope жив |
| A2 | Revoke обычной и noStrict-подписки | Нет новой доставки; число его серверных подписок ноль |
| A3 | Подписка ждёт допуска → revoke → разрешить Promise | Нет активации; поздний handle освобождён |
| A4 | Чтение допущено → ждёт результата → revoke | Поздний результат не раскрывается прежнему scope |
| A5 | Два владельца одного источника, один закрывается | Второй получает события, в том числе при RPC deduplication |
| B1 | Анонимный/запрещённый open | Число вызовов фабрики ноль |
| B2 | Ошибка фабрики до возврата | Нет remote; видна исходная ошибка; посторонний ресурс жив |
| B3 | Задержанная фабрика → close/revoke/disconnect → результат | Ноль публикаций, один disposer |
| B4 | Конкурентные close/revoke/disconnect | Одно завершение; ноль unhandled Promise |
| B5 | Disposer отклоняется или зависает | Доступ закрыт; ошибка/таймаут наблюдаемы; успех освобождения не выдуман |
| B6 | Продление прежнего principal | Экземпляр сохранён; старый deadline не закрывает продлённый grant |
| B7 | Смена ролей/аккаунта и возврат допуска | Новое поколение; сохранённый старый remote недействителен |
| B8 | Подставленные account/sessionId | Невозможно выдать себя за другого; вкладки независимы |
| C1 | Закрыть один ресурс сессии | Другой ресурс и основные commands/views работают |
| C2 | Обрыв и reconnect | Новый синхронизированный remote; команды не повторены |
| C3 | Revoke и запрос по сохранённому raw RPC-пути | Отказ сервера без клиентского guard и React |
| C4 | Authority → serving node → authority для обычных views | Ресурс остаётся у authority; нет лишней комнаты/фабрики |
| C5 | Рестарт authority | Новое поколение; старое presence не воскресает; данные сервиса восстанавливаются своим механизмом |
| T1 | Два разных фасада, неверные имена/аргументы | Ошибки компиляции, точный вывод типов без casts |
| T2 | Descriptor и браузерный bundle | Нет фабрик, секретов, приватного state и Node-only кода |
| D1 | Два браузера и две вкладки одного аккаунта | Правильное присутствие; закрытие одного не закрывает второго |
| D2 | Смена входа/комнаты, отзыв, поздняя готовность в React | Нет прежнего remote; подписки/ресурсы освобождены |

Для A/B использовать Promise-барьеры: «вошли в authorize», «фабрика ждёт», «отзыв применён», «разрешаем завершение». Не воспроизводить гонку случайным `sleep(100)`. Для deadline — управляемое время на уровне примитива; сетевой тест ожидает наблюдаемое событие с ограниченным сроком.

Добавить небольшую модель состояний и фиксированные воспроизводимые последовательности событий. Инварианты: максимум одно активное поколение на контроллер; завершённое не оживает; каждый возвращённый ресурс закрывается один раз; после teardown нет его подписок/таймеров. При сбое сохранять seed/последовательность. Стресс дополняет таблицу, не заменяет её.

A/B доказывают порядок, C — реальные RPC-пути, D — интеграцию UI. Нельзя ограничиться только mocks или только браузером. Серверные счётчики наблюдать через тестовый диагностический фасад, не публиковать их пользователям продукта.

## 11. Комплект результата и приёмка

1. Короткое решение по публичному контракту, ownership, поколениям и authority-placement, с отличиями от предложения.
2. Минимальная реализация, A/B/C тесты, список экспортов, типовые примеры.
3. Документация static registration, динамических подписок, отзыва, reconnect, cooperative cancellation и отсутствия hot code loading.
4. PC1/PC2 и прежние service/RPC проверки зелёные. Старый definition без resources работает без обязательной новой инфраструктуры.
5. Опубликованная версия внедрена в органайзер; прежний `test:peer` и D-проверки проходят. Один только выпуск библиотеки не означает готовую совместную доску.

Лимит текущего хоста: целевой расход 1–2 ГиБ, максимум 3 ГиБ; проверки последовательные. Для A/B и малого C не нужны Docker, VM, медиасервер или локальная ИИ-модель. Непоместившаяся проверка переносится, а не объявляется пройденной.

## 12. Что остаётся приложению

Комнаты, допуск к конкретной задаче, координаты/масштаб/фильтры доски, имена/цвета, срок отображения курсора, selected/follow, рецептуры, Docker/LXD-политики и ИИ-команды. SC1 обеспечивает защищённую границу ресурса, а приложение определяет данные и действия внутри неё.

[Исходный обзор публичных границ](service-session-facets.md) сохранён для контекста; эта постановка уточняет и ограничивает первую версию. Она не открывает заново PC1/PC2 и не обещает отсутствие всех ошибок: гарантии относятся к описанной модели и выполненным проверкам.
