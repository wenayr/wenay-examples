# SC1: композиция дополнительных защищённых фасадов в service runtime

**Детальная задача первой версии:** [SC1 v1 — статические ресурсные фасады](service-session-facets-v1.md). Она уточняет этот обзор: фиксированная регистрация при запуске, authority-размещение, поколения, отзыв динамических подписок и матрица тестов. Это создание экземпляров заранее установленного кода, а не hot reload, установка плагинов или загрузка нового кода во время работы. Для реализации использовать v1; ниже сохранено исходное обоснование.

**SC1 закрыт в 2.19.0: [внедрение и проверки](../changes/common2-2.19.0.md).** Далее сохранён исторический обзор 2.18.2. Опубликованные `doc/changes/2.18.2.md` и `doc/RECOMMENDATIONS.md` прямо отмечают отсутствие нового session/resource API. PC1/PC2 уже исправлены; для следующего шага нужен публичный контракт SC1 либо поддерживаемая композиция текущих API. Приватный документ планирования в исходном репозитории не считается опубликованным API.

Статус: подтверждённое ограничение текущей поверхности и предложение по композиции, **не дефект авторизации**. Проверены опубликованные common2 2.18.1 и react2 3.3.0. Первый потребитель — peer-присутствие органайзера; следующие — conversation и AI run из той же библиотеки.

## Конкретная потребность

Сервис уже запущен через `createServiceLeaderHost`/`runLeaderProcess`, браузер подключён через `createServiceClient` и имеет текущие права. Нужно выдать этому пользователю дополнительный типизированный peer-фасад и освободить его при выходе из комнаты, потере права, смене principal или закрытии сессии. Команды/представления органайзера продолжают работать через существующий runtime.

Нужна небольшая общая точка композиции фасадов с уже имеющимися аутентификацией, ресурсным lifecycle и клиентской сессией. Предметное решение, какую комнату/задачу пользователь видит, задаёт приложение.

## Проверенное основание

В установленном пакете проверены публичные декларации и `doc/SERVICE-RUNTIME.md`:

| API | Доступная поверхность | Недостающая композиция |
| --- | --- | --- |
| `tServiceDefinition` | commands, views, access, readerFacet, version/migrate | Нет объявленной фабрики дополнительного защищённого фасада с владельцем сессии |
| `describeService` | name, названия команд и views/allow | Не описывает дополнительную типизированную клиентскую поверхность |
| service host `mount` | app, leader/node, url, signal, disposer | HTTP/общий lifecycle хоста; не callback создания аутентифицированной RPC-сессии |
| `createServiceClient` | commands, views, identity, health, placement/repick, close | Нет публичного адаптера дополнительного фасада текущей сессии |
| низкоуровневые `rpc`, `createHostResource`, `createServiceLeader` | Дают необходимые строительные блоки | Существующую service-композицию приходится вручную повторять/разветвлять |

`readerFacet` не является подходящим местом: это чтение, а peer включает публикацию, signaling и ресурс на подключение. Курсоры не нужно превращать в durable-команды с receipts и сохраняемые проекции.

Работающие строительные блоки продемонстрированы в [peer-network-check.ts](../../apps/pizzeria/organizer/peer-network-check.ts): публичный service выдаёт/проверяет токен, fixture создаёт peer и подключает его через публичный RPC. Это доказывает, что новый транспорт и новая авторизация не требуются. Но такая fixture не заменяет готовый service runtime: она не реализует весь lifecycle обновления прав, обновления токена, смены узла и стабильных клиентских handles. Копировать эти обязанности в каждый продукт не предлагается.

## Задание

Сначала предложить поддерживаемую композицию **существующих** публичных API. Если можно встроить дополнительный фасад без копирования host/client/session и скрытых импортов, достаточно документированного адаптера и проверки в органайзере. Если нельзя — добавить минимальную точку расширения в service runtime. Названия API и форма регистрации намеренно не навязаны.

Не требуется универсальная система плагинов, собственный room server, новая система ролей, транспорт или общий граф зависимостей. Не нужно делать peer обязательной зависимостью каждого service. Серверные фабрики и секреты не должны попадать в JSON descriptor или браузерный bundle.

## Критерии готовности

1. Первый пример — существующий organizer definition + peer-фасад на текущей аутентифицированной сессии; второй небольшой потребитель — другой фасад ресурса без специальной ветки для peer в runtime.
2. Тип удалённого фасада выводится из публичного контракта. Клиент не приводит приватный RPC hub к самописному интерфейсу. Потребитель может подключить `createPeerClient` и существующие React hooks.
3. В фабрику передаётся проверенный principal и явный контекст жизни сессии. Идентификатор подключения выдаёт сервер; его нельзя использовать для подмены аккаунта из handshake.
4. Запрет доступа действует при создании, последующих вызовах и существующих подписках согласно документированному контракту. Сохранённый фасад после отзыва не продолжает действие; основной фасад разрешённых функций остаётся пригодным.
5. Disconnect, reauth, смена аккаунта, отзыв прав и закрытие host освобождают ресурсы один раз; поздно завершившаяся асинхронная фабрика не воскресит прежнюю сессию. Незавершённые отписки не создают unhandled Promise.
6. Политика размещения дополнительного фасада явная: первый peer-host может принадлежать authority. Переход основного клиента на serving node не должен молча создавать изолированную вторую комнату. Если автоматически маршрутизировать этот фасад пока нельзя, это ограничение явно отражено в контракте и проверке.
7. Reconnect даёт актуальную поверхность/признак недоступности, а не оставляет видимость успешно работающего старого ресурса. Гарантии стабильности handles определены и покрыты тестом.
8. Проверены успешный доступ, отказ, текущая подписка при отзыве, две вкладки одного аккаунта, reconnect и смена serving node. Descriptor остаётся безопасными данными.

Выпускать минимальный объём для первого потребителя. Не обещать бесшовное межузловое перемещение произвольного ресурсного фасада без проверки.

## Что остаётся органайзеру

- Кто видит доску и конкретную карточку; общая комната не раскрывает приватные задачи сотрудников.
- Координаты и преобразования, цвета/имена, выбранная карточка и режим следования.
- Частота обновления и срок отображения курсора, интерфейс неактивного участника.
- Правила конфликтов, ревизии задач и итоговый commit после drag.

Это задачи примера, пока повторное применение не докажет необходимость малого общего примитива. SC1 не требует переносить их в common2 или react2.
