## 2. Проверено кодом, но требует нового запуска

- Пиццерия: `npm test` включает account-id, inventory, host, доменные и сетевые проверки, органайзер, peer, collaboration, canvas и communication. `network-check.ts` описывает отдельные writer PID, изоляцию токенов/фотографий, остановку serving node и рестарт writer с архивом. Это хорошая база проверки 3.1.1, но наличие теста не равно текущему прохождению.
- Органайзер: resource RPC и синтетическое media-generation проверяются автоматически; browser media проверка запускается отдельно. Touch, реальный экран/микрофон, HTTPS между физическими устройствами и поведение при отзыве требуют [DEVICE-ACCEPTANCE](../DEVICE-ACCEPTANCE.md). AI persistence использует публичное replay storage и локальный fsync; платный провайдер не проверялся.
- Хостинг: `npm test` включает протокольные/fixture проверки Docker, агента, gateway, LXD, orchestration и WebSocket. Реальные `test:docker`, `test:stateful`, `test:public-address`, `test:<product>` и `test:library-audit` — отдельные команды, не всё это входит в корневой `check:all`.
- Витрина: тест сверяет карточки с STATUS, заполненность и отсутствие Markdown в текстовых полях. Он проверяет только префикс генератора, а не полное совпадение `products.js` с результатом генерации. Схема сценария не является снимком интерфейса; `visualOf` всегда рисует схему.

Ограничения: один владелец записи, без HA базы и автоматического избрания нового writer; LXD fixtures не настоящие VM, Kubernetes не принимался; локальные gateway не доказывают межмашинную сеть; оплаты, внешнего OIDC и платного AI нет. Никакая задача ниже не требует тяжёлого кластера или запуска моделей.

## 3. Разрывы контроля, подтверждённые чтением до исправлений

| Наблюдение | Доказательство и следствие |
| --- | --- |
| Результаты не связаны с проверенной версией | `run-all.writeLog` пишет только exit/date/duration. `status.collect` читает версии из текущего package.json, а успех — из последнего лога. После major update можно получить новые версии рядом со старым ✓ |
| Пропуск оставляет старый результат | `execute` при отсутствующем инструменте возвращает «пропущено», не вызывая writeLog; `--skip` исключает приложение из обхода. STATUS не знает о таком пропуске и может сохранить старый успех. `runAll` возвращает ошибку только для `fail`, отсутствие script тоже не блокирует |
| Docker gate слишком широкий | `missingTool(app)` вызывается до любого script: `wenayExamples.requires: docker` у hosting блокирует даже typecheck/build без Docker. Workflow отдельно просит typecheck hosting через тот же runner |
| Не весь скелет охвачен общей командой | Корневой `check:all` включает sync/style/links/status, но не `scripts/scaffold-check.mjs`. Поэтому полнота scaffold manifest и защита копирования не являются постоянным CI gate |
| Самостоятельный UI органайзера не собирается общей командой | `pizzeria build` собирает frontend; `build:organizer` отдельный. STATUS одновременно учитывает размер organizer-public, который может быть старым |
| Текст архитектуры пиццерии отстал | README перечисляет backend/leader.ts, access.ts, rest.ts и client.ts; текущие входы импортируют опубликованный service host/client. В tracked перечне этих инфраструктурных файлов нет |
| Колонка «Копия» не доказывает восстановление | `status.collect` выставляет ✓ по существованию backend/backup-check.ts, без проверки его запуска и результата |
| Холодная копия требует доверия к остановке | backup проверяет опциональный port и флаг stopped. После копирования digest вычисляется на копии и повторно на копии; источник не сравнивается. Restore проверяет format, пути, размеры и hashes, но dataVersion сверяет только если обе стороны его указали, совместимость библиотек не проверяет |

Последнее — граница холодного инструмента, а не требование реализовать горячий backup. Восстановление должно принимать совместимую пару кода и архива; хеши удостоверяют байты, но не бизнес-совместимость.

CI в `.github/workflows/check.yml` ставит Node 22/Python 3.12 и `npm ci` приложений, пропускает hosting в общей команде, затем запускает его typecheck отдельно. Успешный запуск workflow на GitHub этим аудитом не подтверждён. Исторический [отчёт плана 3](PLAN3-REPORT.md) тоже прямо отделяет локальное воспроизведение workflow от настоящего GitHub запуска.

### Исправления контроля в текущем этапе

`run-all.mjs` теперь пишет status (включая явный skip), время и SHA256 содержимого package.json + package-lock.json. `status.mjs` отвергает legacy логи и несовпадающий fingerprint: старый успех не подтверждает новую npm-пару. Требования Docker применяются только к test, поэтому typecheck/build не требуют Docker. `status --verify` продолжает сверять версии, приложения, результаты и пропуски; время, длительности и размеры сборки исключены из сравнения, чтобы новый равнозначный прогон не требовал коммита метрик.

Регрессия `node scripts/run-all-status-check.mjs` на изолированном временном fixture проверяет success, устаревший package/lock, skip, legacy log, пропуск отсутствующего инструмента только для test и стабильность сравнения динамических полей. Полный прогон приложений выполняет основной этап обновления; этот отчёт не присваивает ему результат заранее. Отпечаток зависимостей не удостоверяет ревизию исходников: добавление source/revision fingerprint остаётся следующим усилением.

Основной этап также добавил standalone organizer build в `pizzeria npm build`; наблюдение о прежнем пробеле сохранено как объяснение изменения. Остальные разрывы таблицы остаются задачами, а не автоматически закрытыми пунктами.

## 5. Процесс обновлений и поиска библиотечных багов

1. **Сначала зафиксировать проверяемое состояние.** В отдельном журнале major update сохранить старую/новую пары, exports и engines опубликованных пакетов, lock integrity, список изменений API и архивные версии. Обновлять библиотеки отдельно от toolchain: одновременная смена React/TypeScript/Vite затрудняет локализацию. Если toolchain уже изменён, учитывать это как отдельную ось сравнения.
2. **Связать результат с кодом.** Runner записывает единый run ID, app, script, exit или skipped reason, lock hash и ревизию/отпечаток исходников. STATUS отображает точную проверенную пару. После изменения входов успех устаревает; skip не наследует старое ✓. Скрипт, обязательный по профилю, не может исчезнуть молча. Полные typecheck/test/build идут последовательно в бюджете RAM.
3. **Два явных профиля.** Лёгкий gate: типы, fixture/domain/RPC, оба UI органайзера, sync/style/links/status и scaffold-check. Live gate: Docker продуктов, persistent volume/public address/rollback, cold restore. Ручной device gate имеет свой протокол. Пропуск внешней среды сохраняется как пропуск, а не успех или библиотечная ошибка.
4. **Сначала повторить открытые repro.** [WORKAROUNDS](../library-tasks/WORKAROUNDS.md) и [CURRENT-HANDOFF](../library-tasks/CURRENT-HANDOFF.md) описывают три проблемы на 2.21.1: nested replacement, AI policy invalidation и AI resource lifecycle. Повторить обычный и `--expect-fixed` режимы на 3.1.1; historical status не переносить. Удалять workaround только после доказанного прохождения и проверки потребляющих приложений. Новая major версия сама по себе не закрывает задачу.
5. **Один риск — законченный пользовательский сценарий.** Для RPC: разрыв после отправки до ответа + повтор requestId; для ролей: отзыв с открытым фасадом/resource replay; для Store: вложенная замена + snapshot/replay; для ресурсов: позднее завершение после close/abort; для React: mount/unmount, reconnect, pointer/keyboard/cancel; для persistence: остановка во время незавершённой работы. Поведение проверять через фасад, без доступа к private internals.
6. **Локализовать до передачи библиотеке.** Если сбой появляется в приложении, выделить маленький repro только с опубликованным API и точной npm-парой. Сравнить старую и новую пары на одинаковых входах. Зафиксировать ожидаемое/фактическое, шаги, stdout/error, teardown и criterion `--expect-fixed`. Общее удобство передавать библиотеке при двух независимых потребителях; доказанный дефект не требует второго потребителя.
7. **Подтвердить исправление использованием.** После опубликованной версии обновить lock, повторить repro и исходный пользовательский сценарий, убрать только соответствующий workaround и записать результат в doc/changes. Канонические shared файлы адаптировать один раз, разослать sync и проверить всех потребителей. Коммиты обновления — отдельно по приложению; main только после требуемого check:all.

Не требуется расширять число приложений ради API-покрытия. Сильнее всего проявляют библиотечные границы существующие сценарии: пиццерия связывает транзакцию и автоматику; органайзер — отзыв и lifecycle нескольких ресурсов; hosting — uncertain IO и restart; витрина — достоверность результата. Следующий план стоит начинать с P0 миграции и результатов gate, затем брать по одному P1 сценарию и оформлять только воспроизведённые общие проблемы.
