# Холодная копия и восстановление данных

Дата: 11 сентября 2026. Задача O01 [плана 2](../CONSOLIDATION-PLAN.md), первая версия по [плану K04](../K04-BACKUP-RESTORE-PLAN.md).

Сделан прикладной инструмент **холодной** копии каталога данных приложения с проверкой целостности и восстановлением в новое место. Горячий согласованный snapshot работающего сервиса, HA-authority и автоматические миграции формата в эту версию не входят.

## Инструменты

```text
node scripts/backup.mjs <приложение> <пустой каталог> --i-stopped-it [--from=каталог] [--port=NNNN] [--data-version=X]
node scripts/restore.mjs <каталог копии> <новый пустой каталог> [--data-version=X]
```

`backup.mjs` берёт каталог данных из точки входа приложения (`SERVICE_DATA_DIR ?? path.resolve('<имя>')`) либо указанный `--from`, копирует его потоково целиком и пишет рядом `manifest.json`:

| Поле | Зачем |
| --- | --- |
| `format` | Версия формата копии, `wenay-cold-backup-1` |
| `app`, `dataDirectory` | Куда возвращать |
| `dataVersion` | Формат данных приложения; восстановление в чужой формат отклоняется |
| `libraries` | Точные версии common2 и react2 на момент копии |
| `takenAt` | Время точки копирования |
| `files` | Относительный путь, размер и SHA-256 каждого файла |

Признак завершённости `complete` пишется последним: неполная копия не восстанавливается. Значений секретов и пользовательского текста в manifest нет.

Копируется **весь** каталог данных, а не выбранные маски: так новые файлы ресурсов не теряются. У поддержки это `support.jsonl`, `support.control.jsonl` и подкаталог помощника с `drafts.replay`, `runs/runs.replay` и файлами; у документов — журналы, `processing/runs/runs.replay` и `processing/blobs/*` с байтами исходников.

## Защиты

| Проверка | Поведение |
| --- | --- |
| Писатель не остановлен | Без `--i-stopped-it` копия не делается. Если указан `--port`, отвечающий `/health` останавливает работу с явной ошибкой |
| Непустое назначение | Отказ: копия и восстановление работают только в пустой каталог |
| Пересечение путей | Копия не может лежать внутри исходного каталога; восстановление не может пересекаться с копией |
| Ссылки в данных | Symlink в каталоге данных прерывает копирование |
| Неполная копия | Нет `complete` — восстановление отказывает |
| Чужой формат данных | Несовпадение `dataVersion` отклоняется до первой записи |
| Опасный путь в manifest | Абсолютный путь, `..`, обратный слэш и повтор пути отклоняются |
| Повреждённый файл | Размер и SHA-256 сверяются до первой записи: полукопии не остаётся |

Закрытый порт сам по себе ничего не доказывает — это записано в тексте ошибки и в README: фоновые исполнители (probe, обработчики документов) нужно останавливать отдельно.

## Живые проверки

Обе входят в `npm test` соответствующего приложения и запускаются отдельно как `npm run test:backup`.

**Поддержка** — `apps/support/backend/backup-check.ts`. Поднимает сервис на временном каталоге, создаёт обращение, останавливает сервис, делает копию, восстанавливает в новый каталог и запускает сервис уже на нём. Проверено: отказ без подтверждения остановки, наличие manifest и `complete`, отказ при несовпадении формата данных, отказ по повреждённому файлу без остатка полукопии, совпадение числа обращений, сохранённая тема и текст переписки.

**Документы** — `apps/documents/backend/backup-check.ts`. То же, но с настоящей загрузкой файла через SC1-ресурс. Дополнительно проверено, что в копию попал `processing/blobs/*` и что после восстановления `control.download` отдаёт исходные байты без изменений: восстанавливается не только запись о документе.

**Учёт** — `apps/metering/backend/backup-check.ts` (добавлено 11 сентября 2026, задача P03 плана 3). Выпускаются два ключа, резервируются 20 единиц и подтверждаются 12, второй ключ отзывается. После восстановления совпадают журнал расхода и лимиты организации, повтор того же `eventId` с новым command requestId возвращает `fresh: false` и не удваивает расход, секрет ключа в проекции отсутствует, отозванный ключ остаётся отозванным.

**Формы** — `apps/forms/backend/backup-check.ts` (добавлено 11 сентября 2026, задача P03 плана 3). Форма публикуется, приходят два ответа, один удаляется. После восстановления агрегат равен одному ответу, удалённый текст не возвращается ни в списке, ни в выдаче, а повтор его ключа приёма отклоняется надгробием — то есть копия сохраняет и удаление, а не только записи. Копия, снятая **до** удаления, старый текст содержит: это свойство резервных копий, и его закрывает отдельная политика хранения, а не инструмент.

**Остальные продукты** — `apps/{crm,booking,monitoring,content,approvals}/backend/backup-check.ts` (добавлено 11 сентября 2026, задача P04 плана 3). Это общая короткая проверка одного вида: создаётся одна предметная запись (компания, ресурс с расписанием, приостановленная проверка, черновик страницы, черновик заявки), сервис останавливается, снимается копия, восстанавливается в новый пустой каталог и запускается уже на нём. Проверяется отказ без подтверждения остановки, отказ при несовпадении формата данных, наличие manifest и признака завершённости, сохранность исходного каталога по списку файлов manifest и совпадение предметной записи после восстановления.

Предметных следствий копии (повтор события, надгробие удаления, байты вложений) эта общая проверка не касается — они проверяются там, где имеют смысл: поддержка, документы, учёт и формы.

## Что не сделано

- **Горячая копия.** Работающий сервис не копируется. Неизменный размер файла согласованности не доказывает, и выдумывать публичный `flushAll` в библиотеке мы не стали.
- **pizzeria и hosting.** У пиццерии и хостинга структура данных другая (несколько сервисов и каталог рабочих окружений), общая проверка к ним не применялась — в колонке «Копия» файла [STATUS](../STATUS.md) у них стоит «—». Для хостинга остановка и изолированное копирование тома проверяются отдельно в `apps/hosting/backend/stateful-live-check.ts`.
- **Docker-том.** Копирование тома запущенного контейнера здесь не автоматизировано; существующий путь остановки и изолированного копирования тома есть в `apps/hosting/backend/stateful-live-check.ts`.
- **Секреты.** `SERVICE_TOKEN_SECRET` и `SERVICE_NODE_TOKEN` в копию не входят и восстанавливаются оператором отдельно.
