# Обработка документов: createAiRunHost против createFileJobHost

Дата: 11 сентября 2026. Задача L03 [плана 2](../CONSOLIDATION-PLAN.md). Основание — пункт 2 раздела «Использован ли функционал максимально» [контрольной точки 10 сентября](../internal/SAAS-CHECKPOINT-2026-09-10.md): обработка построена вокруг `createAiRunHost`, хотя в библиотеке есть специализированный `createFileJobHost`.

**Решение: оставляем `createAiRunHost`.** Ниже — на чём оно основано.

## Что даёт каждый хост

| | `createFileJobHost` | `createAiRunHost` (используется) |
| --- | --- | --- |
| Файл | Своя запись `FileResource` с состояниями `uploading`/`uploaded`/`failed` | Файла не знает; документ живёт в состоянии сервиса |
| Задание | `FileJob` с `progress`, `message`, `result` | `AiRun` с состояниями, прогрессом, отменой и approvals |
| Связь с предметной записью | `fileId` внутри собственного стора | `resourceIds` запуска указывают на документ сервиса |
| Хранение | Порт `FileStoragePort` | Свой порт persistence плюс `createLocalBlobStorage` приложения |
| Восстановление после рестарта | В контракте нет | `host.recovery.settle(runId, ...)` — явное разрешение судьбы прерванного запуска |
| Права | `policy.canRead/canWrite` по файлу | Policy запуска плюс обычная проверка организации в командах |

## Почему не переносим

**Решает восстановление.** Обработка документа — длительная внешняя работа: дочерний процесс Node или Python может не вернуться из-за перезапуска сервиса. `createAiRunHost` даёт `recovery`, и documents им пользуется: при старте каждый прерванный запуск разбирается явно — если документ дошёл до `review` или `approved`, запуск завершается как выполненный, иначе помечается прерванным с разрешением новой попытки, а в домен уходит `processingFailure` со статусом `uncertain`. В контракте `createFileJobHost` восстановления нет: у `FileJob` есть состояния `queued`/`running`/`ready`/`failed`/`cancelled`, но нет поверхности, которая после рестарта переведёт зависший `running` в осмысленное состояние. Приложению пришлось бы писать эту логику самому — то есть заменить один готовый механизм на самодельный.

**Файл уже не в хосте.** `FileResource` дублировал бы документ: у документа есть организация, владелец, `sourceVersion`, статус проверки, таблица, комментарии и утверждения — ничего этого в `FileResource` нет и быть не должно. Байты исходника уже лежат в `createLocalBlobStorage`, а запись о документе — в состоянии сервиса, где её видит домен и покрывают обычные права. Перенос дал бы третье место хранения сведений об одном и том же файле.

**Проверка попытки остаётся предметной.** Результат обработки принимается только если `activeRun` и `attempt` документа совпадают с пришедшими: поздний ответ отменённой попытки отклоняется. Это правило живёт в доменной команде `processingResult` и опирается на состояние документа, а не на состояние задания. Ни один из двух хостов его не заменяет.

## Что было бы дешевле с FileJobHost

Честно: две вещи.

- `startUpload`/`confirmUpload` дали бы готовый двухшаговый приём файла. Сейчас это отдельные команды домена с проверкой хеша, размера и владельца — около 30 строк.
- `progress`/`message` у задания чуть ближе к задаче, чем общий прогресс AI-запуска.

Обе экономии меньше, чем стоимость собственного восстановления после рестарта, и обе не отменяют предметных проверок.

## Когда решение следует пересмотреть

- Если `createFileJobHost` получит восстановление прерванных заданий, сопоставимое с `recovery` AI-хоста.
- Если появится второй продукт с такой же загрузкой файлов и без потребности в предметной записи документа: тогда общий файловый хост окупится.

Как задача библиотеке это не оформляется: одного потребителя мало, а текущая композиция закрывает сценарий публичным API без обходов.

## Проверка

Решение не меняет кода. Отчёт опирается на публичный контракт `createFileJobHost` установленной версии, на `apps/documents/backend/processing-resource.ts` (325 строк, включая восстановление) и на команды `processingStart`, `processingResult`, `processingFailure` в `apps/documents/backend/domain.ts`.
