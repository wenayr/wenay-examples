# Monitoring — самостоятельная копия, HTTP и обновление контейнера

Проверено 10 сентября 2026. `wenay-common2@2.21.1`, `wenay-react2@3.5.1`. Тесты не используют платные модели и не запускают соседние тяжёлые приложения. Рабочий preview на 3816 и его данные не менялись.

## Самостоятельная копия

Явный scaffold manifest включает 45 файлов: backend, HTTP probe и его проверки, редакторский интерфейс, общий прикладной task-domain, локальные React-адаптеры, Dockerfile и правила. Новая копия имеет npm-имя `monitoring-standalone`, сервисный ID остаётся `monitoring`.

Из пустого каталога прошли `npm ci` (162 пакета), typecheck, build и полный `npm test`:

- Доменные роли, цели, ревизии, аренда, пороги, дедупликация инцидента/задачи/уведомлений.
- Реальный ограниченный HTTP: address pinning, запрет redirect, caps, timeout, malformed targets.
- Встроенный probe: credential login, техническая роль, HTTP при недоступном внешнем адресе gateway, отказ записать поздний результат после отзыва членства.
- AI-сводка: факты, приватный результат, изменение источника, отмена/timeout, отзыв доступа.
- Настоящий authority + два serving nodes + два отдельных probe-процесса: оба выполняют HTTP, работа распределяется, второй подхватывает первую цель при отказе; отключение serving node и полный restart сохраняют данные и продолжают расписание.

Frontend: `index-Ds-uNzwM.js`, CSS `index-DQMtTSLx.css`. Vite сообщает о будущем native config loader и общем chunk около 579 kB; ошибок типов/сборки нет. Браузерный отчёт — [MONITORING-UI-ACCEPTANCE.md](../internal/acceptance/MONITORING-UI-ACCEPTANCE.md).

Общий scaffold-check проходил семь шаблонов после добавления Monitoring; дальнейшая параллельная переработка Documents выявила отсутствующий в его manifest `model-extraction`. Этот отдельный набор обновляет владелец Documents. Окончательная самостоятельная копия Monitoring со всеми локальными импортами прошла независимо.

## Найденная и исправленная проблема композиции

Первая установка показала, что встроенный сетевой probe получает внешний адрес хостингового gateway из roster. Этот адрес недоступен изнутри контейнера, и клиент не находит работающий endpoint. Это проблема адресации встроенного клиента, а не подтверждённый дефект common2.

Общий цикл HTTP/аренд выделен из сетевого adapter. Отдельный процесс использует прежний `createServiceClient`. Встроенный проходит публичный `leader.serve.login`, читает разрешённую assignment projection и вызывает `leader.corridor.fragment` под техническим аккаунтом. Права перечитываются на сервере, системный аккаунт не используется. Новый тест подтверждает работу при заведомо недоступном advertised URL и запрет позднего отчёта после отзыва роли. Полный тест двух сетевых probe также повторно прошёл.

Удалённым исполнителям по-прежнему нужна достижимость объявленных адресов. Автоматическое соединение разных частных сетей не реализовано и не подменяется этим адаптером.

## Docker first → second → rollback

Образы собраны последовательно из окончательной самостоятельной копии; базовый Node 24 Alpine закреплён digest. Сборка использовала существующий Docker driver, `--memory 768m`, heap npm 256 MiB. Дополнительный BuildKit-контейнер, неожиданно инициированный первоначальным выбором builder, остановлен; отдельный сборщик для итоговых образов не понадобился.

| Образ | Digest |
| --- | --- |
| `wenay-examples.local/monitoring:first` | `sha256:589508fa96052de97263053baf18d36190714c73bddd39cd2848a4ba0d40d271` |
| `wenay-examples.local/monitoring:second` | `sha256:cf22892929dcead44e4ef2e99d75979227573e3d0dc6f1162a1605805420a2f9` |

`npm run test:monitoring` из `apps/hosting` прошёл через настоящий Docker-agent, стабильный gateway и постоянный том:

1. На `first` встроенный probe делает HTTP GET к заведомо отсутствующей собственной странице. Полученный 404 открывает инцидент и одну задачу. Дежурный сохраняет внутреннюю заметку. После паузы создаётся частная сводка с этой заметкой.
2. На `second` восстанавливаются прежняя история, инцидент, задача и сводка. Монитор переключается на собственный `/health`: настоящий 200 закрывает инцидент. Человеческая задача остаётся `todo`. Старую сводку сервер отклоняет из-за новых фактов. Первый пункт checklist отмечается, задача переводится в работу, создаётся свежая сводка; роль дежурного отзывается.
3. После отката на `first` сохранены 404/200, закрытый инцидент с заметкой, задача `doing` с одним незавершённым пунктом и свежий частный результат. Старый bearer дежурного получает явный forbidden через стандартный REST библиотеки. Workspace/публичный статус и AI replay не раскрывают частную заметку неразрешённому читателю.

Релизы различаются `APP_RELEASE` при одной совместимой схеме. Миграция между несовместимыми dataVersion этим тестом не заявляется. Повтор create command сохраняет ID монитора и не создаёт второго инцидента/задачи.

Проверен фактический лимит каждого контейнера: 256 MiB, 0.5 CPU, пользователь `node`, собственная метка owner. Снимки памяти: first 57.49 MiB, second 57.39 MiB, rollback 56.62 MiB. Это не измерение пикового RSS. Тест удаляет только собственные контейнеры, том и временные данные; действующий UI preview и чужие ресурсы не затронуты.

## Границы результата

UI-fixture остаётся явно демонстрационным источником отчётов и не входит в Docker. В этом приёмочном сценарии 404/200 получены настоящим HTTP. AI — тестовый исполнитель по фактам, автоматической команды хостингу нет. Приватные старые сводки не выдаются после изменения прав/фактов, но их отдельная физическая retention-политика пока не реализована.

Следующий K04 описан в [плане backup/restore](../K04-BACKUP-RESTORE-PLAN.md): холодная согласованная копия данных и control journal, частных файлов и checkpoints, восстановление в отдельное пустое место и проверка бизнес-идемпотентности. На этой контрольной точке это план, не выполненная новая backup-функция.
