# Пиццерия: пять ролей и польза библиотек

Проверено 8 сентября 2026 года, приложение 0.4.0. Зависимости: `wenay-common2@2.16.0`, `wenay-react2@3.1.0`, опубликованные npm-пакеты без локальных подмен и Zod.

Дополнение 0.5.0: реализованы [полные карточки блюд и фотографии](../../apps/pizzeria/DISHES.md). Новых зависимостей нет; роли и публикация меню используют прежние фасады/replay. Добавлен небольшой бинарный ресурс хранения фотографий. Приведённые ниже числа строк относятся именно к версии 0.4.0, до этой доработки.

Дополнение 0.6.0: опубликованный common2 2.16.1 принят вместе с исправленным scaffold-клиентом; сетевые проверки прошли. Добавлен [органайзер](../../apps/pizzeria/organizer/README.md) в двух режимах. `useReorderBoard` react2 теперь обеспечивает основную операцию нового UI — перенос карточек внутри/между колонками; собственная геометрия перетаскивания не потребовалась. Проверены автоматические задачи пиццерии, работники и права, конкуренция изменений и сохранение. Первоначальные выводы о небольшой роли react2 относятся к версии 0.4.0.

## Вывод

**common2 оказался полезен:** приложение использует его для команд, RPC-фасадов, реактивных проекций, replay, репликации, сохранения истории и повторов запросов. Это основные механизмы работающей сети, а не декоративные импорты. Предметная модель с рецептами, партиями, резервами, порчей и ролями занимает 498 физических строк.

**Обещание «вся пиццерия — совсем немного кода» пока выполнено частично.** Активное приложение содержит 3191 строку, из них 2071 — адаптированный общий scaffold. Значительную часть инфраструктуры уже делает библиотека, но её связывание в сервис остаётся в примере. Следующее выгодное улучшение — уменьшить именно этот повторяемый каркас.

**Польза react2 в этом примере уже:** используются `useStoreNode` и CSS-токены. Они связывают React с библиотечным состоянием и оформлением; готовые сложные компоненты react2 здесь почти не задействованы. По этому приложению нельзя доказать преимущество всего набора компонентов.

Проценты сэкономленного времени и кода не оценивались: равноценной реализации без библиотек и измеренного сравнения нет.

## Что пройдено от каждого лица

Браузерный проход выполнен в пяти отдельных вкладках на свежей сети из двух независимых заведений.

| Роль | Действия и наблюдаемый результат |
| --- | --- |
| Клиент | Регистрация Бориса; добавление в корзину, оформление и отмена первого заказа. Заказ нового блюда, живые переходы до доставки. После изменения цены и скрытия блюда принятый заказ сохранил название и цену 15 €. Переход в другое заведение потребовал отдельного входа; возврат восстановил собственную историю. |
| Менеджер | Создал ингредиент «Перец», принял 200 г с указанным сроком годности, создал блюдо с расходом 100 г. После заказа увидел резерв 100 г и свободный остаток 100 г. Пополнил склад после порчи. Изменил цену на 17 € и скрыл блюдо: оно исчезло из клиентского меню без обновления страницы. |
| Повар | Отметил 150 г испорченного перца с причиной. Начать приготовление не удалось: приложение сообщило о нехватке 50 г. После поступления ещё 100 г тот же заказ удалось приготовить и отметить готовым. |
| Курьер | Получил готовый заказ, забрал его и завершил доставку. Его интерфейс не показывал склад и управление сотрудниками. |
| Владелец | Отозвал у менеджера роль: уже открытая вкладка стала клиентской. Вернул роль: склад и управление блюдами появились без повторного входа. После входа владельцем в оба заведения сводка показала 15 € в Центре, 0 € на Севере и охват 2 из 2. Увеличение числа узлов Севера с 1 до 2 запустило дополнительный процесс. |

Для повара и курьера кнопки завершения доступны у назначенного им заказа; сервер также проверяет исполнителя. Отдельные автоматы на роли или отдельный транспорт не создавались.

## Проверки вне браузера

`npm run typecheck`, `npm test`, `npm run build` завершились успешно. В журналах пяти вкладок ошибок не обнаружено. Сборщик оставляет предупреждения о будущем загрузчике конфигурации Vite и каталоге результата вне frontend; сборку они не блокируют.

Исполняемые проверки покрывают:

- идентификаторы заказов разных аккаунтов и повтор requestId;
- роли, проверку рецептуры, резервирование, освобождение резерва при отмене, расход партий по ближайшему сроку годности;
- неизменность принятой рецептуры, списание порчи без двойного расхода, отсутствие частичных изменений при нехватке и восстановление после пополнения;
- отказ приготовления из просроченных партий и миграцию старого состояния — это серверные проверки, а не ожидание истечения срока в браузере;
- урезанные RPC-фасады, отсутствие чужих заказов и лишних персональных полей, очистку уже открытой закрытой проекции после отзыва роли;
- независимые процессы записи, изоляцию ключей и данных, переход живого клиента после остановки узла и возврат к authority после остановки всех узлов;
- увеличение и уменьшение реальных процессов, продолжение работы второго заведения при остановке первого, восстановление архива и receipts, сохранение топологии после перезапуска;
- продление короткого токена клиентом, созданным с готовым токеном, и передачу нового токена потребителю.

## Где библиотека делает работу

| Механизм | Используемая поверхность | Что остаётся в приложении |
| --- | --- | --- |
| Единая запись и повторы | `Scale.createAuthority`, файловое replay-хранилище | Команды, переходы заказа, складские ограничения |
| Реплики | `createStoreNode` | Запуск процессов, конфигурация заведений, их жизненный цикл |
| Связь и выбор узла | `createRpcClientHub`, `followNodeDirectory`, `pickDirectoryNode` | Связывание endpoint и сессии, исключение отказавших кандидатов |
| Живые данные | `deriveStore`, `exposeStoreReplay`, `syncStoreReplayRoute` | Проекции ролей и политика доступа, переключение независимых источников |
| Идентификация | `createTokenCodec`, библиотечный token provider | Аккаунты, назначение ролей, хранение обновлённого токена в браузере |
| HTTP и описание API | `createHttpFacadeServer` и связанные публичные инструменты | Выбор операций, адаптация схем входа, прикладные проверки |
| React | `useStoreNode`, CSS-токены react2 | Формы, корзина, страницы ролей и обработка действий |

Фасады задают доступную поверхность для роли. Право на команду проверяется authority заново; предметное правило вроде «доставляет назначенный курьер» остаётся внутри команды.

## Найденные проблемы и следующие задания

1. **Переход между независимыми replay-проекциями.** Перенос старого курсора оставлял зеркало заказа несвежим после смены узла. Исправлено через существующий API сброса источника; добавлены ограничение ожидания endpoint и исключение отказавших кандидатов. Это ошибка интеграции поставляемого примера, а не доказанный дефект ядра replay. [Готовое задание для common2](../library-tasks/pizzeria-client-handoff.md).
2. **Права уже открытой сессии.** Теперь закрытые линии проверяют текущие роли при изменениях состояния; клиент сверяет разрешения и пересоздаёт фасад. Цена решения — отдельная закрытая проекция на сессию и опрос раз в секунду. [Задание на улучшение общего клиента и фасада](../library-tasks/pizzeria-session-lifecycle.md).
3. **Продление входа по готовому токену.** Адаптер больше не возвращает прежний токен вместо продления. Новый токен поступает через callback и сохраняется для дальнейшего использования.
4. **Сокращение scaffold.** Выгодно перенести повторяющееся связывание service definition, identity, RPC и replay в поддерживаемую библиотечную фабрику или исправленный генератор. Предметные правила туда переносить не нужно. Критерий успеха — следующий пример использует тот же механизм без копирования и исправления сотен строк клиента и access.

Sol low использован для независимого анализа публичных API и состава файлов. Его результаты проверены по исходникам; связанную реализацию и браузерные сценарии выполнил основной агент. Из этого одного задания нельзя вывести общую оценку скорости разных моделей.

## Границы результата

Это законченный локальный пример с реальными процессами и проверенными пользовательскими сценариями. У каждого заведения один writer; дополнительные узлы обслуживают подключения и чтение. Межмашинный оркестратор, автоматическая передача владения при отказе writer и публичная эксплуатация с реальными клиентами не проверялись.

Отзыв прав на реплике действует после получения изменения ролей, а обновление UI зависит от подключения. Сводка владельца учитывает только доступные ему заведения и явно показывает охват. Это не глобальная учётная запись владельца и не атомарный финансовый снимок всей сети. Подробности запуска и ограничений — в [NETWORK.md](../../apps/pizzeria/NETWORK.md).
